# Right Screen, Wrong Transition: Using a World Model to Catch Hijacked GUI Agents

Agents that operate phones and browsers by looking at the screen and tapping are now common. They also have a specific weakness. If a malicious app or web page can make a fake login screen appear at the right moment, the agent may type the user's password into it, because the screen itself looks exactly like the real one.

A paper this month, [Right Screen, Wrong Transition](https://arxiv.org/abs/2610.11942) (Zhang et al., 8 October 2026, among the most upvoted on Hugging Face this week), makes one observation and builds a defence on it. Whether a screen is safe depends on **how you got there**. A login screen right after tapping "Sign in" is expected. The same login screen right after tapping "View order" is a warning sign. Their checker, a 261-million-parameter world model, scores 0.987 AUC at spotting these hijacked transitions, about as well as the strongest closed vision-language models, in 17 milliseconds per step.

This post explains the problem, the idea of verifying a transition rather than a screen, and why the model that does it predicts embeddings instead of pixels. That last part follows directly from [the JEPA post](/blog/from-classifiers-to-jepa).

## 1. Why checking the screen isn't enough

The obvious safety check for a GUI agent is a monitor that looks at each new screen and asks "is this dangerous?" A password field, a payment form, a permissions dialog: flag them, and ask the user.

The paper's point is that an attacker can defeat any such monitor, in principle, by reusing a legitimate screen. The fake login page can be a pixel-perfect copy of the real one, because the real one exists and can be captured. A monitor that sees only the screen receives the same input in the safe case and the hijacked case, so it must give the same answer to both.

The authors make this exact. They built a benchmark, **RSWT-Bench**, in which every credential screen appears twice: once as the legitimate result of an action and once, pixel-identical, as a hijacked result with the opposite label. They prove that any detector that looks only at the outcome screen has an expected score of exactly 0.5 on it, which is chance. The benchmark has 966 transitions built from 222 pairs, taken from held-out phone-agent episodes, and a blind check by three human annotators agreed with its labels 96.3% of the time.

## 2. Verifying the transition instead

If the screen alone can't tell you, the step can. The question to ask is: *given the screen I was on and the action I took, is this the screen I should expect?* Answering it needs an expectation of the next state, which is exactly what a **world model** provides: a model of how the environment responds to actions.

GUI world models existed already, and the paper compares against them. They produce their prediction as something a person can read: an image of the predicted screen, a text description of it, or code that renders it. That creates two problems for verification:

- **Comparing is a second hard problem.** Given a predicted image and the observed screenshot, something has to judge whether they "match", and pixel differences are a poor guide: a clock changes, an ad rotates, a list scrolls. So these systems hand the comparison to another large model.
- **They are slow.** Generating an image or code for every step takes from about one second to nearly two minutes per decision in the paper's measurements, far too slow to check every step an agent takes.

## 3. Predicting the next screen's embedding

This is the JEPA idea from earlier on this blog, applied to a new problem. Instead of predicting the next screen's pixels, predict its **embedding**, and compare embeddings directly. The paper's model, **LGWM**, has three parts:

1. **An encoder** turns a screenshot into a grid of patch embeddings. It starts from DINOv2, a self-supervised vision transformer, and is fine-tuned.
2. **An action encoder** turns the agent's action into a vector: the action type (tap, type, scroll), an embedding of any text involved, and for taps, the tapped position on the screen grid.
3. **A predictor**, a 12-layer transformer, takes the current screen's embeddings and the action, and predicts the embeddings of the next screen.

As in I-JEPA, the training targets come from a slowly updated copy of the encoder (an exponential moving average, with no gradient), and extra loss terms keep the embeddings from collapsing to a constant. Patches that actually changed between the two screens are weighted 8 times more in the loss, so the model focuses on what an action does rather than on the static parts of the screen. An auxiliary head also predicts the action back from the two screens, which forces the representation to encode what changed.

The training data is 1.85 million recorded transitions from five public datasets of phone and web interactions, with no labels at all. The model never sees an attack during training.

## 4. The check itself is one line

At run time, the verifier encodes the observed next screen, predicts what it should have been, and measures how far apart they are:

$$
q_{\text{int}} = 1 - \cos\big(\hat{z}_{t+1},\; z^{\text{obs}}_{t+1}\big)
$$

In code, with the trained networks loaded:

```python
import torch
import torch.nn.functional as F

@torch.no_grad()
def transition_suspicion(encoder, action_encoder, predictor, screen_before, action, screen_after):
    """0 when the new screen is what the action should produce; larger when it isn't."""
    z_before = encoder(screen_before)                     # patch embeddings of the current screen
    z_expected = predictor(z_before, action_encoder(action))
    z_observed = encoder(screen_after)
    return 1 - F.cosine_similarity(z_expected.flatten(1), z_observed.flatten(1)).item()
```

If an agent taps "View order" and a login form appears, the predicted embedding looks like an order page and the observed one looks like a login page: the score is high, and the agent stops to ask the user. If it taps "Sign in" and the same login form appears, the prediction matches, and the agent carries on.

There's no threshold tuned on attacks and no labelled examples. The score is a byproduct of the model having learned what normally happens.

## 5. The results

From the paper's main table, measured on RSWT-Bench (AUC, higher is better; latency per decision on one A100 GPU):

| Checker | Size | AUC | Latency |
|---|---|---|---|
| Gemini 3.7 Flash, prompted | closed | 0.995 | not measured locally |
| GPT-5.6 Luna, prompted | closed | 0.988 | not measured locally |
| Qwen3-VL-8B, prompted | 8B | 0.907 | 1,098 ms |
| Generative world model gWorld-8B | 8B | 0.885 | 113,200 ms |
| Code-generating world model Code2World | 8B | 0.870 | 92,900 ms |
| **LGWM** | **261M** | **0.987** | **17 ms** |
| Human annotators (40 examples) | | 0.958 | |

The small embedding model sits with the best closed models, about 10 points above the generative world models, and it is three orders of magnitude faster than those. Fast enough to run on every step is what makes it usable as a guard.

## 6. Telling harmful surprises from harmless ones

A surprising screen isn't always an attack. Apps show pop-ups, crash, or redirect for ordinary reasons. The paper checks this directly: the suspicion score alone separates harmful violations from benign ones no better than chance (0.513 AUC), and prompted vision-language models do little better (0.512 to 0.614).

So the authors add one small supervised piece. They take the *difference* between the predicted and observed embeddings, together with the action, and train a linear classifier on 6,786 examples to tell harmful surprises from harmless ones. That reaches 0.953 AUC. The direction of the surprise carries the information its size doesn't: a login form appearing where an order page was expected is a different direction from a "rate this app" pop-up appearing.

## 7. Where it stops working

- **An attacker who targets the embedding.** If attackers know the verifier, they could try to craft a screen that looks harmful to the user but embeds like the expected one. The authors say how hard that is is something they have not yet quantified.
- **One benchmark.** RSWT-Bench is carefully built but small: 222 source pairs, from phone-agent datasets. Desktop software and the open web are untested.
- **The harm classifier needs labels.** The suspicion score needs none, but telling harmful from benign surprises does, and it was fit on one distribution of examples.
- **Not a full safety system.** It checks whether each transition is consistent with the action. It doesn't judge whether the action was a good idea, and it can't help if the agent was talked into a harmful action by text on a screen that arrived legitimately. That is prompt injection, a separate problem.
- **Embeddings can't be read.** When a person needs to see what the model expected, a rendered prediction is still easier to inspect. The paper says so too.

## The idea in one table

| Approach | What it checks | Weakness |
|---|---|---|
| Screen-only monitor | Is this screen dangerous? | Provably at chance when a legitimate screen is reused |
| Generative world model | Does the observed screen match a predicted image or code? | Needs a second model to compare; 1 to 113 seconds per step |
| Prompted vision-language model | Ask a large model whether the step makes sense | Accurate when large, slow, and near chance at telling harmful from benign surprises |
| LGWM (embedding world model) | Is the observed embedding what the action predicts? | Untested against attacks on the embedding; one benchmark so far |
