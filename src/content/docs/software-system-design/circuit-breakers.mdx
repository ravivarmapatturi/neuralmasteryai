# Circuit Breakers and Controlled Recovery Probes

<ELI5>If a workshop's machine repeatedly fails, workers stop feeding it more material and try a small test later. Stopping new work protects the rest of the workshop, but does not repair the machine. Reopening the whole line after one hopeful guess can recreate the failure. A circuit breaker manages admission while evidence of recovery is gathered.</ELI5>

Implement closed, open, and half-open admission states; select meaningful failure evidence; and cap probes and fallbacks without pretending a breaker repairs dependencies.
A **circuit breaker** temporarily denies calls to a dependency after configured evidence suggests they are unlikely to succeed. This can preserve threads, sockets, deadlines, and downstream recovery capacity. It is one control over future attempts, not a replacement for timeouts, resource bounds, idempotency, or the dependency's own recovery mechanism.

The misconception is that opening a breaker fixes the dependency or makes the denied business action successful. Our illustrative policy opens after five consecutive qualifying failures, waits thirty seconds, then permits one half-open probe. Ten calls arriving during the open interval are denied locally instead of becoming ten more dependency attempts. They still require an honest user-visible outcome.

## Closed, Open, and Half-Open Describe Admission

In **closed** state, calls may reach the dependency while outcomes update the policy's evidence. In **open** state, protected calls are denied or routed through an explicitly permitted alternative. In **half-open** state, a bounded test evaluates recovery. State names refer to the circuit analogy; open means the protected path is interrupted, not freely open to traffic.

A successful probe can permit a controlled return to normal traffic, while another qualifying failure can reopen the breaker. More elaborate policies use several probes, rolling rates, minimum samples, or gradual ramp-up. Whatever policy is chosen, the implementation must bound concurrent probes so a traffic burst does not turn half-open into the original overload.

<RunnableCode code={`failures, open_until = 0, None
for second in range(5):
    failures += 1
    if failures >= 5:
        open_until = second + 30
print("Opened after failure count:", failures, "open until second:", open_until)
for now in (5, 20, 34):
    state = "open" if now < open_until else "half-open"
    print("Second:", now, "state:", state,

The example assumes consecutive failures at seconds zero through four and a single controlled probe after the cooldown. A production breaker needs synchronized state transitions for concurrent requests and a clear clock model. If every caller independently sees the cooldown expire and starts a probe, the numerical policy was never actually enforced.

## Count Failures Relevant to This Dependency

A client sending invalid input should not necessarily cause a dependency's breaker to open for valid callers. Classify timeouts, connection errors, overloaded responses, business rejection, and authorization failures according to the protected operation. A legitimate declined reservation is different from an unavailable inventory service. The breaker should use evidence of path health, not merely every non-success status.

Slow calls can exhaust resources even when they eventually succeed. A timeout or latency-threshold policy may be needed alongside error counts. Conversely, one isolated failure on a low-volume service can produce a misleading percentage. Set minimum samples and observation windows appropriate to actual traffic, and record the reason for state changes.

Choose scope deliberately: endpoint, operation, tenant, or dependency pool. A global breaker for unrelated operations can amplify one bad path into a total outage. An extremely narrow breaker can fail to protect a shared exhausted resource. Connect the scope to the capacity or failure boundary it is intended to protect.

## Timeouts and Bulkheads Still Matter

A breaker needs completed observations to update its evidence. Calls already in flight can keep consuming resources after it opens. Bound connect, read, and total useful deadlines, and propagate cancellation where safe. The [gRPC chapter](/docs/software-system-design/grpc) explains why a fresh per-hop timeout cannot preserve an end-to-end budget.

A **bulkhead** limits the resources one dependency or workload can consume. Separate concurrency pools can prevent a slow optional service from exhausting every worker needed for essential operations. A breaker can deny future calls after failures, while a bulkhead protects current occupancy. Neither should be treated as an alias for the other.

Rate limiting controls arrivals, and a queue can defer work when deadlines allow. Combining these controls requires understanding their order. An unbounded queue before an open breaker can retain useless requests, while a retry loop outside it can repeatedly hammer local rejection and inflate apparent demand. Count logical actions separately from attempts and denials.

## Fallbacks Must Preserve the Product Contract

A cached public catalogue description may be a valid degraded response under a stated freshness bound. Inventing an authorization success or a payment confirmation is not. Define what information a fallback proves, how old it can be, and which actions must fail closed or remain unresolved. A lower error chart is not a reason to hide incorrect outcomes.

A fallback can have its own scarce dependencies. Redirecting all failed traffic to a smaller standby or database can overload it and extend the incident. Test degraded-path capacity and avoid making a rarely used alternative more complex than the primary. The [capacity model](/docs/software-system-design/capacity-estimation) should include the promised failure state.

For writes, an unknown outcome remains unknown after the breaker opens. The first attempt may have committed before timing out. A local fallback must not issue a conflicting new effect without idempotency or reconciliation. Opening the breaker stops additional attempts; it does not roll back or classify earlier ones automatically.

<GoDeeper title="Go deeper: per-instance breakers do not impose one fleet-wide probe limit">
If a hundred instances each permit one half-open probe, the dependency can receive a hundred probes together. New instances may also start without failure history. A local breaker can still be valuable, but its aggregate behavior must fit recovery capacity. Jittered cooldowns, admission budgets, or supported coordinated controls can reduce synchronized recovery load; a label saying one probe is incomplete without its scope.
</GoDeeper>

## Exercise the Recovery State Machine

Use a disposable dependency that can return controlled success, failure, and delay. A bounded `curl -i --max-time 1 http://127.0.0.1:8080/dependency` can observe one direct attempt, but does not test a breaker unless the application path actually includes it. Instrument attempted dependency calls and local denials so the test can distinguish them.

Drive five qualifying failures, send ten requests during open state, and assert no protected dependency calls occur in that interval. Advance the test clock through the cooldown, release one probe, and attempt concurrent requests to verify the cap. Then fail the probe and confirm reopening; repeat with success and verify the documented transition to normal admission.

<RunnableCode code={`def admitted(state, arrivals):
    if state == "open":
        return 0
    if state == "half-open":
        return min(1, arrivals)
    return arrivals
for state in ("closed", "open", "half-open"):
    calls = admitted(state, 10)
    print("State:", state, "dependency calls:", calls, "locally denied:", 10-calls)
assert admitted("half-open", 10) == 1
# Try it: remove the half-open cap; recovery can send the whole burst to a fragile dependency.
`} />

This function models an atomic admission decision. In a real asynchronous implementation, reserve probe capacity before sending, and release or transition it under every completion and cancellation path. An exception between checking state and marking a probe active can defeat the cap. Keep the policy testable without waiting thirty real seconds in every test.

## Observe Recovery Without Masking Incidents

Record state changes, their reasons, qualifying sample counts, open duration, attempted calls, denied calls, probe outcomes, and end-user success. A breaker that remains permanently open can make dependency traffic look quiet while users continue to fail. An alert should reflect the product's degraded promise and recovery progress, not only whether the breaker process is healthy.

Tune from measured failure behavior. Too short a cooldown can produce repeated overload; too long can delay useful recovery. A threshold of five failures is our teaching choice, not a universal safe setting. Evaluate low-volume and high-volume paths separately, and preserve configuration history so an incident review can explain the observed state transitions.

Test failure classification with the same dependency endpoint returning three deliberately different outcomes: invalid business input, a slow successful response, and an unavailable response. The expected contribution to breaker evidence should follow the chosen operation policy. A test that treats every non-200 response as identical can pass while denying valid traffic because one caller repeatedly sends bad input.

For half-open recovery, release several concurrent callers at the cooldown boundary and count actual dependency attempts. Exactly one should acquire the illustrative probe slot; the others need a bounded local outcome. Then cancel the probe before its response and verify the implementation releases or transitions ownership safely. Repeat after an instance restart to measure the aggregate recovery load from fresh breaker state. These checks turn a three-state diagram into a concurrency contract rather than a collection of unsynchronized booleans.

A state transition should carry a reason and the observation window that produced it. During an incident, operators need to distinguish a breaker opened by recent dependency failures from one still open because no eligible probe has completed. That distinction changes whether the next action is dependency repair, probe investigation, or configuration correction.

A successful probe should restore traffic gradually enough that queued demand cannot immediately overwhelm the recovering dependency.

## Measure the Dependency at the Boundary the Breaker Controls

A breaker protecting a payment provider should count outcomes from that provider call, not every error returned by the enclosing endpoint. A malformed customer request may fail before any dependency call occurs. Counting it as provider failure can open the breaker even when the provider is healthy. Similarly, a local rejection caused by an already open breaker is not another failed provider attempt. Define the observed population and classify errors according to the dependency contract. Some application responses are expected business refusals rather than infrastructure failures.

The state machine also has a scope. A breaker stored in each application process can protect that process from repeatedly waiting on a failed dependency, but ten instances can each permit their own half-open probe. The fleet therefore permits more than one probe even if each local implementation is correct. A shared breaker can coordinate a broader limit, at the cost of another dependency and synchronization path. Choose the scope according to provider capacity and the desired recovery behavior. The example's one probe describes one breaker instance, not an unlimited deployment's total traffic.

Recovery needs enough evidence without recreating the outage. A single successful response may show that one request completed, while the dependency remains unable to handle normal load. Combine bounded probes with the implementation's supported recovery thresholds and a gradual return of useful traffic where required. Keep timeouts and concurrency limits active when the breaker closes. Otherwise queued demand can overwhelm the dependency immediately and cause repeated opening. During testing, let the provider recover only partially: make a few requests fast while others still time out. Observe admitted work, rejected work, connection occupancy, and state transitions. Also verify the fallback's meaning. Returning a cached recommendation may be acceptable; returning a fabricated payment success is not. A breaker chooses whether to attempt work. It cannot manufacture the missing business outcome.

## Failure Modes and Better Choices

All error codes trip one global breaker. Separate client/business outcomes from dependency health and choose an appropriate scope. Every instance probes simultaneously. Bound fleet recovery demand as well as local probes. A fallback returns stale permission data as current. Preserve the security and freshness contract instead of hiding failure.

The breaker opens but in-flight calls exhaust the pool. Add deadlines, cancellation, and bulkheads. Local rejection is retried at several layers. Keep one bounded retry owner and a shared deadline. The breaker closes after one tiny probe, then full load fails again. Test a recovery ramp appropriate to the dependency's actual capacity.

## When Not to Add a Breaker

| Situation | Better first control |
| --- | --- |
| Calls have no deadlines or occupancy limits | Add those resource boundaries |
| Failure is a permanent invalid request | Correct input rather than probe recovery |
| The fallback cannot preserve required meaning | Return an honest unavailable or unresolved outcome |
| A tiny local operation has no remote failure boundary | Keep the simpler code path |

## Remember

| State or control | Responsibility |
| --- | --- |
| Closed | Admit and collect relevant evidence |
| Open | Deny protected attempts under policy |
| Half-open | Probe with explicit concurrency scope |
| Timeout/bulkhead | Bound existing occupancy and wait |
| Fallback | Preserve a defined degraded result, not invent success |
