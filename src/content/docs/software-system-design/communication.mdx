# Communication and Delivery Guarantees

<ELI5>
Sending a parcel and receiving its delivery receipt are different events. If the receipt disappears, the sender cannot tell whether the parcel arrived. Sending another parcel may create a duplicate. Reliable software therefore needs both a transport plan and a rule for recognizing work already done.
</ELI5>

Our illustrative worker receives event `e17`, commits its business effect, and crashes before the broker receives acknowledgment. The broker redelivers `e17`. A correct design must turn two deliveries into one durable effect without discarding genuinely new work. The misconception is that a queue's delivery label can guarantee every downstream business action happens exactly once.

The [existing API and protocol chapter](/docs/cs-fundamentals/apis-http-and-protocols) explains HTTP methods, polling, webhooks, SSE, and WebSockets. We reuse those mechanics here and focus on choosing a contract, propagating deadlines, and defining where durability begins and ends.

## Request Protocols Express Different Contracts

**REST** models an interface around resources and representations. Standard HTTP methods, status codes, caching, and conditional requests make public interfaces accessible to many clients. Resource naming alone does not make an API safe: authorization, pagination, schema evolution, and idempotency still need explicit semantics.

**gRPC** describes remote procedures through an interface definition, commonly Protocol Buffers, and generates client and server bindings. It supports unary and streaming calls and makes typed internal contracts convenient. Code generation creates compatibility obligations: removing fields or reusing field numbers can break old clients. A typed stub still performs a fallible network operation, so every call needs a deadline and error handling.

**GraphQL** lets a client select fields through a schema and resolver graph. It can reduce over-fetching for clients with different views. It can also turn one client operation into hundreds of backend calls if nested resolvers perform one query per item. Batch compatible reads, cap query cost and depth, enforce field-level authorization, and inspect the actual backend fan-out.

Choose based on the caller and workload. A public link-creation API benefits from HTTP tooling and a small stable resource contract. An internal service mesh with controlled clients may benefit from generated RPC contracts. A product with varied relational client views may justify GraphQL, but a single point lookup does not need a query language merely to return two fields.

## Streaming Connections Do Not Replace Durable History

**Server-sent events**, or SSE, carry server-to-client events over an HTTP response. They fit status updates and feeds where the client primarily receives. **WebSockets** provide bidirectional messaging after connection establishment, fitting chat and interactive collaboration. Neither establishes what happened while the client was offline.

For reconnecting clients, include an event cursor or sequence number and define replay retention. If the requested cursor is older than retained history, return a clear resynchronization requirement. A “connected” indicator does not prove the client has every event, and a TCP acknowledgment does not prove the user read a chat message.

Heartbeat intervals, proxy idle timeouts, and backpressure are part of the contract. A slow client must not force the server to retain an unbounded output buffer. Bound buffers, disconnect or shed with a resumable cursor where possible, and observe connection count separately from event throughput.

An SSE response has a concrete wire form. The server uses `Content-Type: text/event-stream`; each event ends with a blank line. A client can present `Last-Event-ID` on reconnect, but the application must actually retain and replay the corresponding history.

```text
id: 417
event: job-state
data: {"job_id":"j9","state":"finished"}

```

Do not put secret authorization tokens into replayable event payloads merely because the connection was authenticated. Recheck subscription permissions and terminate streams when access is revoked. Public browser caches and intermediary buffering also need deliberate configuration for the chosen transport.

## Queues Distribute Work; Logs Preserve Replayable Sequences

A **work queue** normally assigns a job to one competing worker, tracks acknowledgments, and makes failed work available again. A **publish/subscribe** system gives each subscription its own view of events. A **retained event log** preserves ordered records for consumers to replay by position. Products can support more than one pattern; specify behavior rather than inferring it from a product name.

<PubSubVsPointToPointDiagram />

Apache Kafka partitions a topic into ordered logs. A consumer group assigns each partition to a consumer at a time under the group's protocol, while different groups independently consume the topic. Ordering is per partition, not global across a topic. Key related events consistently when their order matters, and account for a hot key concentrating work on one partition.

With an illustrative twelve partitions and twenty workers in one group, no more than twelve workers can actively own partitions at a time in the usual partition-assignment model. More workers do not split a single partition's ordered processing automatically. Increasing partitions may change key placement, so consumers need a deliberate migration and ordering plan.

A queue or log absorbs temporary mismatch, not infinite overload. At 1,200 events/s arriving and 1,000 events/s consumed for five minutes, backlog grows by 60,000 events. If consumers later reach 1,500/s, the spare 300/s takes 200 seconds to drain it. Monitor oldest-event age and lag together; a modest count can still represent unacceptable delay for sparse high-priority events.

## Acknowledgment Boundaries Define Delivery Semantics

**At-most-once** delivery permits loss while avoiding redelivery within the stated system boundary. A consumer that advances its position before performing work can crash and lose the work. **At-least-once** delivery retries unacknowledged work, which permits duplicates. It is often the right starting point for durable jobs if the consumer can handle repetition.

**Exactly-once** must name a boundary. Kafka transactions can atomically coordinate consumed offsets and produced records inside supported Kafka workflows. They do not automatically make an external email provider or arbitrary database write part of that transaction. External effects need an idempotent destination, a transactionally coordinated state change, or a reconciliation design.

## Idempotency Requires a Durable Identity

An **idempotent operation** has the same intended durable effect when repeated with the same operation identity. A payment request should include an idempotency key scoped to the customer and operation type. Store a request fingerprint, execution status, and result. A repeated key with a different amount must conflict instead of silently returning an unrelated success.

In a database consumer, insert the event identity under a unique constraint and update business state in the same transaction. If the insert conflicts, load the previous outcome rather than repeat the effect. Retaining deduplication records for less time than messages can be replayed reopens the duplication window, so retention policies must agree.

<RunnableCode code={`import sqlite3
conn = sqlite3.connect(":memory:")
conn.executescript("CREATE TABLE seen(id TEXT PRIMARY KEY); CREATE TABLE total(n INTEGER); INSERT INTO total VALUES(0);")
for event in ["e17", "e17", "e18"]:
    with conn:
        inserted = conn.execute("INSERT OR IGNORE INTO seen VALUES(?)", (event,)).rowcount
        if inserted:
            conn.execute("UPDATE total SET n = n + 1")
    print(event, "durable effects:", conn.execute("SELECT n FROM total").fetchone()[0])
assert conn.execute("SELECT n FROM total").fetchone()[0] == 2
# Try it: add another e18; the total remains two because identity is durable.
`} />

This example uses one local transaction and a counter to make the boundary visible. It does not send email or charge a card. For an external provider, pass a stable provider idempotency key when supported and reconcile ambiguous outcomes. A database row marked “sent” before sending can lose the email; marking it afterward can resend after a crash.

<GoDeeper title="Go deeper: bounded retries and poison messages">
Retry transient failures with a capped exponential delay and jitter, but keep an overall deadline or retry horizon. A deterministic schema error will not improve with ten thousand retries. Move exhausted work to a quarantined queue with the original identity, failure reason, and replay procedure. Quarantine is an operational state, not permission to forget the user's requested action.
</GoDeeper>

## Evolution and Backpressure Are Part of the Interface

Events should include a stable identity, occurrence time, entity key, and schema version where needed. Prefer compatible additive changes, and preserve the meaning of existing fields. A consumer replaying old records must not depend on a producer deployment that no longer exists. Test old payloads against new consumers and new optional fields against old consumers.

Backpressure means a downstream limit changes upstream admission or production. A bounded worker queue can return a retryable rejection; a stream consumer can pause fetching; a gateway can reject expensive requests before allocating large buffers. Simply accumulating a bigger queue postpones the failure and increases recovery time.

Avoid encoding a distributed transaction as a synchronous call chain with no timeout budget. If a gateway has a 300 ms deadline, three services cannot each independently spend 300 ms retrying the next hop. Propagate the remaining budget, stop work when cancellation is safe, and preserve durable operation identity when the response may be lost.

## Common Problems and Fixes

Duplicate effects require atomic deduplication, not a process-local set. Out-of-order events require per-entity versions or ordered partition ownership, not wall-clock sorting alone. Stuck queues need oldest-event alerts and poison-message handling. Reconnect gaps need retained cursors and resynchronization, not just a new socket.

A schema that “works with today's producer” can still fail during replay. Retain representative historical fixtures and exercise the replay path before changing payload interpretation. Event history is an interface to past software, and consumers must account for it.

## When Not to Introduce Messaging

| Situation | Better choice |
| --- | --- |
| Caller needs one immediate authoritative result | A bounded synchronous request |
| One local database transaction owns all changes | Commit the transaction directly |
| No replay or independent consumers are required | A simple durable work queue |
| Client receives rare updates | Polling with validators may suffice |

## Remember

| Boundary | Question to answer |
| --- | --- |
| RPC | Which deadline and compatibility rules apply? |
| Stream | How does a disconnected client recover? |
| Queue | When is work acknowledged and redelivered? |
| Log | Which key defines order and replay? |
| Effect | Where are identity and state committed together? |
