# Communication and Delivery Guarantees

<ELI5>A request, a live connection, and a durable message make different promises. Choose what must survive a disconnect and which effect a retry may repeat. These chapters trace one boundary at a time before combining them in a service.</ELI5>

## Why it exists

Clients, services, and workers use several communication shapes, each with a different completion boundary. A response can be lost after an effect commits; a live connection can drop before a client receives an event; a durable message can be redelivered. Choose the mechanism from what must survive and what may repeat.

## Common mistakes

| Mistake | Why it happens | Fix |
| :--- | :--- | :--- |
| Treat every successful send as completed work | The acknowledgement may cover only transport or broker receipt | Name the commit boundary |
| Retry after timeout with a new identity | The first effect may already have committed | Preserve operation identity and reconcile |
| Use a live connection as durable history | Disconnect can lose an unretained event | Persist events or provide a replay cursor |

## When not to use it

| Situation | Better choice |
| :--- | :--- |
| A synchronous local call fits the action | Keep the simpler boundary |
| No durable obligation exists after disconnect | Do not introduce a broker |
