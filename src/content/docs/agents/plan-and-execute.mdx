# Plan-and-Execute

[Agent Architectures](/docs/agents/agent-architectures#react-reasoning-acting) covers [ReAct](/docs/agents/agent-architectures#react-reasoning-acting) — reason, act, observe, one step at a time. Plan-and-execute inverts the order: think through the whole task *before* acting on any of it, then execute the resulting plan with far less per-step reasoning. This page covers the three components and the loop that connects them, runs that loop (and asks you to write it), weighs it against ReAct in both directions, shows how plans become graphs that run in parallel, and describes how planning actually shows up in agents in 2026, where it is more often a to-do list the agent keeps than a separate planner.

<ELI5>

Think of the difference between planning a road trip turn-by-turn as you drive versus mapping the whole route before leaving the driveway. ReAct is the first: figure out the next move, do it, see what happened, figure out the next move again — useful when the road might be closed and you won't know until you get there. Plan-and-execute is the second: work out the whole route up front, then just follow it — much less thinking per mile, as long as the roads are actually open the way you expected. The "replanner" is what happens when you hit a detour anyway: it doesn't throw out the whole trip, it just re-routes from where you actually are.

</ELI5>

## 1. The Architecture

Three real components, matching how [LangChain describes the pattern](https://www.langchain.com/blog/planning-agents), which traces back to earlier work like [Plan-and-Solve prompting](https://arxiv.org/abs/2305.04091) and BabyAGI:

- **Planner** — one LLM call that reasons about the entire task and produces a full multi-step plan upfront, not one step at a time.
- **Executor** — runs each step in the plan. Each step is "the user's query and a step in the plan," invoking whatever tools that step needs — a much smaller prompt than re-reasoning about the whole task, and cheap enough to hand off to a smaller model.
- **Replanner** — after execution, decides whether to finish with a response or generate a follow-up plan, based on what actually happened during execution (not just what was planned).

### Run the Control Loop For Real

A real planner/replanner is an LLM call — not something to fake in a browser sandbox. What *is* real and runnable here is the **orchestration loop itself**: given any planner's output and any replanner's decision, exactly how does the loop advance, splice in a fix, and keep going? Below, `execute_step` and `replan` are deterministic stand-ins (so the whole trace is reproducible) for what would otherwise be tool calls and an LLM call — but `run_plan`, the actual control flow being demonstrated, is the real thing, unsimplified:

    if "old-blog.example" in original_plan[failed_index]:
        return ["fetch https://web.archive.org/web/2023/old-blog.example/post-42"]
    return []  # no fix available -> give up on this step

def run_plan(plan, execute_step, replan):
    """The real orchestration loop: execute each step in order; on
    failure, ask the replanner for replacement step(s), splice them in
    right after the failed step, and keep going."""
    steps = list(plan)
    results = []
    i = 0
    while i < len(steps):
        step = steps[i]
        outcome = execute_step(step)
        results.append((step, outcome["ok"]))
        if not outcome["ok"]:
            steps[i + 1:i + 1] = replan(plan, i, outcome)
        i += 1
    return results

## 2. Why It's Often More Efficient Than ReAct

LangChain's own framing of the tradeoff names three real advantages of separating planning from execution:

- **Speed** — no LLM call is needed after every single tool invocation; a step that doesn't need re-reasoning just runs.
- **Cost** — "smaller, domain-specific models" can execute individual steps, reserving the larger (and more expensive) model specifically for the planning call that needs the most reasoning.
- **Quality** — forcing one call to reason through the *entire* problem space upfront, chain-of-thought style, produces more coherent multi-step plans than reasoning about each step in isolation without seeing the whole shape of the task first.

## 3. Limitations: Where It Loses to ReAct

The tradeoff runs the other way for tasks that genuinely need per-step adaptation: a plan committed to upfront is exactly the wrong structure when each step's *result* changes what the next step should even be, not just whether it succeeded. ReAct's interleaved reason-act-observe cycle handles that naturally; plan-and-execute has to detour through the replanner every time, which is slower than never having committed to a rigid plan in the first place.

The basic version also has a real, named limitation: it's "still restricted by serial tool calling" and "doesn't support variable assignment" between steps — later frameworks (LLMCompiler and similar DAG-based approaches) address this by letting independent steps run in parallel and by passing structured values between steps instead of only natural-language results, but that's beyond what the basic planner/executor/replanner pattern itself provides.

<GoDeeper title="Go deeper: serial tool calling is exactly the fake-edge problem, named">

[Loops and Graphs' real-vs-fake-edge test](/docs/agents/loops-and-graphs#real-edges-vs-fake-edges) applies directly to this limitation, not just by analogy. A plan with 5 steps, executed serially, has 4 edges between them by default — but the real-vs-fake test asks: can you name the variable crossing each one? If step 3 doesn't actually consume anything step 2 produced, that edge is fake — an artificial wait imposed by writing the plan as a numbered list. The basic planner/executor/replanner pattern executes every plan as if all its edges were real, because a flat step list has no way to *represent* the difference between "step 3 needs step 2's output" and "step 3 just happens to be listed after step 2." LLMCompiler's fix is exactly what the loops-and-graphs framing predicts: represent the plan as an actual DAG, not a list, so real edges (data dependencies) stay serial and fake edges (mere ordering) get parallelized — the plan becomes a graph, with the planner's job now including which edges are real.

</GoDeeper>

## 4. Plans as Graphs

The basic pattern runs steps one after another, but many plans don't need to. If step 3 doesn't use anything step 2 produced, the order between them is an accident of writing the plan as a list. **LLMCompiler** (Kim et al., 2023) has the planner output a directed acyclic graph instead: each step lists the earlier steps whose outputs it needs, with placeholders for those outputs, and a scheduler runs every step whose inputs are ready in parallel. The authors reported both lower latency and lower cost than ReAct on tasks with independent sub-steps. The same idea underlies parallel tool calling, now supported natively by most model APIs: the model can request several independent tool calls in one turn.

## 5. How Agents Plan Today

Separate planner and executor models are less common in 2026 than the pattern's prominence suggests, for two reasons.

- **Reasoning models plan internally.** A model trained to think before answering already works out a plan in its reasoning, then acts. The explicit planning call is folded into the model.
- **Plans became a tool.** Coding agents such as Claude Code keep a to-do list as a tool the agent itself writes and updates: it lists the steps at the start, marks them done as it goes, and revises the list when something unexpected happens. That's plan-and-execute with the planner, executor and replanner all being one agent, and the plan kept visible in the context, where it also helps the agent stay on track across a long session ([Context Engineering](/docs/agents/context-engineering)).

The explicit pattern still earns its place when the executor should be a cheaper model than the planner, when the plan must be shown to a person for approval before anything runs, or when steps should run in parallel as a graph.

## 6. When to Reach for It

Predictable-structure tasks — the ones where you could sketch the steps yourself before starting — are the actual fit: "search three specific sources and synthesize a comparison" has a shape you already know; "debug this failing test" doesn't, since what to do next depends entirely on what the previous step revealed. The general rule from [Agent Architectures](/docs/agents/agent-architectures#react-reasoning-acting) still applies: reach for structure once managing a plain loop by hand gets error-prone, not by default.

## 7. When *Not* to Use Plan-and-Execute

| Situation | Better choice |
|---|---|
| Each step's result changes what the next step should be (debugging, exploration) | ReAct, which re-decides after every observation |
| Short tasks of two or three steps | A single agent loop; a planning call adds latency for nothing |
| Independent steps executed one at a time | A DAG planner or parallel tool calls |
| A capable reasoning model running a single agent | Let it plan internally, with a to-do list tool for long tasks |
| Plans that must be approved before execution | Plan-and-execute is the right fit: show the plan, then run it |

## Remember

| Idea | In one line |
|---|---|
| Pattern | Plan the whole task first, then execute the steps, replanning on surprises |
| Components | Planner (one strong call), executor (cheap per step), replanner (on failure or completion) |
| Gains | Fewer model calls, cheaper executors, more coherent plans |
| Losses | Rigid when each result changes the next step; serial by default |
| DAG plans | LLMCompiler runs independent steps in parallel |
| Today | Reasoning models plan internally; agents keep a to-do list as a tool |
