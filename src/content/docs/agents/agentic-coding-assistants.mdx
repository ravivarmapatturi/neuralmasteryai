# Agentic Coding Assistants

[Agent Architectures](/docs/agents/agent-architectures) and [Loops and Graphs](/docs/agents/loops-and-graphs) describe agent loops in general. This page is the specific, named application: tools like Claude Code, Cursor, Windsurf, and Gemini CLI that read a real codebase, edit real files, and run real commands — not a toy example, a tool that operates on the same repository you're actually working in.

These are all real, current, open or hybrid tools, not a hypothetical category: [Claude Code](https://code.claude.com/docs/en/overview) (Anthropic), [Cursor](https://cursor.com) (built on VS Code), [Gemini CLI](https://github.com/google-gemini/gemini-cli) (Google, open source, 100k+ GitHub stars), and Windsurf (Cognition) are all in active daily use, and DeepLearning.AI alone runs on the order of a dozen short courses specifically on this category — spec-driven development, AI code review, and each individual tool.

<ELI5>

Imagine a new colleague fixing a bug in a large codebase they've never seen. They don't read every file first. They run the failing test, search for the function it mentions, open that file, make a change, and run the test again. If it's still failing, they look further. They stop when the test passes.

A coding agent does exactly that, using a few tools: search, read a file, edit a file, run a command. The difference from a chat assistant that suggests code is that it runs the check itself and keeps going until the check passes. Everything below is how that works, and how to make sure "the check passes" really means the code is right.

</ELI5>

## The Core Loop

The loop is the same one [Loops and Graphs](/docs/agents/loops-and-graphs#loop-vs-graph-precisely) describes generically — produce, check, correct, repeat — applied concretely: gather context, decide a plan, take an action, verify the result against something real (a test, a build), and go back for more context if it didn't work.

<AgenticCodingLoopDiagram />

The step through above is a real (if abbreviated) trace: the first fix doesn't actually resolve the failure, so the loop goes back for *more* context rather than trying random variations of the same fix — the same "real pass/fail condition" discipline Loops and Graphs insists a gate needs, applied to a test's exit code instead of a human's approval.

## The Loop, Run

Here is the whole loop in miniature against a real repository on disk with a real test: a discount function that forgets to divide a percentage by 100. The tools are the four every coding agent has (run a command, search, read, edit by exact string replacement), and they really execute; a fixed sequence stands in for the model's choices so the run is reproducible:

```python
import pathlib, subprocess, sys, tempfile, textwrap

# A tiny repository with a bug and a test, like the ones a coding agent works in.
repo = pathlib.Path(tempfile.mkdtemp())
(repo / "prices.py").write_text(textwrap.dedent("""
    def apply_discount(price, percent):
        return price - price * percent
"""))
(repo / "test_prices.py").write_text(textwrap.dedent("""
    import unittest
    from prices import apply_discount
    class TestPrices(unittest.TestCase):
        def test_ten_percent(self):
            self.assertEqual(apply_discount(200, 10), 180)
"""))

# The agent's tools: search, read, edit (exact string replacement), run a command.
def grep(pattern):
    return subprocess.run(["grep", "-rn", pattern, "."], cwd=repo, capture_output=True, text=True).stdout.strip()
def read(path):
    return (repo / path).read_text()
def edit(path, old, new):
    text = read(path)
    if text.count(old) != 1:                      # refuse ambiguous edits, as real edit tools do
        return f"error: '{old}' found {text.count(old)} times"
    (repo / path).write_text(text.replace(old, new)); return "ok"
def run_tests():
    r = subprocess.run([sys.executable, "-m", "unittest", "-q"], cwd=repo, capture_output=True, text=True)
    lines = r.stderr.strip().splitlines()
    detail = next((l for l in lines if l.startswith("AssertionError")), "")
    return r.returncode, (lines[-1] + " " + detail).strip()

# The loop. A stand-in plays the model, choosing each next tool call from what it has seen.
plan = [
    ("run_tests", ()),
    ("grep", ("apply_discount",)),
    ("read", ("prices.py",)),
    ("edit", ("prices.py", "price * percent", "price * percent / 100")),
    ("run_tests", ()),
]
for name, args in plan:
    result = {"grep": grep, "read": read, "edit": edit, "run_tests": run_tests}[name](*args)
    shown = str(result).strip().replace("\n", " | ")
    print(f"{name}{args if args else '()'} -> {shown[:110]}")
    if name == "run_tests" and result[0] == 0:
        print("tests pass: the loop's check is satisfied, so the agent stops")
        break
```

```text
run_tests() -> (1, 'FAILED (failures=1) AssertionError: -1800 != 180')
grep('apply_discount',) -> ./test_prices.py:3:from prices import apply_discount | ./test_prices.py:6:        self.assertEqual(apply_disco
read('prices.py',) -> def apply_discount(price, percent): |     return price - price * percent
edit('prices.py', 'price * percent', 'price * percent / 100') -> ok
run_tests() -> (0, 'OK')
tests pass: the loop's check is satisfied, so the agent stops
```

Every element of the real thing is here. The agent starts from the failing test, not from reading the repository. The test's assertion message (`-1800 != 180`) is the information that points to the bug. The edit tool replaces one exact string and refuses ambiguous matches, which is how real coding agents keep edits precise. And the loop ends on a real check, the test suite's exit code, rather than on the model's opinion that it's done.

## Context Gathering: Search, Not Necessarily an Index

A common assumption is that a coding agent works off a pre-built semantic index of the whole repository, the way a code-search product might. That's not quite how the two most-used tools actually describe their own agent mode: Claude Code's agent [reads files and greps for patterns as it goes](https://code.claude.com/docs/en/overview), and Cursor's Agent similarly "relies on its available tools to search and access codebase information as needed during task execution" rather than a pre-computed index driving the agent loop itself. (Cursor does offer separate codebase indexing for other features; the point here is specifically about what drives the *agent's* moment-to-moment decisions, not every feature the product ships.)

This matters practically: a coding agent's first few tool calls on an unfamiliar task are almost always search — grep for the failing test's name, read the file it exercises, check what calls what — not a single "understood the whole repo" step. Context gathering is itself part of the loop, not a setup phase that happens once before it starts.

## The Tool Palette

Across every major coding agent, the actual tools converge on the same short list: read a file, edit or write a file, run a shell command, and search (grep/glob) across the repository. [Claude Code's tool set](https://code.claude.com/docs/en/overview) and [Cursor's Agent tools](https://cursor.com/docs/agent/overview) both name this same handful, plus MCP as the standard way to extend it — see [MCP Overview](/docs/agents/mcp/overview) for the protocol these tools increasingly share to connect to external systems (Jira, Slack, a design doc) instead of every product inventing its own integration.

## Two Different Safety Models

Giving an agent `bash` access and file-write access is a real risk surface — the same "blast radius" question [Loops and Graphs](/docs/agents/loops-and-graphs#gate-on-reversibility-not-confidence) raises for any gate applies directly here. The two dominant tools answer it two genuinely different ways:

<CodingAgentSafetyModelDiagram />

Neither is strictly safer in the abstract. Gate-before catches a bad action before it happens, at the cost of a pause on every risky step (mitigated by allowlisting known-safe commands, or — per [Claude Code's permission docs](https://code.claude.com/docs/en/permissions) — swapping the human gate for a classifier in "auto" mode, which keeps the gate but changes who evaluates it). Checkpoint-after assumes the action really is cheaply reversible, which holds for a local file edit and stops holding the moment the action leaves the machine — a `git push`, a deploy, an API call with a side effect. That's exactly the reversibility tiering Loops and Graphs describes: reversible-and-contained actions are where "just let it run and allow undo" is a reasonable default; the "hard to reverse" tier needs a real gate regardless of which tool you're using.

## Iterative Self-Correction, Including in Parallel

The verify step in the core loop above is what actually makes an agent's edits trustworthy rather than merely fast: run the test, read the real output, and if it's still red, go back to context-gathering with the new information instead of guessing again blind. [Claude Code documents running multiple agents in parallel](https://code.claude.com/docs/en/overview) on different parts of a task, with a lead agent coordinating and merging results — the macro-orchestration graph from [Loops and Graphs](/docs/agents/loops-and-graphs#which-graph-is-this-micro-or-macro) applied to coding tasks specifically: independent sub-agents each running their own loop, coordinated rather than sharing one context.

## Persistent Project Context

Re-explaining a codebase's conventions every single session doesn't scale. Claude Code's answer is a `CLAUDE.md` file at the project root — read at the start of every session, holding coding standards, architecture decisions, and review checklists — plus an auto-memory system that accumulates learnings across sessions without anyone writing them down by hand. It's the same idea as a graph's "long learning edge" from Loops and Graphs: an accepted result (or a correction) doesn't just fix the current run, it becomes a standing constraint future runs start from.

## From "Vibe Coding" to Spec-Driven Development

"Vibe coding" has a real, specific origin: Andrej Karpathy [coined the term in a February 2025 post](https://x.com/karpathy/status/1886192184808149383), describing his own workflow as "I just see stuff, say stuff, run stuff, and copy-paste stuff, and it mostly works" — no diff review, errors pasted back in until they clear. It's one real point on a spectrum, not the only way to work with these tools, and by 2026 the term itself draws as much pushback as adoption even as the underlying no-review workflow persists under other names.

<OversightSpectrumDiagram />

Spec-driven development is the disciplined middle, not a compromise: write and review the spec or plan first, then let the agent implement against it with less line-by-line scrutiny on the resulting diff. The oversight moves earlier in the loop rather than disappearing — closer to reviewing a PR description before the PR exists than to reviewing every line after the fact.

## Verifying Spec-Driven Work: Beyond Reading the Diff

Spec-driven development answers what the agent should do, but not how you know it actually did that once the diff itself gets less line-by-line scrutiny. A spec is only as good as the mechanism that checks the code actually satisfies it — the same idea [RL Environment & Reward Engineering](/docs/reinforcement-learning/rl-environments-and-reward-engineering#from-learned-reward-models-to-verifiable-rewards) covers for RLVR (a verifier program, not a learned judge, checking AI output against ground truth), applied here to human-agent collaboration instead of RL training.

Four real, current techniques do most of the actual verifying, each catching a different class of mistake, and none substituting for the others:

- **Executable specs as the actual gate.** Acceptance criteria written as tests *before* the agent implements, not after, so "done" has a mechanical definition instead of a subjective one. Writing the test first also forces the spec itself to be concrete enough to check — a spec too vague to turn into a test was probably too vague to hand to an agent in the first place.
- **Property-based / invariant testing.** A fixed example test checks specific inputs; a property-based test (Hypothesis in Python, fast-check in JS) checks a general property instead — round-trip encode/decode, idempotency, no crash on any input — across many generated cases. This matters specifically for AI-generated code because an agent can satisfy three example tests with a solution that's wrong in general; property-based testing is what catches that gap.
- **A second, independent model as critic.** Having a separate agent or model review the first one's output is a real, current practice, distinct from an agent re-reading its own work — a second context with no stake in the first attempt looking correct. The real limit: it only helps for properties the critic can actually check by inspection, so it narrows the diff that still needs a human look, it doesn't replace an executable spec.
- **Type systems and static analysis as the cheap first pass.** A strict type checker and a linter with real rules (not just style) catch a meaningful share of mistakes before any test even runs, deterministically and for close to free — the right first filter, not the last word.

<VerificationLayersDiagram />

None of this eliminates the need for human judgment on *intent* — did the code do the right thing, not just a thing that happens to pass every check written for it. A test suite, a property check, and a critic model can all agree a result is "correct" by their own definitions while still missing that the actual goal was slightly different from what got specified. Spec-driven verification narrows how much of a diff needs that judgment; it doesn't remove the need for it, and no technique above claims otherwise.

## When *Not* to Hand a Task to a Coding Agent

| Situation | Better approach |
|---|---|
| There's no test or check that defines "done" | Write the check first, or keep a person reviewing every change |
| The change touches production systems, data or money directly | Gate those actions behind human approval; let the agent prepare, not execute |
| The task needs a decision only the team can make (architecture, product behaviour) | Decide first, then hand the agent a spec |
| Agent output is merged without reading on code others depend on | Review the diff, or require tests that would catch the failure |
| A large, vague request ("improve the codebase") | Break it into specific tasks with acceptance criteria |

## Remember

| Idea | In one line |
|---|---|
| Loop | Gather context, act, verify against something real, repeat |
| Context | Search as you go (grep, glob, read), not a one-off index of the repo |
| Tools | Read, edit by exact replacement, run commands, search; MCP for the rest |
| Safety | Gate risky actions before, or checkpoint and roll back after; neither covers actions that leave the machine |
| Memory | `CLAUDE.md` or `AGENTS.md` carries conventions across sessions |
| Spec-driven | Review the plan and the acceptance tests first, then let the agent implement |
| Verification | Tests written first, property tests, types and linters, an independent critic |
