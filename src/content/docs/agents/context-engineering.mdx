# Context Engineering

[Agent Fundamentals](/docs/agents/agent-fundamentals#agent-memory) ended with a problem it didn't solve: a model's only working memory is its context window, which is finite, while useful agent tasks touch far more information than fits. **Context engineering** is the discipline of deciding, at every step, what that window should contain. Anthropic defines it as the set of strategies for curating and maintaining the optimal set of tokens during inference, including everything that lands in the context besides the prompt. This page explains why the window degrades as it fills, what an agent's context is actually made of and what each part costs, the four strategies for managing it, the specific techniques behind each (compaction, memory files, just-in-time retrieval, sub-agents), **Agent Skills**, the standard way to give an agent many procedures without loading them all, measured below, and how to keep the context friendly to the provider's cache.

<ELI5>

Imagine a desk where you do all your work, and it's the only place you can read anything. A small desk with exactly the papers you need lets you work fast. A desk buried under every document you've ever touched makes you slow and error-prone: the one page that matters is somewhere in the pile.

Context engineering is keeping the AI's desk tidy. Put the task and the important notes on top. File finished work away in a drawer and keep a one-line note saying where it is. Keep the instruction manuals on a shelf and take one down only when you need it. Send an assistant off to read a long report and bring back a summary instead of piling the whole report on the desk.

Everything below is those habits made exact.

</ELI5>

## 1. Why a Fuller Context Is a Worse Context

Context windows grew from 4,000 tokens to hundreds of thousands, and in some models over a million. It's tempting to treat that as solving the problem: just include everything. It doesn't, for two reasons.

**Context rot.** As the number of tokens grows, a model's ability to find and use any particular piece of information declines. Earlier work showed the **lost in the middle** effect (Liu et al., 2023): facts in the middle of a long prompt are used less reliably than facts at the start or end. Later evaluations (Chroma's 2025 context-rot study among them) found performance falling with context length across many models even on simple retrieval tasks, and falling faster when the context contains distractors: text that looks relevant but isn't. Two mechanisms contribute. Attention spreads each token's focus over every other token, so more tokens means thinner attention; and models see far fewer very long dependencies in training than short ones.

**Cost and speed.** An agent re-sends its whole context on every model call. Input tokens grow with the square of the number of steps ([the Agents overview](/docs/agents/overview) computes it), and every extra token in a long-lived prefix is paid for again on every turn.

So the target isn't "as much as fits". It's the **smallest set of high-signal tokens** that makes the right next step most likely.

## 2. What an Agent's Context Contains

A running agent's context has five kinds of content, each with a different lifetime and a different fix when it grows:

| Part | Typical size | Lifetime | How it grows |
|---|---|---|---|
| System prompt | 1K to 10K tokens | Whole session | Instructions accrete over time |
| Tool definitions | 100 to 500 tokens per tool | Whole session | Every connected tool or MCP server adds its schemas |
| Conversation | Grows with each turn | Session | User messages and the agent's replies |
| Tool calls and results | Often the largest part | Session unless trimmed | File contents, search results, command output |
| Retrieved or remembered material | Varies | Per step | Documents, memory entries, loaded skills |

In practice, **tool results** dominate long sessions: one file read can be 5,000 tokens, one web page 20,000. Tool definitions are the quiet cost: forty tools at 300 tokens each is 12,000 tokens on every single call, whether used or not.

## 3. Four Strategies

LangChain's framing groups the techniques into four strategies. They're a toolbox, not a sequence; most agents use all four.

<ContextEngineeringStrategiesDiagram />

- **Write**: save information *outside* the context so it survives without occupying it: notes files, memory stores, scratchpads.
- **Select**: bring into the context only what the current step needs: retrieval, just-in-time file reads, loading one skill out of many.
- **Compress**: keep the gist of something with fewer tokens: summarizing history, trimming old tool results, returning compact tool outputs.
- **Isolate**: give a sub-task its own context, so its working material never enters the main one: sub-agents, sandboxed code execution.

The next sections are the main techniques under each.

## 4. Compress: Compaction and Trimming

**Trimming** drops content that's no longer needed. The safest target is old tool results: once the agent has read a file and acted on it, the raw content can usually be replaced by a short placeholder ("read `config.py`, 240 lines"), keeping the record that it happened. Some APIs offer this as a built-in context-editing feature that clears stale tool results automatically.

**Compaction** goes further: when the context nears its limit, the agent writes a summary of the work so far (decisions made, current state, open problems, important specific values such as file paths and error messages) and continues from that summary in a fresh context. Coding agents such as Claude Code do it automatically as the window fills.

The craft is in the compaction prompt. Tune it for **recall first**: make sure everything that might matter later survives, especially specific values, unresolved bugs and the reasons behind decisions. Only then tighten it for **precision**, cutting redundant tool output and dead ends. Failing the other way is worse, because a summary that silently dropped one critical detail produces an agent that just gets quietly worse three steps later, with no error to point at.

## 5. Write and Select: Memory, Notes and Just-in-Time Retrieval

**Structured notes.** An agent working on a long task keeps a file outside the context, such as a to-do list, a progress log, or a `NOTES.md`, and writes to it as it goes. After a compaction or in a new session, it reads the file back. Anthropic described an agent playing Pokémon for thousands of steps that stayed coherent this way, tracking goals and maps in its notes. **Project memory files** such as `CLAUDE.md` or `AGENTS.md` are the same idea set up by people: standing instructions loaded at the start of every session.

**Just-in-time retrieval.** Instead of loading everything that might be relevant up front, the agent holds lightweight **references** (file paths, URLs, stored queries) and fetches content only when a step needs it, the way a person uses a file system rather than memorizing it. Coding agents combine both: a memory file is loaded up front, while `grep`, `glob` and file-read tools pull in specific code as needed. The trade-off is speed: each fetch is a tool call and a model round trip, so information needed on nearly every step belongs up front.

**Retrieval for knowledge.** For large document collections, selection is [retrieval-augmented generation](/docs/llms-genai/rag): search, then put the best few passages in context.

## 6. Agent Skills: Many Procedures, Loaded One at a Time

A special case of "select" has become a standard of its own. Agents need *procedures* as well as facts: your release checklist, your report format, the steps before touching the billing database. Putting every procedure in the system prompt makes each one cost tokens on every call; fine-tuning is slow; retrieval may miss the step-by-step guide at the moment it's needed.

**Agent Skills** package each procedure as a folder with a `SKILL.md` file: YAML frontmatter with a `name` and a `description` saying what the skill does and when to use it, followed by Markdown instructions, plus optional `scripts/`, `references/` and `assets/` folders. Anthropic introduced them, published the open specification in December 2025, and donated it to the Agentic AI Foundation on 22 October 2026, alongside MCP. Many agent platforms, including ChatGPT, Cursor, GitHub Copilot and VS Code, load the same format.

The design that makes them cheap is **progressive disclosure**, in three stages:

1. **At startup**, the agent loads only each skill's name and description, roughly 100 tokens per skill.
2. **When a task matches a description**, it loads that skill's full instructions (the specification suggests keeping them under about 5,000 tokens).
3. **Only if needed**, it reads the extra files or runs the scripts.

The model itself does the matching, by reading the descriptions as part of its normal reasoning, so the description must say *when* to use the skill in the words users actually use. Here's the mechanism, with three skills on disk and a tokenizer used to measure each stage:

```python
import pathlib, tempfile, textwrap
import tiktoken, yaml

count = lambda text: len(tiktoken.get_encoding("o200k_base").encode(text))   # an OpenAI tokenizer, as a ruler

# Three skills, each a folder with a SKILL.md: YAML frontmatter (name, description) + Markdown instructions.
SKILLS = {
    "release-notes": ("Writes release notes from the git log since the last tag, grouped into features, "
                      "fixes and breaking changes. Use when the user asks for release notes or a changelog.",
                      "Group commits; one line per change starting with a verb; breaking changes first. " * 60),
    "billing-migration": ("Runs a database migration on the billing tables safely. Use when the user asks "
                          "to change, migrate or alter billing tables.",
                          "Check the backup; run on staging; compare row counts; then production. " * 80),
    "incident-report": ("Drafts a post-incident report from a timeline. Use when the user asks for a "
                        "postmortem or incident write-up.",
                        "Timeline, impact, root cause, contributing factors, action items with owners. " * 70),
}
root = pathlib.Path(tempfile.mkdtemp())
for name, (desc, body) in SKILLS.items():
    (root / name).mkdir()
    (root / name / "SKILL.md").write_text(f"---\nname: {name}\ndescription: {desc}\n---\n\n{textwrap.fill(body, 100)}\n")

def read_skill(path):
    _, front, body = path.read_text().split("---", 2)
    return yaml.safe_load(front), body.strip()

# Stage 1, at startup: only name + description of every skill goes into the system prompt.
index = {meta["name"]: meta["description"] for meta, _ in (read_skill(p) for p in root.glob("*/SKILL.md"))}
startup = "\n".join(f"- {n}: {d}" for n, d in index.items())

# Stage 2, when a task matches: load that one skill's full instructions.
# (A real agent's model makes this choice by reading the descriptions; a keyword match stands in here.)
task = "Please write the changelog for v2.3"
chosen = next(n for n, d in index.items() if "changelog" in d.lower() and "changelog" in task.lower())
loaded = read_skill(root / chosen / "SKILL.md")[1]

everything = "\n\n".join(read_skill(p)[1] for p in root.glob("*/SKILL.md"))
print(f"all instructions always in the prompt:  {count(everything):5d} tokens on every call")
print(f"progressive disclosure, at startup:     {count(startup):5d} tokens (3 descriptions)")
print(f"after choosing '{chosen}':      {count(startup) + count(loaded):5d} tokens")
print(f"with 50 skills like these: {50 * count(everything) // 3:,} tokens always loaded, vs about {50 * count(startup) // 3:,} for the descriptions")
```

```text
all instructions always in the prompt:   3317 tokens on every call
progressive disclosure, at startup:        98 tokens (3 descriptions)
after choosing 'release-notes':       1098 tokens
with 50 skills like these: 55,283 tokens always loaded, vs about 1,633 for the descriptions
```

With three skills, always loading every instruction costs about 3,300 tokens on every call; progressive disclosure costs about 100 until a task needs a skill, and about 1,100 after loading the one it needs. Scaled to 50 skills of this size, it's the difference between some 55,000 tokens on every call and about 1,600.

**Skills and MCP are different layers.** [MCP](/docs/agents/mcp/overview) connects an agent to an external system, a running server exposing tools. A skill is know-how the agent reads and follows itself, often telling it which MCP tools to use, in what order, and what to check in between. Two cautions: a skill's scripts run with the agent's permissions, so read a skill before installing it like any code; and a skill only helps if its description matches how tasks are phrased, which is worth testing with and without the skill. The blog post [Agent Skills, Explained](/blog/agent-skills-explained) goes further.

## 7. Isolate: Sub-Agents and Sandboxes

A **sub-agent** gets a focused task and its own clean context, does the token-heavy work there (reading fifty files, running searches), and returns only a condensed result, often 1,000 to 2,000 tokens, to the parent. The parent's context holds conclusions, not working material. This is the main reason coding agents use sub-agents for broad searches, and the trade-offs of splitting are covered in [Single vs Multi-Agent](/docs/agents/single-vs-multi-agent).

**Code execution** isolates too: instead of loading a 50,000-row table into context, the agent writes code that processes it in a sandbox and returns only the answer. Anthropic described the same idea for MCP: letting agents call tools from code they write, so large intermediate results stay in the execution environment rather than passing through the model's context.

## 8. Keep It Cache-Friendly

Providers cache the processed prefix of a prompt and bill repeated prefixes at a fraction of the normal price, often a tenth. An agent's context is almost all repeated prefix, so caching decides much of its cost, and context engineering should preserve it:

- **Stable first, changing last.** System prompt, then tool definitions, then the conversation. Anything that varies per call, such as the current date or a timestamp, goes at the end, not the start.
- **Append, don't rewrite.** Editing an early message invalidates the cache for everything after it. Compaction necessarily rewrites history, which is one reason to compact rarely and decisively rather than trimming a little on every turn.
- **Keep tool lists stable.** Adding or reordering tools mid-session invalidates the cached prefix; MCP's current specification asks servers to return tools in a deterministic order for this reason.

<GoDeeper title="Go deeper: tool definitions are context too">

It's easy to count conversation tokens and forget the tools. Each tool's name, description and JSON schema is sent on every call, and connecting several MCP servers can put dozens of tools, and tens of thousands of tokens, into every request before the user has said anything.

The fixes mirror the rest of this page. **Fewer, broader tools**: one `search_issues(query, state, labels)` instead of five filters. **Tool search**: give the agent a tool for finding tools, and load a tool's full definition only once the agent has decided it needs it, which is progressive disclosure applied to tools. **Skills over tools for procedures**: a procedure written as a skill costs about 100 tokens until it's used, where the same guidance in tool descriptions costs its full length every time. And **compact results**: return the fields the next step needs, paginate, and say what was truncated.

</GoDeeper>

## 9. When *Not* to Over-Engineer Context

| Situation | Better choice |
|---|---|
| Short tasks that fit easily in the window | Plain context; compaction and sub-agents add complexity for nothing |
| Information needed on almost every step | Keep it in the system prompt or a memory file, not fetched just in time |
| Aggressive compaction on tasks full of exact values | Recall-first summaries, or keep raw tool results and trim less |
| A handful of procedures | A clear system prompt; skills pay off as the count grows |
| Editing early history to save tokens | Append-only history and occasional decisive compaction, to keep the cache |
| Skills from unknown sources | Read and test them first; they run code with the agent's permissions |

## Remember

| Idea | In one line |
|---|---|
| Goal | The smallest set of high-signal tokens that makes the right next step likely |
| Context rot | Recall degrades as context grows, faster with distractors |
| Anatomy | System prompt, tools, conversation, tool results, retrieved material; tool results dominate |
| Four strategies | Write (outside), select (just what's needed), compress (summarize, trim), isolate (sub-agents) |
| Compaction | Summarize and restart; tune the prompt for recall before precision |
| Notes and memory files | Persist what matters outside the window; read it back after compaction |
| Agent Skills | `SKILL.md` folders; about 100 tokens each until needed; the description decides activation |
| Skills vs MCP | Skills teach procedures; MCP connects systems |
| Caching | Stable prefix first, append-only history, stable tool lists |
