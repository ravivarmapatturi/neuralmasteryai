# Reflection and Self-Critique, In Full Depth

[Plan-and-Execute](/docs/agents/plan-and-execute) changes *when* an agent thinks — all upfront, versus per step. Reflection changes what happens *after* a result comes back: does the agent just move on, or does it actually check its own work first? This page covers the Reflexion architecture and its results, runs a reflection loop against real tests, separates reflection from plain verification, and spends time on the most important practical finding: self-critique works when it has an **external signal** to work from (tests, tool errors, a checker), and often doesn't when the model only re-reads its own answer.

<ELI5>

Imagine redoing a homework problem, but before turning it in, you re-read your own work and ask "does this actually answer the question, and where did I probably mess up?" That's reflection: after the agent produces an attempt, a separate step grades it, and if it's wrong, writes down *specifically* what went wrong — not "try again," but "you looked in the wrong drawer, check the desk instead." The agent reads that note before its next attempt. No re-training happens anywhere; the "learning" is just a sentence the agent gets to read next time.

</ELI5>

## 1. The Real Architecture: Reflexion

Shinn et al.'s ["Reflexion: Language Agents with Verbal Reinforcement Learning"](https://arxiv.org/abs/2303.11366) (2023) is the paper this pattern is named after, and it's precise about the mechanism — three distinct models, not one agent grading itself in the same breath it answered:

- **Actor** — generates the actual attempt (an action, an answer, a piece of code), conditioned on the task and — critically — any reflections from *previous* trials.
- **Evaluator** — scores the attempt: exact-match grading for reasoning tasks, heuristics for decision-making tasks, or an LLM-based judgment call, depending on the domain.
- **Self-Reflection** — takes the Evaluator's (often sparse — just pass/fail) signal and the actual trajectory, and generates *specific, actionable* natural-language feedback: not "that was wrong," but what specifically to do differently next time.

The paper calls this **verbal reinforcement learning** deliberately: there's no weight update anywhere in the loop. The "learning" is a piece of text, written to an episodic memory buffer, that the Actor reads before its next attempt.

<GoDeeper title="Go deeper: how does text in a prompt change behavior with no gradient step?">

This isn't a metaphor for reinforcement learning — it's a real substitution in the RL objective. Standard RL updates the *policy's parameters* $\theta$ using a reward signal: $\theta \leftarrow \theta + \alpha \nabla_\theta J(\theta)$, nudging weights in the direction that would have produced more reward. Reflexion replaces the parameter update with a *context* update: instead of changing $\theta$, it appends text $m$ to the prompt, so the effective policy becomes $\pi_\theta(a \mid s, m)$ rather than $\pi_\theta(a \mid s)$ — same frozen weights, different conditioning input. This works specifically because a large enough language model's behavior is highly sensitive to its context (the same mechanism behind [few-shot prompting](/docs/llms-genai/prompt-engineering) and [in-context learning](/docs/llms-genai/prompt-engineering) generally) — reflection is a way of writing that context *adaptively*, based on the model's own most recent failure, rather than a human hand-picking few-shot examples in advance. The tradeoff is exactly what you'd expect from optimizing a prompt instead of a weight: it's cheap and immediate (no training run), but the "learning" only persists as long as $m$ stays in context — nothing is retained once the episode ends and the buffer isn't carried forward.

</GoDeeper>

Step through it: trial 1 fails at "use desklamp 1" because the agent never actually found the lamp first — a genuinely different mistake than the wrong desklamp, which matters because self-reflection has to name what actually went wrong to be useful. The reflection it generates is specific enough to change trial 2's very first action — the agent goes straight to desk 1 instead of wherever it was searching before. That specificity is the whole mechanism: a reflection that just says "try harder" wouldn't have fixed anything.

## 3. The Loop, Run Against Real Tests

The same three roles in code. The Evaluator here is real: it executes the candidate function against unit tests. The Actor and Self-Reflection steps are stand-ins for model calls, with the Actor's second attempt depending on the lesson in its memory, so the mechanism is visible and reproducible:

```python
# A Reflexion-style loop: Actor attempts, Evaluator runs real tests, Self-Reflection writes a lesson
# that the next attempt reads. The tests are real; the Actor and reflector are stand-ins for model calls.
TESTS = [((3,), 6), ((0,), 1), ((5,), 120), ((1,), 1)]           # factorial

ATTEMPTS = {   # what the stand-in Actor writes, depending on which lessons are in its memory
    (): "def solve(n):\n    out = 1\n    for i in range(1, n):\n        out *= i\n    return out",
    ("range(1, n) stops before n: include n itself.",):
        "def solve(n):\n    out = 1\n    for i in range(1, n + 1):\n        out *= i\n    return out",
}

def actor(memory):
    return ATTEMPTS[tuple(memory)]

def evaluator(code):
    namespace = {}
    exec(code, namespace)                                       # run the candidate against real tests
    failures = [(args, want, namespace["solve"](*args)) for args, want in TESTS if namespace["solve"](*args) != want]
    return failures

def self_reflect(code, failures):
    # A real system asks the model: given the code and the failing tests, what specifically went wrong?
    args, want, got = failures[0]
    print(f"   failing: solve{args} = {got}, expected {want}")
    return "range(1, n) stops before n: include n itself."

memory = []
for trial in range(1, 4):
    code = actor(memory)
    failures = evaluator(code)
    print(f"trial {trial}: {len(TESTS) - len(failures)}/{len(TESTS)} tests pass")
    if not failures:
        break
    memory.append(self_reflect(code, failures))
    print(f"   lesson stored: {memory[-1]!r}")
```

```text
trial 1: 2/4 tests pass
   failing: solve(3,) = 2, expected 6
   lesson stored: 'range(1, n) stops before n: include n itself.'
trial 2: 4/4 tests pass
```

Everything useful in the loop comes from the Evaluator's concrete signal: which test failed, with what input, and what came out. The reflection turns that into a specific lesson ("include `n` itself"), and the next attempt fixes exactly that. A reflection written without the failing test, from re-reading the code alone, would have had much less to go on, which is the subject of section 5.

## 4. Not the Same as a Verifier

A plain verifier checks one output and accepts or rejects it — useful, but the lesson dies with that single decision. Reflexion's self-reflection step does something structurally different: it writes a *reusable* lesson into memory that changes the *next* attempt's starting point, not just this one's verdict. In the terms [Loops and Graphs](/docs/agents/loops-and-graphs#two-return-paths-on-rejection) uses for a gate's two return paths, a plain verifier is closer to the **short correction edge** (fixes this run); Reflexion's memory buffer is closer to the **long learning edge** (an accepted-or-corrected result becomes a standing constraint for future runs) — except here it's built from natural language instead of a structured constraint, and it persists across trials of the *same* task rather than across entirely different future tasks.

## 5. Self-Critique Needs Something to Check Against

Reflexion's strongest results came from settings with a real external signal: unit tests for code, success or failure in an environment. That's not a detail. Later work tested what happens without one:

- **Intrinsic self-correction often fails.** Huang et al. (2023), "Large Language Models Cannot Self-Correct Reasoning Yet", asked models to review and revise their own answers on reasoning benchmarks with no external feedback. Accuracy didn't reliably improve and often dropped, as models changed correct answers to incorrect ones. Earlier reported gains had often relied, implicitly, on knowing which answers were wrong.
- **External feedback works.** When the critique can use a compiler, tests, a search result, a calculator or a checker, the model has new information, and revision helps. Coding agents iterate against test output and error messages for exactly this reason.
- **Separate judges help some.** A different model or a differently prompted critic, especially with a rubric, catches more than the same model re-reading its answer, though it shares many blind spots with the generator ([LLM-as-judge](/docs/llms-genai/evaluation-and-serving)).

The practical rule: before adding a reflection step, ask what new information the critic will have that the actor didn't. If the answer is "none", expect little gain for the extra cost.

## 6. Real Numbers, and Real Limitations

The paper's headline result: Reflexion reaches **91% pass@1 on HumanEval**, versus GPT-4's 80% without it — a genuine, cited improvement from the reflect-and-retry loop alone, not a marginal gain.

It's not universal, and the paper says so directly rather than leaving it implied:

- On **WebShop**, Reflexion "is unable to solve tasks that require a significant amount of diversity and exploration" — the pattern helps an agent get *better at the same kind of mistake*, not discover fundamentally different strategies it never considered.
- The system "may still succumb to non-optimal local minima" — a specific, wrong approach can get incrementally refined without ever being abandoned for a better one.
- Some trials produced "unhelpful, unintuitive self-reflections" — the Self-Reflection model is still an LLM call, and it can misdiagnose its own failure just as easily as the Actor can fail in the first place. Nothing here checks the reflection's own accuracy.

That last point is the real, honest failure mode worth naming explicitly: self-critique catches the failures the model *can* recognize as failures. A blind spot in the model's judgment is invisible to a critique step running on the same judgment.

## 7. When *Not* to Add Reflection

| Situation | Better choice |
|---|---|
| No external signal to critique against | A better prompt, or build a check (tests, validation) first |
| Latency-sensitive single answers | Answer once; reflection multiplies calls |
| A deterministic check exists | Run the check in code and feed back its result, rather than asking the model whether it's right |
| The failure is a missing capability, not a fixable mistake | A stronger model or different tools; reflection refines, it doesn't invent new strategies |
| Unbounded retry loops | A fixed trial limit, and escalate to a person when it's reached |

## Remember

| Idea | In one line |
|---|---|
| Reflexion | Actor attempts, Evaluator scores, Self-Reflection writes a lesson the next attempt reads |
| Verbal RL | The "update" is text in the context, not a weight change |
| Measured | 91% pass@1 on HumanEval with tests as the signal, against 80% without |
| External signal | Tests, tool errors and checkers make critique work; re-reading alone often doesn't |
| Verifier vs reflection | A verifier rejects one output; reflection writes a reusable lesson |
| Limits | Local minima, weak exploration, and wrong self-diagnoses |
