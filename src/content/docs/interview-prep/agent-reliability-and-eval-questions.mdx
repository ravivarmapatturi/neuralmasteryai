# Agent Reliability & Evaluation Interview Questions

These 24 questions test the two pillars that turn fragile demo loops into dependable agent systems: failure recovery (retries, timeouts, idempotency, and durable checkpoints) and trajectory-aware evaluation over execution traces. For checkable items, pick or compute your answer first; for debugging and system-design scenarios, lay out your invariants and failure modes before reading the worked explanation.

## Agent Failures: Retries, Timeouts, Idempotency & Checkpoints

<Choice id={"af-transient-vs-permanent-retry-concept"} q={"An agent tool call fails inside an automated workflow. Which failure class should trigger automated exponential backoff with jitter in the harness, rather than immediate failure or feeding the error back to the LLM?"} context={"Your agent calls internal REST APIs, SQL executors, and third-party SaaS endpoints."} sourceRoute={"/docs/software-system-design/retries-and-backoff"} answer={2} options={[{"text": "`400 Bad Request` caused by missing required JSON fields in the tool call.", "why": "Retrying identical malformed arguments fails deterministically every time; return the validation error to the LLM so it can fix its arguments."}, {"text": "`403 Forbidden` because the user lacks permission on the target workspace.", "why": "Permission denials are permanent policy boundaries; retrying wastes quota and never flips authorization."}, {"text": "`429 Too Many Requests`, `503 Service Unavailable`, or a transient TCP connect timeout.", "why": "Transient saturation and network blips resolve cleanly after jittered backoff without bothering the LLM."}, {"text": "A deterministic Python `ZeroDivisionError` inside a local calculation tool.", "why": "Deterministic code or input bugs require the agent to revise its code or inputs, not blind transport retries."}]}>

Separate **transient infrastructure faults** (`429`, `502`/`503`/`504`, socket timeouts) from **permanent or semantic faults** (`400`, `403`, `404`, schema violations). Retrying transient errors silently inside the transport layer with bounded attempts and full jitter shields the LLM context from noisy hiccups and resolves temporary overload without burning extra model turns. Retrying a deterministic `400` or `403` in tight loops wastes attempt budgets, amplifies downstream load, and stalls the user for seconds when the right move is aborting immediately (for `403`) or returning the exact schema hint to the LLM (for `400`). Strict error classification keeps recovery fast while requiring every tool adapter to map vendor errors accurately.

</Choice>

<Calc id={"af-exponential-backoff-deadline-calc"} q={"An HTTP tool wrapper uses a 4.0-second per-attempt timeout and up to 3 total attempts (1 initial call plus 2 retries), with deterministic backoff sleeps of 1.0 s after attempt 1 and 2.0 s after attempt 2 (no sleep after the final failure). If every attempt hangs until its timeout fires, what is the worst-case elapsed time in seconds for that single tool step?"} context={"Ignore minor Python loop overhead and jitter variance; sum full timeout and sleep waits."} sourceRoute={"/docs/software-system-design/retries-and-backoff"} answer={15} tolerance={0.0} unit={"s"}>

Sum all three hanging attempts plus the two inter-attempt sleeps: `(3 × 4.0 s) + 1.0 s + 2.0 s = 12.0 + 3.0 = ` **`15`** seconds. Engineers routinely configure per-attempt timeouts and retry counts independently, forgetting that `3 × 4s + backoff` consumes 15 seconds on a single step—blowing past a 10-second agent turn SLA or holding worker pools hostage. Always pass a shared **step deadline** into the retry loop (`min(attempt_timeout, remaining_deadline)`) and abort retries immediately once remaining time drops below a viable call budget.

</Calc>

<QA id={"af-idempotency-key-scope-concept"} q={"Why must an agent harness bind an idempotency key to the logical step `(run_id, step_seq, tool_name, args_hash)` before network dispatch, rather than generating a fresh UUID inside the HTTP retry helper or reusing one static key per user?"} context={"The agent calls a `create_payout` API over an unstable network where responses occasionally drop after commit."} sourceRoute={"/docs/software-system-design/idempotency"}>

Generating a fresh `uuid4()` inside the low-level HTTP retry helper defeats idempotency completely: if attempt 1 commits the payout and times out before the HTTP response returns, attempt 2 sends a different UUID and creates a **duplicate payout**. Conversely, reusing one static key per user across different turns causes turn 5's legitimate second refund to return turn 2's cached response silently! Binding the key deterministically to `(run_id, step_seq, tool_name, canonical_args_hash)`—and persisting that step intent before calling the network—ensures network retries and worker crash recoveries share the exact same key, while distinct turns generate distinct keys. Step-scoped idempotency guarantees at-most-once side effects on supported APIs at the cost of persisting step metadata before external dispatch.

</QA>

<Choice id={"af-non-deterministic-replay-bug"} q={"A multi-step agent checkpoints after every completed step. After executing `charge_card($50)` on step 4, the worker crashes before persisting step 4's completion marker. On restart from step 3, the supervisor re-invokes the LLM to generate step 4 again; the LLM picks slightly different wording (`memo: \"Order retry\"`), generating a different argument hash, bypassing the idempotency cache, and double-charging the customer. What durable-execution invariant failed?"} context={"Idempotency keys are computed from `hash(run_id, step_seq, args)` and checkpoint writes happen only after the HTTP tool returns."} sourceRoute={"/docs/harness-engineering/state-continuity-and-memory"} answer={0} options={[{"text": "Durable replay must record deterministic tool intents *before* execution and replay logged history rather than re-running a non-deterministic LLM past the boundary.", "why": "Even at temperature 0, re-calling an LLM across batches or changed timestamps can mutate tool arguments and break replay identity."}, {"text": "Idempotency keys should be stored in browser `localStorage`.", "why": "Server-side worker crashes require durable server storage, not client browser storage."}, {"text": "Checkpoints should only run at the end of the entire conversation.", "why": "Coarse checkpoints widen the lost-work window instead of preventing step-4 double execution."}, {"text": "The payment API should accept HTTP GET requests for card charges.", "why": "Mutations must remain non-safe POST operations guarded by durable operation intent."}]}>

Re-invoking an LLM during crash recovery breaks deterministic replay because LLM outputs can vary across batch scheduling or updated timestamps—even changing a harmless `memo` string alters an `args_hash` and turns a retry into a brand-new charge. A durable agent runner must follow a **write-ahead intent log**: (1) persist the exact LLM-selected `(step_seq, tool_name, canonical_args, idempotency_key)` to durable storage *before* dispatching the HTTP call; (2) on restart, replay committed results from the log without calling the LLM; and (3) if step 4 has an uncommitted in-flight intent on disk, re-execute or reconcile using that exact logged `idempotency_key` rather than asking the LLM again. Write-ahead step logging closes the crash-before-ack race completely at the cost of one small DB write per tool step.

</Choice>

<Calc id={"af-retry-amplification-calc"} q={"During a partial database brownout, a three-layer stack runs independent retries: the root supervisor retries a failing sub-agent up to 3 times (4 total tries), the sub-agent's tool client retries a flaky internal service up to 3 times (4 total tries), and that internal service retries its database query up to 2 times (3 total tries). For 1 user request when every call stalls, how many total database attempts can this stack emit?"} context={"Assume all layers retry independently on timeout with no shared retry budget."} sourceRoute={"/docs/software-system-design/retries-and-backoff"} answer={48} tolerance={0.0} unit={"attempts"}>

Nested retries multiply across call hops: `4 supervisor tries × 4 tool-client tries × 3 database tries = ` **`48`** database attempts triggered by a single stalled user request. Across just 500 active users, that 48× multiplier floods a struggling database with 24,000 queries, locking a brief brownout into a prolonged total collapse (**metastable retry storm**). Prevent amplification by retrying **at most at one layer** (typically closest to the immediate transient hop or at the orchestrator with non-retrying inner hops), setting **retry budgets** (capping total retries at ~10% of normal traffic), and propagating remaining request deadlines. Single-layer bounded retries protect recovery headroom at the cost of failing unrecoverable inner calls slightly earlier.

</Calc>

<QA id={"af-idempotency-payload-mismatch-debug"} q={"Your ops agent calls `create_ticket(priority=\"high\")`, gets a schema rejection from a downstream validator, self-corrects to `priority=\"urgent\"`, and accidentally reuses the previous step's `idempotency_key`. The server returns HTTP 200 with the original response (`priority=\"high\"`), leaving the agent convinced its correction succeeded. What two bugs caused this?"} context={"The tool server keys its idempotency table solely on `idempotency_key` without comparing request payload hashes."} sourceRoute={"/docs/software-system-design/idempotency"}>

Two complementary bugs collided: on the **server side**, the idempotency store returned a cached result keyed solely on `idempotency_key` without verifying that the incoming request body matches the original `payload_hash` (it should reject mismatched payloads with `409 Conflict` or `422`); on the **harness side**, the agent incremented a reasoning retry without advancing its `attempt/substep` sequence when generating logically *new* arguments. Anytime an LLM mutates tool arguments to fix a validation error, it is issuing a new logical intent that requires a fresh idempotency key, whereas only identical transport retries keep the original key. Enforcing server-side payload-digest equality and step-revision keys prevents silent stale-cache illusions at the cost of storing a 32-byte payload hash per idempotency record.

</QA>

<Calc id={"af-checkpoint-granularity-calc"} q={"A 50-step autonomous coding workflow runs at 4.0 seconds per step. Saving a durable state checkpoint after every step adds 0.5 seconds overhead per step (25.0 s total across 50 steps). Suppose a worker preemption hits once right after step 25 finishes: without checkpoints, the run restarts from step 0 (re-running 25 steps); with per-step checkpoints, recovery resumes immediately at step 26 with 0 lost steps. How many net seconds does per-step checkpointing save on this preempted run?"} context={"Compare total execution time without checkpoints versus with per-step checkpoints across the single preemption after step 25."} sourceRoute={"/docs/harness-engineering/state-continuity-and-memory"} answer={75} tolerance={0.0} unit={"s"}>

Without checkpoints, restarting after step 25 wastes `25 × 4.0 s = 100.0 s` re-executing completed steps (`200 s` useful + `100 s` wasted = `300 s` total). With per-step checkpoints, lost work is `0 s` and total checkpoint writes across all 50 steps add `50 × 0.5 s = 25.0 s` (`225 s` total), yielding **`75`** net seconds saved (`100 − 25 = 75 s`). Notice the break-even trade-off: if preemption probability is tiny (say 1% of runs) and checkpoint overhead is large (for instance, serializing multi-gigabyte container snapshots instead of lightweight workspace diffs + conversation state), checkpointing every 5–10 steps or before expensive irreversible phases beats per-step snapshots.

</Calc>

<QA id={"af-poison-pill-dlq-debug"} q={"An async agent worker pulls a malformed webhook event containing invalid UTF-8 bytes, crashes with an unhandled `UnicodeDecodeError` before acking the message, and restarts. The queue immediately redelivers the same message to the next pod, and within 5 minutes every worker pod is stuck crash-looping. Diagnose and fix this poison-pill failure."} context={"Queue uses standard at-least-once delivery with infinite immediate redelivery on unacked worker crashes."} sourceRoute={"/docs/mlops/message-queues-and-async-processing"}>

An unguarded fatal payload (**poison pill**) coupled with unbounded immediate redelivery creates an infinite crash-and-redeliver loop that starves every healthy task in the queue. Because the crash fires before `ack()`, the broker keeps re-queuing the exact toxic message to healthy pods one by one until the whole fleet OOMs or enters `CrashLoopBackOff`. Fix this with three controls: (1) track `delivery_count` (`max_receive_count = 3–5`) at the broker and automatically divert exhausted items to a **Dead-Letter Queue (DLQ)** with alert triage; (2) wrap top-level message deserialization in non-fatal schema validation that explicitly `nack(requeue=false)` / dead-letters permanent `DecodeError`s on attempt 1; and (3) apply exponential visibility backoff between legitimate retries. DLQ routing isolates toxic events cleanly at the cost of building replay tooling for dead-lettered items.

</QA>

<QA id={"af-zombie-heartbeat-orphan-tool-debug"} q={"A background agent worker picks up a 10-minute database backfill tool job from a queue configured with a 60-second visibility timeout and no heartbeats. At second 61, the broker marks the task stalled and hands it to Worker B, so two workers run the same non-atomic migration concurrently. How do you stop split-brain execution?"} context={"Backfills vary from 10 seconds to 15 minutes; queue visibility defaults to 60 seconds."} sourceRoute={"/docs/software-system-design/distributed-locks"}>

Fixed short visibility timeouts without lease renewal cause **zombie workers** whenever legitimate long tool runs outlive the lease. At 61 s, Worker A is still alive and mutating rows while Worker B acquires a fresh message delivery and collides on the same target. Resolve split-brain with three layers: (1) run a background **lease heartbeat** inside the worker extending visibility (e.g., every 20 s) only while the process holds its thread/cancellation health; (2) pass a monotonically increasing **fencing token** (`lease_epoch`) into downstream locks/stores so any paused or orphaned Worker A with an older token gets rejected once Worker B acquires token `n+1`; and (3) check cooperative cancellation flags before committing side effects. Heartbeats plus fencing tokens eliminate duplicate long-tool execution at the cost of minor lease-renewal traffic and store-side epoch validation.

</QA>

<QA id={"af-context-bloat-on-retries-concept"} q={"Why does appending full raw stack traces from four failed tool retries directly into an agent's active message history degrade accuracy on step 5, and how should the harness surface retry failures instead?"} context={"Each Python/SQL traceback spans ~1,800 tokens; the agent must pivot to an alternative query strategy."} sourceRoute={"/docs/harness-engineering/verification-loops"}>

Dumping four multi-kilobyte stack traces into active context floods attention with repetitive noise and error priors (**context poisoning**), making the model anchor on failed paths or confuse old tracebacks with current code lines—cutting step-5 recovery accuracy sharply while multiplying input token cost quadratically. Instead of raw trace logs, collapse historical failed retries into a compact **structured diagnostic envelope** (under 150 tokens: `tool_name`, `error_code`, normalized 2-line root cause, `attempt 2/3`), store full logs out-of-band by `artifact_id` if the agent explicitly requests inspection, and prune or replace superseded failed attempts once an attempt succeeds. Compact error envelopes keep reasoning context crisp and cheap while risking loss of obscure tail clues unless full traces remain fetchable on demand.

</QA>

<QA id={"af-checkpoint-schema-evolution-design"} q={"You ship a breaking refactor to your agent workflow—renaming a tool and splitting a single `plan` state node into `draft_plan` and `verify_plan`—while 2,000 long-running agent runs are checkpointed in `AWAITING_APPROVAL`. How do you resume all 2,000 runs cleanly without deserialization crashes?"} context={"Checkpoints stay valid up to 7 days while waiting on human approvals."} sourceRoute={"/docs/harness-engineering/state-continuity-and-memory"}>

Never deserialize live workflow checkpoints blindly into mutated code graphs—treat persisted checkpoints as versioned API contracts. Stamp every snapshot with explicit `graph_version` and `schema_version` fields alongside immutable step history. Route upgrades through two clean mechanisms: (1) **versioned worker deployment (blue-green routing)**, pinning resumed `v1` checkpoints to long-lived `v1` worker replicas while new requests run on `v2`, retiring `v1` workers after the 7-day approval TTL drains; or (2) **explicit lazy state upcasters** (`migrate_v1_to_v2(snapshot)`) that map old `plan` nodes into completed `draft_plan` + pending `verify_plan` states and translate deprecated tool names deterministically, gated by migration tests over real archived checkpoints before deploy. Version pinning and tested upcasters prevent mass deserialization outages at the cost of temporarily carrying two runtime versions or writing migration adapters.

</QA>

<QA id={"af-durable-agent-recovery-design"} q={"Design a durable checkpoint-and-recovery engine for a multi-step enterprise agent executing mixed external APIs—some idempotent (Stripe), some non-idempotent legacy SOAP/SMTP endpoints—in an environment with 30-second spot-instance preemption notices."} context={"Runs span 5–30 minutes; spot nodes can terminate 30 seconds after receiving a shutdown webhook."} sourceRoute={"/docs/agents/react-agent-production"}>

Separate execution into deterministic **checkpointed state transitions** paired with an **outbox / effect classification policy** and graceful preemption draining:

1. **Preemption handler:** On the 30-second termination signal, stop accepting new tasks, allow short in-flight steps to commit or cancel cleanly before shutdown, flush the current write-ahead state + workspace diff to object storage/DB, and release leases immediately so a replacement worker picks up without waiting for timeout expiry.
2. **Effect classification:** Before running a step, persist its `intent_log` entry (`run_id`, `step_seq`, `args_hash`). For idempotent APIs (Stripe), retry cleanly with the stored deterministic key; for non-idempotent legacy APIs (SMTP email, legacy SOAP), mark the step `UNCERTAIN_IF_INTERRUPTED` if preemption hits mid-socket: query a side-channel reconciliation lookup (sent-mail log / SOAP status query) before retrying, or pause for human confirmation rather than risking double customer emails.

Separating idempotent replay from non-idempotent reconciliation protects legacy side effects during spot churn, trading extra reconciliation adapters and occasional operator review for zero silent duplicates.

</QA>

## Agent Evaluation & Traces

<Choice id={"ae-outcome-vs-trajectory-eval-concept"} q={"An agent finishes a customer support task with the exact right final refund amount, yet its execution trace shows it ignored an internal policy cache, queried an admin-only table twice, and retried 11 turns to get there. Why must agent evaluation grade trajectory alongside end-state outcome?"} context={"You are designing an automated CI gate for tool-using customer operations agents."} sourceRoute={"/docs/ai-evaluation/llm-rag-agent-evaluation"} answer={1} options={[{"text": "Outcome checks cannot compare numeric dollar values accurately.", "why": "Exact outcome assertions check final balances and fields accurately; what they miss is how the state was reached."}, {"text": "Outcome-only checks miss security/policy breaches, side-effect pollution, and runaway step costs along the path, while requiring an exact golden sequence is too brittle when multiple valid paths exist.", "why": "Grade end-state invariants together with trajectory policy rules and step/cost budgets rather than exact sequence matching."}, {"text": "Trajectory evaluation eliminates the need to reset databases between test tasks.", "why": "State isolation between trials remains mandatory regardless of whether trajectories are scored."}, {"text": "Grading traces removes non-determinism from temperature 0.7 sampling.", "why": "Trace grading measures behavioral reliability; it does not make sampling deterministic."}]}>

Outcome-only scoring rewards lucky accidents and hides dangerous paths—an agent that probes restricted endpoints or wastes 14 unnecessary tool calls still passes if the final database row matches. Conversely, demanding exact string-match equality against one hardcoded reference tool sequence fails valid alternative plans (for example, looking up customer ID before order date instead of order date before customer ID). Production agent evals pair **end-state assertions** (final DB diff / test exit code) with **trajectory invariant checks** (no forbidden tool arguments, required confirmation gates honored, zero redundant cycle repeats) and **efficiency ceilings** (turn count and token cost). Separating invariant checks from rigid sequence matching catches unsafe behavior without penalizing valid reasoning flexibility.

</Choice>

<Calc id={"ae-pass-hat-k-reliability-calc"} q={"A customer-refund agent succeeds independently on 85% of trials (`p = 0.85`). Enterprise release criteria evaluate `pass^k`, requiring all `k = 4` independent trials on a scenario to pass without failure. What is `pass^4` as a percentage? (One decimal.)"} context={"Assume independent identically distributed runs with no cross-trial memory."} sourceRoute={"/docs/ai-evaluation/llm-rag-agent-evaluation"} answer={52.200625} tolerance={0.01} unit={"%"}>

For all 4 independent trials to succeed, multiply single-trial reliability: `0.85⁴ = 0.52200625 = ` **`52.2%`**. Unlike `pass@4` (`1 − 0.15⁴ = 99.95%`), which measures whether an agent can get lucky once in four tries, `pass^4` measures whether a team can trust the agent repeatedly across four production invocations on the same task shape. Dropping from an encouraging `85%` single-run score to `52.2%` at `k = 4` highlights why customer-facing workflows need strict schema constraints, deterministic validation retries, and conservative autonomy gates before claiming enterprise readiness.

</Calc>

<QA id={"ae-environment-state-grading-concept"} q={"Why do agent benchmarks like tau-bench and SWE-bench grade the final mutated environment state (database diffs or unit-test suites) rather than scoring the agent's final natural-language message against a reference string?"} context={"An airline booking agent replies \"Done! Your flight is moved to Friday\" to a customer request."} sourceRoute={"/docs/ai-evaluation/llm-rag-agent-evaluation"}>

Text similarity or even an LLM judge reading only the assistant's closing message cannot verify whether the agent actually changed reality or hallucinated tool execution. An agent can write a polite, fluent `"Done! Moved to Friday"` while forgetting to pass `confirm=true`, mutating the wrong passenger leg, or misreading a silent API error—and conversely, valid terse responses score poorly against verbose reference strings. Grading the **mutated environment end-state** (comparing live SQLite/Postgres table snapshots, file-system git diffs, or running hidden unit tests inside a fresh sandbox) measures true task accomplishment deterministically. Environment grading eliminates linguistic sycophancy at the cost of building fast sandbox reset snapshots and deterministic world-state assertions per task.

</QA>

<Choice id={"ae-trace-span-schema-concept"} q={"In an OpenTelemetry-instrumented agent runtime, why must LLM generations, tool invocations, and sub-agent calls share a single root `trace_id` with parent-child `span_id` links rather than emitting flat independent HTTP logs?"} context={"One user request fans out across a planner, two parallel retrieval workers, and three external tool servers."} sourceRoute={"/docs/agent-observability/opentelemetry-and-distributed-tracing"} answer={0} options={[{"text": "Parent-child span trees capture causal execution order, exact critical-path timing, and per-branch token accumulation across async workers and retries.", "why": "Without `trace_id` and `parent_span_id`, you cannot reconstruct which sub-agent triggered a failing retry or where 80% of total latency actually sat."}, {"text": "Span trees automatically compress JSON prompt text by 4× in GPU VRAM.", "why": "OpenTelemetry traces record telemetry out-of-band and never alter GPU KV caches."}, {"text": "Flat logs cannot store timestamps in UTC.", "why": "Flat logs hold timestamps cleanly, yet lack parent-child causal pointers across concurrent async branches."}, {"text": "Using `trace_id` bypasses external rate limits on tool servers.", "why": "Trace propagation is strictly observational and never overrides API rate limiters."}]}>

Flat per-service logs break down immediately on multi-turn, parallel agents because concurrent tool calls and nested sub-agents interleave arbitrarily in shared log streams. Propagating a single root `trace_id` and parent-child `span_id` (plus `step_index`, `gen_ai.usage.*`, and `tool.status`) builds a causal **execution DAG** showing exact critical-path wait (parallel vs sequential tool waits), total rolled-up dollar cost per user turn, and the exact upstream span whose bad output poisoned downstream reasoning. Causal span trees make multi-hop agent triage deterministic at the cost of propagating W3C `traceparent` metadata across HTTP, queues, and local subprocess tool boundaries.

</Choice>

<QA id={"ae-mock-vs-live-sandbox-eval"} q={"Compare running agent CI evaluations against deterministic recorded tool stubs (VCR mocks) versus live ephemeral sandboxes (seeded containers and mock servers). When do VCR mocks give dangerous false confidence?"} context={"Your PR gate runs 150 agent scenarios in under 3 minutes; staging integrates real CRM and billing microservices."} sourceRoute={"/docs/mlops/ml-and-llm-testing"}>

Deterministic tool mocks execute in seconds with zero external flakiness, making them ideal for fast PR smoke checks on prompt parsing and known regressions—yet they freeze past API assumptions in place. If the live billing service changes an enum field, adds a stricter pagination cursor, or if the agent explores a slightly different query filter (`status=open` instead of `status=pending`), static recorded mocks either crash on missing cassette keys or replay stale successes that mask broken production integrations. Use **seeded ephemeral sandboxes** (containerized databases + local HTTP tool implementations with reset hooks) for nightly/release gates to catch real stateful mutations, ordering preconditions, and schema drift, while keeping minimal fast mocks for inner-loop PR iteration—balancing fast developer velocity against real end-to-end fidelity.

</QA>

<Calc id={"ae-step-efficiency-cost-calc"} q={"On a 500-task evaluation suite, Agent V1 solves 80% of tasks (400 tasks), averaging $0.06 per successful trajectory and $0.14 per failed trajectory (where the remaining 100 runs exhaust the turn cap). What is the effective cost per resolved task (`total spend ÷ resolved tasks`) in USD? (Three decimals.)"} context={"Include spend from both passing and failing attempts in the numerator."} sourceRoute={"/docs/agent-observability/token-and-cost-attribution"} answer={0.095} tolerance={0.01} unit={"USD"}>

Calculate total suite spend across all 500 tasks:

- **Passing runs:** `400 × $0.06 = $24.00`.
- **Failing runs:** `100 × $0.14 = $14.00`.
- **Total spend:** `$24.00 + $14.00 = $38.00` across `400` resolved tasks.

Effective cost per resolved task is `$38.00 ÷ 400 = ` **`$0.095`** (nearly 60% higher than the naive `$0.06` sticker price of successful trajectories alone!). Evaluating cost per resolved task instead of average cost per call stops teams from shipping an agent that raises pass rate slightly from 80% to 82% while doubling failed-trajectory retry loops and exploding total unit economics.

</Calc>

<Choice id={"ae-trace-root-cause-localization-debug"} q={"Your billing agent fails 32% of multi-step refund tasks. Reading only final outputs makes every failure look like the LLM hallucinated refund amounts—yet step-by-step traces show `lookup_order` returned stale cached rows on step 2 before step 3 computed the refund. What evaluation taxonomy fix separates these failures?"} context={"Team engineers were about to spend three weeks fine-tuning the model on refund math."} sourceRoute={"/docs/agent-observability/failure-taxonomy-and-anomaly-detection"} answer={3} options={[{"text": "Compute BLEU between the agent's apology and a template string.", "why": "Surface phrasing similarity says nothing about which tool or reasoning step broke first."}, {"text": "Raise the LLM's `max_tokens` so it prints longer intermediate explanations.", "why": "Longer reasoning over stale tool rows still produces wrong totals."}, {"text": "Score only the final turn with a larger frontier judge model.", "why": "An end-only judge without tool-output inspection still blames the LLM's final math."}, {"text": "Perform first-fault span attribution across each trace—separating retrieval/tool staleness, argument construction, reasoning errors, and policy stops—so each team fixes the actual broken layer.", "why": "Pinpointing the earliest bad span stops prompt engineers from trying to tune away broken upstream APIs."}]}>

Final-answer error rates conflate upstream data defects with model failures whenever later LLM steps reason logically over bad tool observations. **First-fault trace attribution** classifies each failed trajectory at the earliest diverging span: (1) environment/tool bug (stale data, 5xx, wrong tool doc); (2) tool-argument/schema slip; (3) reasoning/planning error over valid inputs; or (4) premature stop / budget exhaustion. Attributing step 2's stale `lookup_order` response to the data layer saves weeks of pointless prompt engineering or fine-tuning and directs fixes straight to cache invalidation. Automated fault-attribution classifiers over traces cut root-cause triage time dramatically, at the cost of labeling an initial golden taxonomy of failure traces.

</Choice>

<QA id={"ae-user-simulator-bias-debug"} q={"Your conversational agent scores 94% completion against an LLM user simulator in staging, yet drops to 61% during live customer beta. Inspecting transcripts shows the simulator always answers clarifying questions clearly, copies exact IDs verbatim, and never reverses itself mid-conversation. Diagnose the gap and fix it."} context={"Live customers frequently send typos, ambiguous pronouns, half-remembered order numbers, and impatient topic switches."} sourceRoute={"/docs/ai-evaluation/human-and-adversarial-evaluation"}>

Polite, cooperative LLM user simulators suffer from **instruction-following echo bias**: because the simulator model shares helpful assistant priors, it supplies crisp formatted details, never pushes back ambiguously, and cooperates cleanly—inflating staging scores by 30+ points above real messy human behavior. Harden user simulation by seeding personas directly from anonymized production conversation traces: inject realistic behaviors including terse fragmented replies, typos in IDs, partial information revealed only after probing, mid-stream goal changes, and strict turn-impatience cutoffs. Pairing stratified real-behavior personas with human dogfooding closes the offline-to-online gap at the cost of higher variance and periodic persona refreshes as product habits shift.

</QA>

<Calc id={"ae-trace-compliance-calc"} q={"An agent benchmark runs 400 evaluation tasks. Exactly 300 runs pass the final database end-state verification, yet trajectory trace auditing flags that 15% of those 300 passing runs violated a safety or tool policy (calling an unapproved admin read or bypassing confirmation). What is the true policy-compliant pass rate across all 400 tasks, in percent? (Two decimals.)"} context={"Count a run as compliant-pass only if it satisfies both end-state correctness and trajectory policy rules."} sourceRoute={"/docs/ai-evaluation/llm-rag-agent-evaluation"} answer={63.75} tolerance={0.01} unit={"%"}>

Out of `300` end-state passes, `15%` (`45` runs) violated policy, leaving `300 × (1 − 0.15) = 255` compliant passes. Across `400` total tasks, the true policy-compliant pass rate is `255 ÷ 400 × 100 = ` **`63.75%`** (11.25 points lower than the raw 75.0% end-state headline!). Reporting end-state accuracy alongside policy-compliant pass rate stops safety regressions from masquerading as productivity wins, while showing explicitly whether improvements came from better capability or stricter tool constraints.

</Calc>

<QA id={"ae-non-deterministic-flaky-ci-debug"} q={"Your 100-task agent eval suite fails PR CI randomly 35% of the time on completely unchanged commits, causing engineers to ignore red builds and hit retry. Why does a naive single-run threshold fail on multi-step agents, and how do you make CI deterministic and reliable?"} context={"Each task averages 6 LLM turns at temperature 0.2 plus external search calls; passing threshold was set to 85/100."} sourceRoute={"/docs/mlops/ml-and-llm-testing"}>

When individual multi-step tasks succeed with ~85% per-trial probability across 100 binary items (`SE ≈ 3.6%`), random binomial variance routinely drops single-run scores from 87% down to 81% on identical code—triggering a 35% false-fail rate when gated against a fixed 85% cutoff! Restore CI trust with a two-tier strategy: (1) on every PR, run **fast deterministic structural gates** using recorded/seeded tool sandboxes and `temperature = 0` on a curated deterministic core slice (schema, tool bounds, cycle guards); and (2) on release/nightly candidates, evaluate stochastic tasks across `k = 3–5` trials per item using **paired statistical comparison** (McNemar or paired bootstrap CI against the baseline commit) rather than noisy single-shot absolute cutoffs. Separating deterministic PR gates from multi-trial release gates restores developer trust in red CI builds at the cost of slightly longer nightly compute.

</QA>

<QA id={"ae-production-trace-to-eval-flywheel-design"} q={"Design an automated production trace-to-eval flywheel that mines live agent OpenTelemetry traces for novel failures, strips PII, and turns them into regression tests without bloating CI or overfitting stale traffic."} context={"Production emits 200,000 agent traces daily; CI budget allows up to 300 regression cases."} sourceRoute={"/docs/agent-observability/failure-taxonomy-and-anomaly-detection"}>

Build a staged trace curation pipeline:

1. **Failure-signal ingestion:** Filter tail-sampled OpenTelemetry traces matching high-signal anomalies—user re-asks/edits, cycle-breaker halts, guardrail triggers, tool retries `>= 3`, or human escalation handoffs.
2. **PII scrubbing & minimal reproduction:** Redact customer identifiers deterministically, extract the minimal diverging sub-trajectory (system prompt + seed context + failing tool response), and synthesize deterministic mock stubs for external state at that turn.
3. **Deduplication & stratification:** Cluster failure embeddings so one widespread outage spawns 1–2 representative cases rather than 100 duplicates; cap the active CI suite at 300 cases balanced across core invariants, recent incidents, and retired-bug sampling so old regressions stay covered without slowing CI forever.

Automated trace mining ensures real user failures enter CI within days rather than waiting for quarterly manual labeling, trading modest engineering maintenance on PII scrubbers and mock extractors for continuous regression hardening.

</QA>

<QA id={"ae-multi-agent-eval-harness-design"} q={"Design an evaluation harness for a hierarchical multi-agent system (Lead Planner, Research Worker, Code-Execution Worker) that isolates component regressions, preserves cross-agent traces, and resets shared state cleanly."} context={"Upgrading the Research Worker prompt recently degraded end-to-end coding passes, yet teams cannot tell whether planning, search, or coding broke."} sourceRoute={"/docs/agent-observability/opentelemetry-and-distributed-tracing"}>

Design the harness around **propagated trace IDs, isolated sandbox snapshots, and modular component ablations**:

- **Cross-agent tracing:** Propagate root `trace_id` and `parent_span_id` across every handoff packet (`planner → researcher → coder`), tagging each span with `agent_role`, `prompt_hash`, `model_id`, tokens, and structured handoff payload validation.
- **Component-level ablation:** Evaluate both full end-to-end runs and isolated **interface harnesses**—feeding fixed golden planner sub-goals directly into the Research Worker (scoring retrieval recall + citation grounding) and fixed golden research briefs directly into the Code Worker (scoring test pass rate). When an upgrade drops end-to-end passes, comparing full runs against frozen-interface ablations isolates within minutes whether the Research Worker dropped facts or the Planner stopped delegating properly.
- **Hermetic reset & composite scorecard:** Snapshot container filesystems and DB seeds per trial (zero leaked temp files across tasks) and report pass rate, `pass^k`, policy violations, total tokens across all sub-agents, and critical-path wall time together.

Modular ablations eliminate multi-agent blame games at the cost of maintaining clean handoff schemas and interface fixtures between agent roles.
