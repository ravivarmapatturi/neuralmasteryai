## Model Routing & Choosing Models

<Choice id={"mr-model-version-pinning"} q={"Your production extraction service calls the provider's floating `model-latest` alias rather than a pinned dated snapshot. Why is this risky even when API uptime is 100%?"} context={"Downstream workflows expect deterministic JSON field formats and calibrated confidence thresholds measured in last month's evaluation."} sourceRoute={"/docs/mlops/deployment-strategies"} answer={2} options={[{"text": "Floating aliases double per-token billing without changing weights.", "why": "Provider aliases carry the same published token pricing as the underlying snapshot."}, {"text": "Aliases bypass prompt caching at the network edge.", "why": "Caching still works per prefix until the underlying weights change and invalidate KV compatibility."}, {"text": "Provider-side model updates silently shift output distributions, formatting habits, and safety refusals without any deploy on your side.", "why": "Pinning an immutable version keeps behavior frozen until you replay your regression suite on the new snapshot."}, {"text": "Floating aliases disable streaming responses.", "why": "Streaming transport works identically across pinned and unpinned model identifiers."}]}>

Floating aliases let the provider swap weights or system defaults underneath live traffic, silently invalidating your prompt tuning and calibrated thresholds. Every production endpoint should pin an immutable snapshot ID and treat a model upgrade like a code release: run shadow comparisons and regression evals on the candidate snapshot before shifting canary traffic. A routine silent update often alters whitespace formatting, tool-call verbosity, or borderline refusal rates overnight while HTTP 200 status codes stay green. Pinning guarantees behavioral reproducibility across incidents, at the cost of tracking deprecation dates and running scheduled migration gates before old snapshots retire.

</Choice>

<QA id={"mr-when-small-beats-large"} q={"When should you choose a specialized 8B model (or fine-tuned encoder) over a frontier reasoning model in a production system?"} context={"A support router classifies 400 tickets/second into 12 fixed intents under a strict 150 ms p99 latency SLA."} sourceRoute={"/docs/ml-system-design/model-catalog-and-benchmarking"}>

Choose a specialized small model when the task has bounded input-output structure, tight latency or cost targets, and enough labeled examples to match frontier quality on that narrow distribution. Small encoders or distilled 8B models finish in tens of milliseconds on compact GPUs and avoid verbose reasoning drift on rigid schemas. Sending 400 classification requests per second to a frontier reasoning model blows latency budgets, multiplies spend by 10–30×, and introduces occasional explanatory prose around enum labels. Narrow models win on predictable unit economics and speed, trading away broad zero-shot generalization when new ticket categories emerge.

</QA>

<Calc id={"mr-blended-router-cost-calc"} q={"A two-tier router serves 1,000,000 monthly requests averaging 1,000 input tokens and 300 output tokens each. It sends 70% of requests to a fast tier ($0.15/1M input, $0.60/1M output) and 30% to a frontier tier ($3.00/1M input, $15.00/1M output), while the router classifier adds $0.02 per 1,000 requests. What is the total monthly spend in USD?"} context={"Assume no prompt caching discounts and zero retries across the 1,000,000 requests."} sourceRoute={"/docs/mlops/ai-cost-engineering"} answer={2501} tolerance={0.0} unit={"USD"}>

Compute each tier separately plus router overhead:

- **Fast tier (700,000 requests):** 700M input tokens × $0.15 = $105.00; 210M output tokens × $0.60 = $126.00; subtotal = $231.00.
- **Frontier tier (300,000 requests):** 300M input tokens × $3.00 = $900.00; 90M output tokens × $15.00 = $1,350.00; subtotal = $2,250.00.
- **Router overhead:** 1,000 thousand requests × $0.02 = $20.00.

Total spend is $231 + $2,250 + $20 = **$2,501**, saving two-thirds compared with sending all traffic to the frontier model ($7,500). Output tokens dominate the frontier bill ($1,350 vs $900), so routing verbose generation tasks accurately yields the biggest savings while misrouting easy verbose replies wastes budget fast.

</Calc>

<Choice id={"mr-router-vs-cascade-tradeoff"} q={"Compare an upfront predictive router against a sequential confidence cascade. When does a cascade lose both latency and cost against direct frontier calls?"} context={"User-facing coding assistant expects sub-second TTFT; complex multi-file queries make up 65% of live traffic."} sourceRoute={"/docs/mlops/ai-cost-engineering"} answer={1} options={[{"text": "When the small model answers correctly 95% of the time without needing verification.", "why": "High small-model pass rates make sequential cascades maximally cheap because few requests escalate."}, {"text": "When most queries escalate to the frontier tier anyway, forcing requests to pay small-model generation plus verifier latency before starting the frontier call.", "why": "At high escalation rates, the cascade adds wasted small-model tokens and doubles first-token wait for the majority of users."}, {"text": "When the predictive router uses a logistic regression classifier over embeddings.", "why": "Lightweight embedding classifiers add under 10 ms overhead and avoid running any failed LLM generation first."}, {"text": "When frontier pricing is lower than small-model pricing.", "why": "Frontier models carry higher per-token costs; the issue is paying two generations plus verification on escalated traffic."}]}>

An upfront router classifies query difficulty before generation, whereas a sequential cascade tries the cheap model first, evaluates the draft, and escalates weak outputs to the frontier tier. When complex queries dominate traffic, cascades burn both time and money: 65% of users wait through a full small-model decode and verifier check only to restart from scratch on the frontier model. Under heavy escalation, streaming cannot begin safely until verification clears, destroying perceived TTFT. Upfront routing cuts tail latency when labeled routing data exists, trading verifier accuracy on ambiguous edge cases for single-hop dispatch.

</Choice>

<Calc id={"mr-cascade-threshold-breakeven-calc"} q={"Sending a request directly to a frontier model costs $0.020. A cascade instead runs a small model ($0.002) plus an external verifier ($0.002) on every request, then escalates failing cases to the frontier model ($0.020). What is the maximum escalation rate (in percent) where the cascade still stays cheaper than calling the frontier model directly?"} context={"Ignore latency cost and assume all escalated requests pay both the initial cascade pass and the full frontier price."} sourceRoute={"/docs/mlops/ai-cost-engineering"} answer={80} tolerance={0.0} unit={"%"}>

Each request pays $0.002 + $0.002 = $0.004 upfront, plus `e × $0.020` for escalated traffic. Setting expected cost below direct frontier cost gives `0.004 + 0.020 × e < 0.020`, so `0.020 × e < 0.016`, yielding break-even escalation **`e = 80%`**. Beyond 80% escalation, paying the small model and verifier wastes more money than skipping straight to the frontier endpoint. In real systems where escalations also degrade TTFT and consume extra KV capacity, teams cap cascade escalation well below 40%–50% or switch to an upfront predictive router once traffic difficulty shifts upward.

</Calc>

<Choice id={"mr-verifier-bottleneck-debug"} q={"Your two-tier cascade uses a small model with a prompt asking it to rate its own certainty (1–5) and escalates scores below 4. Monthly cost drops 55%, yet wrong answers on subtle policy edge cases jump while escalation stays at 12%. Why?"} context={"Escalation rate sits near 12%, HTTP errors are zero, and customer complaints cluster around outdated exception rules."} sourceRoute={"/docs/mlops/ai-cost-engineering"} answer={0} options={[{"text": "Small models are poorly calibrated on out-of-distribution errors and emit high self-confidence scores on fluent hallucinations.", "why": "Self-reported certainty correlates with surface fluency rather than factual accuracy on edge cases."}, {"text": "The frontier model is overriding small-model answers with lower quality.", "why": "Only 12% of queries ever reach the frontier tier, so the 88% handled by the small tier drives the accuracy drop."}, {"text": "Token-level log probabilities always return 1.0 under greedy decoding.", "why": "Greedy decoding picks the argmax token, whose softmax probability can still be low (for example 0.35), though prompted numeric self-ratings are even less calibrated."}, {"text": "Prompt caching hid the escalation instructions after the first request.", "why": "Prompt caching preserves exact prefix behavior and does not erase rubric instructions."}]}>

Self-assessed confidence ratings from a small generator fail as a cascade gate because models hallucinate plausibly with high stated certainty (`5/5`). When subtle policy exceptions diverge from pretraining priors, the 8B model confidently outputs stale guidance and skips escalation, cutting API spend at the cost of silent accuracy collapse on the hardest 15% of queries. Production cascades replace self-ratings with external signals: deterministic schema or code checks, retrieval grounding scores, sequence log-probability margins, or an independent lightweight verifier model. External verifiers restore recall on policy traps at the cost of 20–100 ms verification overhead.

</Choice>

<Calc id={"mr-shadow-eval-calibration-calc"} q={"On a 2,000-query golden benchmark, a tuned routing threshold sends 1,400 queries to the fast tier (where the fast tier achieves 88.0% accuracy) and 600 queries to the frontier tier (where the frontier tier achieves 95.0% accuracy). What is the router's blended accuracy in percent?"} context={"Evaluate exact weighted accuracy across the 2,000 queries with no abstentions."} sourceRoute={"/docs/ml-system-design/model-catalog-and-benchmarking"} answer={90.1} tolerance={0.01} unit={"%"}>

Count correct answers per slice: `(1,400 × 0.88) + (600 × 0.95) = 1,232 + 570 = 1,802` correct queries out of `2,000`, so blended accuracy is `1,802 ÷ 2,000 × 100 = ` **`90.1%`**. Tracking only aggregate accuracy can mislead if the 198 failures in the fast slice happen on high-stakes billing or medical intents. Reporting accuracy per routed bucket alongside cost-normalized accuracy shows whether the frontier tier would have fixed those 198 misses (avoidable routing errors) or whether both models failed on bad retrieval context, guiding threshold calibration vs data fixes.

</Calc>

<QA id={"mr-multiturn-router-stickiness-debug"} q={"A chat coding assistant runs a per-turn router: greetings go to an 8B model and debugging turns go to a 70B model. Users report abrupt tone and formatting whiplash across turns, and provider prompt-cache hit rates sit near zero on long threads. What went wrong, and how do you fix it?"} context={"Conversations average 8 turns; each turn re-sends the growing thread history."} sourceRoute={"/docs/agents/routing-and-supervisor"}>

Routing every turn independently breaks both behavioral continuity and prefix KV caching across a session. When turn 1 runs on an 8B model, turn 2 on a 70B model, and turn 3 back on an 8B model, neither provider holds warm prefix blocks from the prior turn (causing full prefill re-computation and zero cache discount), while the weaker model reads earlier 70B code blocks and regresses style or tool formatting mid-thread. Switch to **session-sticky routing** or a **one-way escalation ratchet**: classify the thread on turn 1, pin the session to that tier (or escalate permanently to the stronger model once complexity triggers), and keep the prefix immutable. Session pinning restores prompt-cache hits and tone stability at the cost of keeping escalated sessions on the pricier tier until reset.

</QA>

<QA id={"mr-tool-capability-aware-routing"} q={"Why do static leaderboard ranks (like overall MMLU or Arena Elo) fail as the sole model-selection criterion in an enterprise agent router, and what capability signals belong in the routing matrix instead?"} context={"Your platform routes structured extraction, SQL tool-use, long-contract summarization, and non-English customer chat across four model families."} sourceRoute={"/docs/ml-system-design/model-catalog-and-benchmarking"}>

Aggregate benchmark averages mask steep per-capability cliffs—a model scoring top-3 on general chat can drop 25 points on parallel function calling, strict JSON grammar conformance, 64k-token multi-hop recall, or non-Latin tokenizer efficiency. Routing an enterprise SQL agent purely by Arena Elo sends complex multi-table joins to a chatty model that invents column names or breaks tool schemas under 40k context. Build a task-capability matrix from your own golden slices tracking schema pass rate, needle-reconciliation recall at real context lengths, non-English token fertility multiplier, and p99 TTFT. Capability-sliced routing matches workloads accurately at the cost of maintaining periodic eval runs per capability cell.

</QA>

<QA id={"mr-canary-router-rollback-debug"} q={"You add a new fast model to a production semantic router. Aggregate p50 latency drops 30% and spend drops 25%, yet checkout conversion in French and German drops 14% with zero HTTP errors. How do you isolate and resolve this?"} context={"English makes up 85% of daily queries; automated error-rate alerts remained silent."} sourceRoute={"/docs/mlops/monitoring-and-drift"}>

Aggregate medians hid a localized quality regression because English traffic (85%) dominated global metrics while the new fast model degraded non-English prompts. Slice routing telemetry by `(model_id, locale, intent)` to compare refusal rates, output-token inflation, and conversion immediately before vs after router weights shifted. Often a fast model exhibits higher subword tokenization fertility on French/German—tripling token count toward `max_tokens` truncation—or overly aggressive safety refusals on translated idioms. Pin affected locales back to the baseline model, add per-locale minimum cohorts to automated canary gates, and require stratified multilingual evals before admitting new models, trading higher non-English token spend for preserved conversion.

</QA>

<QA id={"mr-multi-region-latency-routing-design"} q={"Design a multi-region LLM routing gateway serving US, EU, and APAC users where EU prompts must stay strictly inside EU endpoints under data residency rules while minimizing global tail latency."} context={"Each region runs primary and secondary model endpoints; traffic peaks rotate across time zones."} sourceRoute={"/docs/mlops/llm-hosting-and-serving-patterns"}>

Split routing into a hard **compliance filter** followed by a **region-local latency and health scorer**. First, bind tenant residency tags (`region_lock: eu`) in signed auth claims so the EU ingress router filters candidate endpoints exclusively to EU VPC clusters, hard-failing (`503`) rather than spilling over to US replicas during an EU outage. Second, within allowed regions, score healthy endpoints using EWMA TTFT, active queue depth, and circuit-breaker state; non-residency-locked APAC/US traffic can spill across nearest healthy neighbors when local GPUs saturate. Global health broadcasting without residency pinning risks silent cross-border PII transfers during failover. Hard policy filters plus local EWMA scoring maintain legal compliance and low latency at the cost of higher standby capacity inside locked regions.

</QA>

<QA id={"mr-online-bandit-router-design"} q={"Design an online contextual-bandit router that learns model selection weights from live production feedback without starving newly added models or chasing delayed labels blindly."} context={"Explicit feedback is rare; ticket resolution outcomes arrive 2 to 24 hours after a chat ends, and new models onboard monthly."} sourceRoute={"/docs/mlops/ai-cost-engineering"}>

Use an off-policy logged contextual bandit (such as LinUCB or Thompson Sampling over query/task features) combined with bounded exploration (`epsilon = 2%–5%`), composite cost-quality rewards, and delayed attribution windows. Log the router's exact propensity score `p(arm | x)` at request time so delayed resolution signals arriving 24 hours later train updates without selection bias, while gating reward updates with short-horizon proxy checks (format validity, zero immediate re-asks) so catastrophic broken models halt within minutes instead of waiting 24 hours. Greedy argmax routing without exploration locks out newly onboarded models permanently, while uncapped exploration leaks bad answers to paying users. Propensity-logged shadow traffic plus capped exploration balances continual adaptation with strict user-experience bounds.

</QA>

## Fallbacks & Graceful Degradation

<Choice id={"fb-degradation-ladder-concept"} q={"When your primary frontier LLM times out on a RAG product-search assistant, what is the right graceful degradation order rather than immediately returning HTTP 500?"} context={"Users are browsing product documentation; sub-second responsiveness matters more than polished prose during an upstream outage."} sourceRoute={"/docs/mlops/production-reliability"} answer={3} options={[{"text": "Retry the primary frontier endpoint 10 times with 5-second waits before failing.", "why": "Ten sequential retries keep threads blocked for 50 seconds and amplify load on a struggling upstream."}, {"text": "Ask a smaller model to answer without running retrieval.", "why": "Dropping retrieval turns product docs into ungrounded hallucinations."}, {"text": "Return raw stack traces so power users know which region crashed.", "why": "Exposing internal stack traces hurts UX and leaks topology details."}, {"text": "Step down a ladder: backup model tier → cached popular answer or fast extractive summary → plain lexical search links → deterministic status message.", "why": "Each rung lowers dependency cost while preserving grounded utility instead of hard-failing."}]}>

A graceful degradation ladder trades conversational polish for deterministic availability across progressive fallback rungs: switch to a secondary model or backup provider first, drop expensive reranking or generation to return cached/extractive snippets from retrieved docs next, fall back to plain BM25 search results if generation fails entirely, and show a clean static retry message as the floor. Immediately jumping to 500 pages users needlessly when retrieval itself still works, while ungrounded parametric fallbacks fabricate product specs. Every degraded rung must display clear UI state (`"Showing matching docs while chat recovers"`) and alert ops so prolonged brownouts never hide silently behind green HTTP 200 metrics.

</Choice>

<Calc id={"fb-parallel-vs-fallback-availability-calc"} q={"A primary model provider delivers 99.0% availability (0.99), and an independent secondary provider delivers 98.0% availability (0.98). Assuming instant health failover on outage, what is the combined theoretical availability in percent?"} context={"Assume failure modes across the two providers are statistically independent."} sourceRoute={"/docs/mlops/production-reliability"} answer={99.98} tolerance={0.001} unit={"%"}>

Failover only breaks when **both** providers fail simultaneously: `(1 − 0.99) × (1 − 0.98) = 0.01 × 0.02 = 0.0002` failure probability, yielding combined availability `1 − 0.0002 = 0.9998 = ` **`99.98%`** (cutting downtime by 50× from 7.2 hours/month to ~8.6 minutes/month). In production, shared upstream failures—DNS outages, regional fiber cuts, or identical safety-filter bugs triggered by the same adversarial input—introduce correlation that caps real availability lower than 99.98%. Keeping backups on distinct clouds and testing failover with scheduled chaos drills validates genuine independence at the cost of maintaining dual prompt parity.

</Calc>

<QA id={"fb-circuit-breaker-states-concept"} q={"Explain the Closed, Open, and Half-Open states of a circuit breaker on an LLM gateway, and clarify why a breaker does not repair a failing model server."} context={"Upstream GPU nodes start hanging at 30 s timeouts under load; gateway worker threads are saturating."} sourceRoute={"/docs/software-system-design/circuit-breakers"}>

A circuit breaker stops callers from piling onto a broken dependency: in **Closed** state, traffic flows normally while tracking rolling error/timeout rates; once failures breach a threshold, it trips **Open** to fail fast locally (or route immediately to fallback) without waiting 30 s per request; after a cooldown timer, it moves to **Half-Open** to admit limited test probes, closing on success or reopening on failure. Without a breaker, 30-second hanging calls exhaust every gateway thread and connection pool, cascading an upstream model stall into a total API outage. Remember that a breaker only buys recovery headroom and protects caller resources—it cannot fix an upstream OOM or bad deploy unless autoscaling, load shedding, or rollback relieves the root cause.

</QA>

<Choice id={"fb-error-taxonomy-for-breaker-debug"} q={"Your LLM gateway's circuit breaker suddenly trips Open during a busy afternoon, dropping healthy requests to a degraded fallback—yet upstream GPU health checks are 100% green. Logs show a surge of `HTTP 400` and guardrail rejection responses from malformed client payloads. What bug triggered the false trip?"} context={"One enterprise customer deployed a broken script sending oversized invalid JSON payloads for 5 minutes."} sourceRoute={"/docs/software-system-design/circuit-breakers"} answer={1} options={[{"text": "Half-Open probe interval was set to 5 seconds instead of 60 seconds.", "why": "Probe duration affects recovery speed, not why healthy client errors tripped the closed breaker initially."}, {"text": "The circuit breaker counted `4xx` client validation and policy rejections as dependency failures instead of restricting trips to `5xx`, `429`, and network timeouts.", "why": "One bad tenant sending invalid `400` payloads polluted the global error ratio and locked out every other tenant."}, {"text": "Circuit breakers must run inside the database rather than gateway memory.", "why": "Per-gateway or shared breakers work cleanly once error classification separates client vs upstream faults."}, {"text": "HTTP 400 responses consume more KV cache than HTTP 200 responses.", "why": "Bad payload rejections fail at validation before KV-cache allocation."}]}>

Counting `4xx` client mistakes (invalid schemas, auth errors, context-length rejections, or safety blocks) inside the dependency failure counter lets a single buggy client trip the breaker for every healthy tenant. Circuit breakers must classify errors strictly: count only upstream infrastructure signals (`5xx`, connection resets, read timeouts, and optionally `429` for capacity routing) toward trips, while excluding `400`/`401`/`403`/`422` client errors. Similarly, multi-tenant gateways should isolate per-endpoint breakers from per-tenant rate limiters so abusive callers get `429` locally without failing over global capacity. Tight error taxonomy prevents self-inflicted outages at zero extra latency.

</Choice>

<Calc id={"fb-hedged-requests-cost-calc"} q={"To cut tail latency, your gateway sends a hedged backup call to a secondary endpoint whenever the primary model has not returned a first token by its p95 latency mark (affecting 5% of traffic). On 200,000 daily requests costing $0.006 per dispatched call (with no partial billing refund on late abort), what extra daily spend in USD does hedging add?"} context={"Assume secondary calls have identical $0.006 unit pricing and no retries inside either branch."} sourceRoute={"/docs/software-system-design/latency"} answer={60} tolerance={0.0} unit={"USD"}>

Hedged duplicates fire on `5%` of `200,000` requests = `10,000` extra calls per day, adding `10,000 × $0.006 = ` **`$60`** per day (a 5% cost premium over the $1,200 baseline). Hedging trims p99 tail latency dramatically against straggler GPUs at modest cost when triggered only past p95. However, if primary latency degrades globally during an overload event, >50% of traffic crosses the fixed latency threshold simultaneously, turning hedging into a 1.5×–2× traffic amplifier that worsens cluster saturation. Pairing hedged calls with dynamic percentile thresholds and a hedging token budget prevents overload amplification while preserving clean p99 bounds.

</Calc>

<QA id={"fb-half-open-probe-thundering-herd-debug"} q={"During recovery from a provider outage, all 40 gateway pods exit their 30-second Open cooldown simultaneously in Half-Open state, each allowing 5 probe requests through—instantly crashing the warming upstream vLLM cluster again. Diagnose and fix this."} context={"Normal steady-state capacity of the recovering cluster is 80 RPS; 40 pods sit behind round-robin load balancing."} sourceRoute={"/docs/software-system-design/circuit-breakers"}>

Synchronized cooldown timers caused a Half-Open probe thundering herd: 40 independent pods × 5 concurrent probes dumped 200 cold-queue requests into the recovering backend at the exact same millisecond. Because newly restarted inference pods are still compiling CUDA graphs or warming prefix caches, that burst immediately trips timeouts and flips all 40 pods back to Open in an endless oscillation loop. Add **jittered open cooldowns** (`30s ± 10s`), restrict Half-Open probes to **1 in-flight probe per pod** (or coordinate via a central token bucket / slow-start ramp: 1% → 5% → 25% → 100% traffic over 60 seconds), and enforce consecutive successes before closing. Slow-start ramping protects warming GPUs cleanly at the cost of slightly longer time to full recovery.

</QA>

<Choice id={"fb-priority-load-shedding-concept"} q={"Under severe upstream GPU saturation, why is strict priority-based load shedding (rejecting background batch jobs first) better than keeping FIFO queues or dropping 20% of all requests at random?"} context={"Your gateway serves interactive checkout assistants alongside nightly document tagging and offline eval replays."} sourceRoute={"/docs/mlops/production-reliability"} answer={2} options={[{"text": "Random drops violate TCP checksum ordering.", "why": "HTTP/TCP framing is unaffected; the issue is wasting GPU capacity on non-urgent work while dropping interactive users."}, {"text": "FIFO queues execute higher-token prompts faster.", "why": "FIFO queues actually mix long batch prompts ahead of interactive prompts, hurting interactive TTFT."}, {"text": "FIFO queueing makes every request wait past client timeouts (goodput drops toward zero), whereas priority shedding drops deferrable background work so interactive users stay fast.", "why": "Dropping low-priority batch jobs preserves high goodput for latency-sensitive user traffic."}, {"text": "Priority shedding disables KV-cache eviction.", "why": "Shedding occurs at gateway admission before KV-cache allocation."}]}>

Under overload, FIFO queues accumulate deep backlogs where even fast interactive requests wait past client timeouts, causing the GPU to burn 100% compute on abandoned responses (`0%` useful goodput). Random shedding still drops critical checkout traffic while burning capacity on deferrable nightly tags. Priority load shedding assigns an explicit criticality tier (`P0` interactive, `P1` async workflows, `P2` batch/evals) at admission: when queue delay or concurrency crosses thresholds, shed `P2` and `P1` immediately with `429 Retry-After` and keep `P0` queues shallow and fast. Priority admission preserves user-facing SLOs during spikes at the cost of delaying batch pipelines and requiring honest caller tier tags.

</Choice>

<Calc id={"fb-stale-cache-fallback-calc"} q={"A RAG pipeline serves 100,000 daily requests with 99.5% primary upstream availability (500 primary failures/day). When the primary generator fails, a graceful fallback serves cached answers or BM25 document cards for 76% of failed requests, leaving 24% visibly failing. What is user-visible availability in percent?"} context={"Assume degraded responses satisfy the fallback SLO when primary generation is unavailable."} sourceRoute={"/docs/mlops/production-reliability"} answer={99.88} tolerance={0.001} unit={"%"}>

Of the `0.5%` primary outage slice (`500` requests), only `24%` still fail visibly: `0.005 × 0.24 = 0.0012 = 0.12%` (`120` failed requests per day). Subtracting from `100%` gives effective user-visible availability `100% − 0.12% = ` **`99.88%`** (cutting unserved requests from 500 to 120 daily). Measuring primary health and fallback-served availability separately is vital: if ops alerts only on user-visible 500s, a broken primary model hidden behind 76% degraded card coverage can linger unnoticed for days while search quality drops.

</Calc>

<QA id={"fb-cross-provider-schema-drift-debug"} q={"During a primary API outage, traffic fails over cleanly to a backup open-weight model hosted elsewhere—with HTTP 200s across the board—yet downstream JSON parsers crash on 18% of requests and tool calls loop. What failed across the failover boundary?"} context={"Primary uses strict JSON Schema enforcement; backup uses prompt-only JSON mode and a 16k context window."} sourceRoute={"/docs/mlops/production-reliability"}>

Failover succeeded at the transport layer yet broke semantic and schema contracts because backup capabilities did not match primary assumptions. Specifically: (1) backup lacked constrained grammar decoding (`strict: true`), returning Markdown fences or missing keys; (2) slightly different tool-call formatting or weaker instruction adherence caused repetitive malformed arguments; and (3) a 32k prompt quietly exceeded the backup's 16k window, truncating critical tool definitions. Never ship an untested backup target: run your full schema, tool-use, and truncation contract suite continuously against every fallback tier, cap input lengths to the smallest tier's context ceiling (or apply an automatic summarizer step on failover), and keep fallback prompt adapters versioned alongside primary prompts—trading minor latency for reliable multi-provider parity.

</QA>

<QA id={"fb-retrieval-degradation-without-hallucination"} q={"During a vector-database timeout on a medical benefits assistant, an engineer suggests falling back to pure LLM generation without context so users still get a fast answer. Why is that dangerous, and what degraded path should you build instead?"} context={"Users ask about drug coverage, deductibles, and out-of-pocket limits from current plan PDFs."} sourceRoute={"/docs/mlops/production-reliability"}>

Dropping retrieval and falling back to ungrounded LLM generation converts a visible latency outage into a silent, high-liability hallucination outage. The model fluently invents outdated deductible rules or coverage limits with confident medical phrasing that looks indistinguishable from cited policy facts. Instead, degrade down a **grounded-only ladder**: (1) fall back from vector search to a fast backup BM25/keyword index or precomputed plan-summary cache; (2) if all knowledge stores fail, return a structured deterministic error or link directly to the relevant plan portal section (`"Plan database temporarily unavailable — please verify coverage directly at..."`); and (3) require explicit UI badges on degraded modes. Refusing cleanly preserves clinical and legal trust at the cost of temporary zero-answer rates during total retrieval outages.

</QA>

<QA id={"fb-brownout-feature-shedding-design"} q={"Design an automated brownout controller for an enterprise AI research assistant when GPU cluster utilization exceeds 92% or error-budget burn spikes 5×."} context={"A full request runs query rewriting, 3-hop retrieval, cross-encoder reranking, multi-step reflection, and verbose frontier synthesis."} sourceRoute={"/docs/mlops/production-reliability"}>

Build a centralized feature-flag **brownout state machine** (`NORMAL` → `CONSERVE` → `CRITICAL`) driven by sliding-window TTFT, queue depth, and SLO burn rate, shedding optional quality multipliers before rejecting traffic. At `CONSERVE` (GPU > 88%), disable multi-pass reflection and speculative query expansion (cutting LLM calls per query from 4 to 1). At `CRITICAL` (GPU > 94%), bypass the cross-encoder reranker (using bi-encoder top-5 directly), cap `max_tokens`, and route eligible queries to a faster quantized model while keeping core grounded citations intact. Add **hysteresis** (trip at 92% for 30 s, recover only below 80% for 2 min) and minimum dwell times to prevent flapping oscillation across states. Staged brownouts keep core queries fast during spikes at the cost of temporary recall dips and complex testing across degraded permutations.

</QA>

<QA id={"fb-multiregion-active-passive-failover-design"} q={"Design active-passive regional failover for a stateful conversational AI API when Region A loses all GPU capacity. Address in-flight streams, conversation history, prompt-cache warmness, and preventing Region B overload."} context={"Region B runs warm at 35% baseline load while Region A serves 65% of global traffic; active streams last up to 20 seconds."} sourceRoute={"/docs/software-system-design/multi-region-design"}>

Separate stateless compute failover from durable state replication and controlled traffic draining. <QA id={"ob-blameless-postmortem-ai-incident"} q={"What changes in a blameless postmortem when an AI incident stems from probabilistic drift (a subtle prompt edit, upstream model behavior shift, or retrieval index staleness) rather than a deterministic code crash?"} context={"No server threw an exception; for 3 hours, 22% of financial summaries omitted tax liabilities."} sourceRoute={"/docs/mlops/observability"}>

Traditional deterministic postmortems link a commit SHA directly to a stack trace, whereas probabilistic AI incidents require reconstructing exact **data, prompt, and model provenance** to explain why outputs shifted silently. A strong AI postmortem captures: (1) exact immutable `prompt_hash`, `model_snapshot_id`, `retriever_index_version`, and inference parameters (`temperature`, `seed`) at incident time; (2) the **detection gap** explaining why HTTP monitoring missed semantic omissions; (3) **blast-radius quantification** over sampled traces using an offline rubric evaluator; and (4) **durable preventive gates**—promoting failing trace inputs directly into deterministic CI regression tests and adding automated output invariant alerts (e.g., `"tax_field_present_rate"`). Without immutable version tagging across prompts and indexes, teams blame "model flakiness" and repeat the exact outage weeks later.

</QA>

<QA id={"ob-correlated-telemetry-incident-triage"} q={"At 09:15 UTC, customer escalations spike for wrong invoice totals. API status codes are 100% HTTP 200, GPU utilization looks normal, and no code deploy ran. Walk through the exact triage steps using logs, OpenTelemetry traces, and evaluation telemetry."} context={"Your pipeline combines PDF ingestion, hybrid retrieval, and LLM structured extraction."} sourceRoute={"/docs/software-system-design/observability"}>

Follow the causal trace pipeline backward from output to ingestion rather than guessing at prompts:

1. **Correlate by time and slice:** Group recent bad traces by `tenant`, `document_type`, `model_snapshot`, and `index_version` to see if failures hit everything or one upstream change (e.g., an external model update or an overnight ingestion batch).
2. **Inspect LLM inputs vs outputs in traces:** Check whether extracted totals match the retrieved chunks inside the span; if chunks already contain mangled table rows, the fault is **ingestion/parsing**, not the LLM.
3. **Check retrieval score distributions:** Compare `top_k` similarity scores, filter drop counts, and empty-context rates against yesterday's baseline to spot index staleness or embedding drift.
4. **Verify model and guardrail spans:** Check if `model_id` resolved to an updated upstream snapshot, `finish_reason` shifted to `length`, or post-processing normalizers stripped signs/decimals.

Causal trace isolation resolves the right layer in minutes, avoiding wasted prompt rewrites over a broken PDF parser.

</QA>

<QA id={"ob-otel-genai-observability-design"} q={"Design an OpenTelemetry observability architecture for a 5,000 QPS multi-model AI gateway: specify GenAI span attributes, PII redaction, cost-bounded tail sampling, and real-time incident alerting."} context={"Storing 100% of raw traces at 5,000 QPS costs more than GPU inference itself; strict privacy compliance forbids raw PII in central trace stores."} sourceRoute={"/docs/agent-observability/opentelemetry-and-distributed-tracing"}>

Combine low-cardinality Prometheus metrics at the edge with PII-scrubbed, tail-sampled OpenTelemetry traces. Every gateway and tool step propagates W3C `traceparent` headers and emits OpenTelemetry GenAI attributes (`gen_ai.system`, `gen_ai.request.model`, `gen_ai.usage.input_tokens`, `cached_tokens`, `output_tokens`, `prompt_hash`, `finish_reason`, `ttft_ms`, `guardrail_verdict`). Run a local collector processor inside the VPC to mask PII/secrets and store raw prompts only in encrypted short-TTL debug buckets (or drop payloads while retaining hashes and token counts). Use **tail-based sampling** in the collector tier: keep **100%** of traces with `5xx`/`429`, `ttft > SLO`, guardrail triggers, retries, or implicit user re-asks, and keep only **1%–2%** baseline head-sampled healthy traces. Pair edge metrics with multi-window SLO burn alerts and automated token-velocity alarms, giving complete incident visibility at ~5% of full-trace storage cost while requiring sufficient collector buffer RAM for tail-sampling trace assembly.

</QA>
