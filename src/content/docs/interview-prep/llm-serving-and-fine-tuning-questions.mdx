# LLM Serving and Fine-Tuning Interview Questions

GenAI interviews now go past "what is a transformer" into what it costs to run one and how to adapt it. These questions use a typical 8B-class model with grouped-query attention: 32 layers, 8 key-value heads, head dimension 128, served in bf16. The arithmetic is the same for any model, so it's worth doing once by hand.

## Prefill, decode and memory

<Choice id={"srv-decode-bound"} q={"When a model generates tokens one at a time for a single user, what limits its speed on a GPU?"} answer={2} options={[{"text": "Network latency between the user and the server.", "why": "That adds time before and after, not to each token's generation."}, {"text": "Compute: the GPU's FLOPs.", "why": "That's what limits prefill, where many tokens are processed in parallel."}, {"text": "Memory bandwidth: every new token has to read all the weights from GPU memory.", "why": "Decode does little arithmetic per byte it reads, so it waits on memory."}, {"text": "The tokenizer.", "why": "Tokenising is tiny compared with a forward pass."}]}>

**Prefill** processes the whole prompt in parallel: big matrix multiplications, compute-bound. **Decode** produces one token per forward pass: for each token the GPU streams every weight through for a few operations each, so it's **memory-bandwidth-bound**. That's why batching many users together makes decode far more efficient: the weights are read once per step and used for every sequence in the batch.

**Follow-ups you'll get**

- **So what improves single-user decode speed?** Moving fewer bytes per token: quantised weights, speculative decoding (several tokens per weight read), or hardware with more bandwidth.

</Choice>

<Calc id={"srv-decode-ceiling"} q={"A 7B model in bf16 (14 GB of weights) runs on a GPU with 2 TB/s of memory bandwidth. What's the theoretical maximum decode speed for one sequence? (Tokens per second.)"} answer={142.85714285714286} tolerance={0.03} unit={"tokens/s"}>

Each token reads every weight once: 2 × 10¹² bytes/s ÷ 14 × 10⁹ bytes = **143 tokens/s**. Real numbers land lower (the KV cache is read too, and kernels don't hit peak bandwidth), but this ceiling is the right first estimate, and it's why 7B models feel fast and 70B ones don't.

**Follow-ups you'll get**

- **What happens to this ceiling with a batch of 32?** Total throughput rises almost 32× until compute or KV-cache reads take over, because the weights are read once for all 32 sequences.

</Calc>

<Calc id={"srv-decode-int4"} q={"Same GPU, same model, but quantised to int4 weights (3.5 GB). What's the new ceiling for one sequence?"} answer={571.4285714285714} tolerance={0.03} unit={"tokens/s"}>

2 × 10¹² ÷ 3.5 × 10⁹ = **571 tokens/s**, four times the bf16 figure, because decode speed follows the bytes moved. Quantisation is mainly a memory-bandwidth optimisation for decode, which is why weight-only quantisation is so common in serving.

**Follow-ups you'll get**

- **What does int4 cost you?** Some quality, and how much varies by model and task, so evaluate on your own prompts. Some kernels also dequantise on the fly and lose part of the speed-up.

</Calc>

<Calc id={"srv-kv-per-token"} q={"With 32 layers, 8 KV heads of dimension 128, and bf16 (2 bytes), how much KV cache does one token take? (KiB.)"} answer={128.0} tolerance={0.0} unit={"KiB"}>

Each layer stores a key and a value for each KV head: 2 × 32 layers × 8 heads × 128 dims × 2 bytes = 131,072 bytes = **128 KiB** per token. With full multi-head attention (32 KV heads) it would be 512 KiB. Grouped-query attention cuts the cache by 4× here.

**Follow-ups you'll get**

- **Why doesn't the number of query heads appear?** Queries are used and thrown away each step. Only keys and values are cached for future tokens.

</Calc>

<Calc id={"srv-kv-8k"} q={"How much KV cache does one sequence with an 8,192-token context need? (GiB.)"} answer={1.0} tolerance={0.0} unit={"GiB"}>

8,192 tokens × 128 KiB = 1,048,576 KiB = **1 GiB** per sequence. Long contexts are expensive mainly because of the cache, not the weights.

**Follow-ups you'll get**

- **And at 128k context?** 16 GiB for a single sequence, more than the 7B model's weights.

</Calc>

<Calc id={"srv-kv-concurrency"} q={"After loading the weights, 40 GiB of GPU memory is left for the KV cache. How many 8k-token sequences can run at once?"} answer={40.0} tolerance={0.0} unit={"sequences"}>

40 GiB ÷ 1 GiB per sequence = **40** sequences. This is what really limits how many users one GPU can serve. It's why paged attention (allocating the cache in small blocks as sequences grow, instead of reserving the maximum up front) raises throughput so much: most sequences never reach 8k.

**Follow-ups you'll get**

- **How else can you fit more?** Quantise the KV cache to 8 bits (twice the sequences), cap the context length, or use a model with fewer KV heads.

</Calc>

<Choice id={"srv-gqa"} q={"Why do most recent open models use grouped-query attention (GQA)?"} answer={1} options={[{"text": "It improves accuracy over multi-head attention.", "why": "It's chosen for efficiency, at a small cost in quality, or about the same quality."}, {"text": "Several query heads share each key-value head, which shrinks the KV cache and the memory read per token.", "why": "With 32 query heads and 8 KV heads, the cache is 4× smaller."}, {"text": "It increases the context length.", "why": "It makes long contexts cheaper, but it doesn't change the maximum by itself."}, {"text": "It makes training faster.", "why": "The main benefit is at inference, through the cache."}]}>

In decode, every step reads the whole KV cache. **GQA** lets groups of query heads share one key-value head, so the cache and the bandwidth it needs shrink by the group factor. Multi-query attention (one KV head) is the extreme case and costs more quality.

**Follow-ups you'll get**

- **Can you convert a multi-head model to GQA?** Yes, by averaging the key and value heads in each group and then continuing training for a while (uptraining), as in the original GQA paper.

</Choice>

## Throughput, latency and batching

<Choice id={"srv-continuous-batching"} q={"With static batching, a batch of 16 requests finishes only when the longest answer finishes. What does continuous batching change?"} answer={0} options={[{"text": "Finished sequences leave the batch at every step and waiting requests join, so slots never sit idle.", "why": "It's scheduling at the token step, not at the request."}, {"text": "It processes requests one at a time.", "why": "That's the opposite: no batching at all."}, {"text": "It makes each forward pass faster.", "why": "A step costs about the same. More of each step's work is useful."}, {"text": "It compresses the KV cache.", "why": "That's a separate optimisation."}]}>

Output lengths vary widely. In static batching, a request that finishes early holds an empty slot until the longest one ends. **Continuous (in-flight) batching** schedules per decode step: it evicts finished sequences and inserts new ones straight away. Combined with paged KV caches, it's the main reason modern serving engines get several times more throughput from the same GPU.

**Follow-ups you'll get**

- **What's the cost?** More complex scheduling and memory management, and prefill for new requests competes with decode for existing ones, which is why engines offer chunked prefill.

</Choice>

<Choice id={"srv-ttft"} q={"Users say answers take a long time to *start*, but once text appears it streams quickly. Which metric is bad, and what are the usual fixes?"} answer={1} options={[{"text": "Throughput: add more GPUs.", "why": "More GPUs can help with queueing, but the specific symptom is the delay before the first token."}, {"text": "Time to first token (TTFT): reuse shared prompt prefixes, shorten prompts, and reduce queueing.", "why": "Streaming speed (time per output token) is fine here."}, {"text": "Time per output token: quantise the model.", "why": "That's the metric users say is fine."}, {"text": "Accuracy: fine-tune the model.", "why": "Quality isn't the complaint."}]}>

TTFT covers queueing plus prefill of the whole prompt. Long system prompts and retrieved context make prefill slow. Fixes: **prefix caching** (keep the KV cache of a shared system prompt and reuse it), trimming retrieved context, **chunked prefill** so long prompts don't block everyone, and enough capacity that requests don't queue. Report TTFT and time per output token separately. They have different causes.

**Follow-ups you'll get**

- **How would you measure where TTFT goes?** Log the queue wait, prefill time and prompt length per request, then plot TTFT against prompt length.

</Choice>

<Choice id={"srv-prefix-cache"} q={"Every request starts with the same 3,000-token system prompt. Which optimisation targets that directly?"} answer={1} options={[{"text": "Quantising the KV cache.", "why": "That saves memory but still recomputes the prefix every time."}, {"text": "Prefix (prompt) caching: compute the KV cache for the shared prefix once and reuse it.", "why": "Requests skip prefill for the shared part."}, {"text": "Speculative decoding.", "why": "That speeds up generating the output, not processing the prompt."}, {"text": "Increasing temperature.", "why": "Temperature changes sampling, not the cost."}]}>

Prefill for 3,000 identical tokens on every request is pure waste. **Prefix caching** stores the KV blocks for a common prefix and maps new requests onto them, cutting TTFT and compute. Many API providers bill cached input tokens at a discount for the same reason. Put the stable parts of the prompt first and the variable parts last, so the shared prefix stays as long as possible.

**Follow-ups you'll get**

- **What breaks prefix caching?** Anything that changes early tokens: a timestamp or user name at the top of the system prompt invalidates the cache for everything after it.

</Choice>

<Calc id={"srv-speculative"} q={"In speculative decoding, a small draft model proposes 4 tokens and the large model checks them in one pass. Each draft token is accepted with probability 0.8, independently, and checking stops at the first rejection. On average, how many tokens does each pass of the large model produce? (Two decimals.)"} answer={3.3616} tolerance={0.02} unit={"tokens"}>

The large model always produces at least one token (its own correction or continuation), plus each accepted draft token. The expected count is (1 − α^(k+1)) ÷ (1 − α) = (1 − 0.8⁵) ÷ 0.2 = **3.36** tokens per pass of the large model. Decode is memory-bound, so checking 4 tokens costs about the same as producing 1. That's where the speed-up comes from: about 3.4× fewer large-model passes, minus the draft model's own cost.

**Follow-ups you'll get**

- **When does speculative decoding not help?** When acceptance is low (the draft model predicts the large one poorly), or when the server is already compute-bound from large batches.
- **Does it change the output?** No. With the standard acceptance rule, outputs come from the large model's distribution exactly.

</Calc>

<Choice id={"srv-temp0"} q={"With temperature 0 in production, the same prompt sometimes gets slightly different answers. What's the usual explanation?"} answer={3} options={[{"text": "The model has a bug.", "why": "This happens with correct models and serving engines."}, {"text": "Temperature 0 still samples randomly.", "why": "At temperature 0, decoding takes the argmax, with no sampling."}, {"text": "The tokenizer is non-deterministic.", "why": "Tokenisation is deterministic."}, {"text": "Floating-point results depend on how requests are batched together, so tiny numerical differences can change which token wins a near-tie.", "why": "Batch composition changes the order of the GPU's reductions, and floating-point addition isn't associative."}]}>

Greedy decoding picks the highest-probability token, but the logits themselves vary by tiny amounts depending on **which other requests share the batch**, because kernel choice and reduction order change. When two tokens are nearly tied, that's enough to flip the choice, and the rest of the text diverges from there. Batch-invariant kernels can make serving fully deterministic, at some cost in speed.

**Follow-ups you'll get**

- **Why does this matter for evaluation?** A single run of an eval set is a sample. Run it more than once, or accept a margin, before calling a 1-point change real.

</Choice>

## Fine-tuning

<Choice id={"ft-rag-or-finetune"} q={"A support bot must answer from a policy manual that changes every week. Fine-tune, or use RAG?"} answer={3} options={[{"text": "Fine-tune once, then never update.", "why": "The bot would be out of date within a week."}, {"text": "Fine-tune every week on the new manual.", "why": "Expensive, slow to update, and fine-tuning is unreliable at teaching facts precisely."}, {"text": "Neither: write a longer system prompt with the whole manual.", "why": "That works for a short manual. Retrieval scales further and keeps prompts short."}, {"text": "RAG: put the current policy in the context at query time.", "why": "Knowledge that changes weekly belongs in retrieval, not in the weights."}]}>

Rule of thumb: **RAG for knowledge, fine-tuning for behaviour.** Retrieval keeps facts current and lets answers cite their source. Fine-tuning is good at teaching a format, a tone, a task-specific skill, or shortening prompts, and much less reliable at teaching facts. Many production systems use both: a lightly fine-tuned model that's good at answering from retrieved documents.

**Follow-ups you'll get**

- **When would you fine-tune here?** If the bot keeps ignoring the output format, or needs to follow a complex escalation procedure more reliably than prompting achieves.

</Choice>

<Choice id={"ft-lora-what"} q={"What does LoRA train?"} answer={2} options={[{"text": "All the weights, at a lower learning rate.", "why": "That's full fine-tuning."}, {"text": "Only the final classification layer.", "why": "That's linear probing or head-only training."}, {"text": "Two small low-rank matrices per adapted weight matrix. Their product is added to the frozen original weights.", "why": "W stays frozen, and only A and B (rank r) are trained."}, {"text": "A new set of embeddings for special tokens only.", "why": "That's closer to prompt tuning."}]}>

For a weight matrix W (d × d), LoRA learns B (d × r) and A (r × d) with r much smaller than d, and uses W + (α/r)·BA in the forward pass. Only A and B get gradients and optimiser state, so memory and checkpoint size drop sharply. The adapter can be merged into W after training, so inference costs nothing extra, or kept separate and swapped per customer.

**Follow-ups you'll get**

- **Which matrices do people usually adapt?** The attention projections, and increasingly the MLP projections too. Adapting more matrices usually helps quality more than raising the rank does.

</Choice>

<Calc id={"ft-lora-params"} q={"LoRA with rank 16 on one 4,096 × 4,096 projection matrix. How many trainable parameters does that add?"} answer={131072} tolerance={0.0}>

A is 16 × 4,096 and B is 4,096 × 16: 2 × 4,096 × 16 = **131,072** parameters, against 16,777,216 in the matrix itself.

**Follow-ups you'll get**

- **Why does such a small adapter work?** Fine-tuning updates tend to have low intrinsic rank: the change a task needs can be expressed in a few directions.

</Calc>

<Calc id={"ft-lora-pct"} q={"As a percentage of that matrix's 16,777,216 parameters, how many does the rank-16 adapter train? (Percent, three decimals.)"} answer={0.78125} tolerance={0.01} unit={"%"}>

131,072 ÷ 16,777,216 × 100 = **0.781%**. Across a whole model, LoRA typically trains 0.1–1% of the parameters. Optimiser state shrinks by the same factor, which is what makes a single-GPU fine-tune possible.

**Follow-ups you'll get**

- **Does fewer trainable parameters mean worse results?** For adapting style and task format, LoRA is usually close to full fine-tuning. For teaching a lot of new capability, full fine-tuning tends to win.

</Calc>

<Choice id={"ft-qlora"} q={"What does QLoRA add on top of LoRA?"} answer={3} options={[{"text": "It quantises the adapters to 4-bit.", "why": "The adapters stay in bf16 or fp16. Only the frozen base is 4-bit."}, {"text": "It removes the need for a GPU.", "why": "It reduces memory a lot, but training still needs a GPU."}, {"text": "It trains a smaller model and then distils it.", "why": "That's distillation, a different technique."}, {"text": "The frozen base model is stored in 4-bit, while the LoRA adapters train in higher precision.", "why": "The base model's memory drops about 4× compared with bf16."}]}>

QLoRA quantises the frozen base weights to 4-bit NormalFloat, dequantises them on the fly in the forward pass, and backpropagates into bf16 LoRA adapters. Paged optimisers handle memory spikes. A 7B model's base weights take about 3.5 GB instead of 14 GB, so fine-tuning fits on one consumer GPU.

**Follow-ups you'll get**

- **What's the trade-off?** Slower steps, from dequantising, and a small quality gap that's usually negligible for instruction tuning.

</Choice>

<Calc id={"ft-tokens"} q={"You fine-tune on 10,000 examples averaging 1,500 tokens each, for 3 epochs. How many training tokens is that, in millions?"} answer={45.0} tolerance={0.0} unit={"million tokens"}>

10,000 × 1,500 × 3 = 45,000,000 = **45 million** tokens. It's the number that sets both the cost (hosted fine-tuning is usually priced per training token) and the time (divide by your tokens per second).

**Follow-ups you'll get**

- **Is 3 epochs a good default?** For small curated datasets, 1–3 is typical. Watch held-out task performance, because more epochs on small data overfits quickly.

</Calc>

<Choice id={"ft-forgetting"} q={"After fine-tuning on 5,000 legal Q&A pairs, the model is great at legal questions but worse at general instructions and basic maths. What happened, and what helps?"} answer={2} options={[{"text": "Use a higher learning rate to finish faster.", "why": "Higher learning rates usually make forgetting worse."}, {"text": "The model was too small.", "why": "Larger models forget less, but the cause is the narrow training."}, {"text": "Catastrophic forgetting. Mix general instruction data back in, lower the learning rate or epochs, or use LoRA.", "why": "Narrow training pulls the weights away from what made the model generally capable."}, {"text": "The legal data must contain wrong maths.", "why": "It doesn't need to. Simply never seeing general tasks is enough."}]}>

Training only on one narrow distribution overwrites general behaviour. Mitigations: **replay** (mix in 10–30% general instruction data), a smaller learning rate and fewer epochs, parameter-efficient methods like LoRA, which change fewer weights, and an eval suite that includes general tasks, so you notice the regression before shipping.

**Follow-ups you'll get**

- **How would you detect it before launch?** Run a fixed general-capability eval before and after every fine-tune, alongside the task eval.

</Choice>

<Choice id={"ft-loss-vs-quality"} q={"Validation loss on your fine-tuning data keeps going down, but when people try the model, its answers are getting worse. What's the likely gap?"} answer={1} options={[{"text": "The tokenizer changed.", "why": "That would usually break loss too."}, {"text": "Validation loss scores the next token on reference answers, which isn't the same as the quality of the model's own generated answers. Evaluate on generated outputs.", "why": "Loss measures imitating the references token by token, not how good the model's own answers are."}, {"text": "The model needs more epochs.", "why": "More epochs would push the loss lower and may make generations worse still."}, {"text": "The validation set is too small.", "why": "Possible, but loss going down while generations get worse is a mismatch of metric, not only of sample size."}]}>

Validation loss uses teacher forcing: the model always sees the correct previous tokens. At inference it builds on its own outputs, and small errors compound. Lower loss can also come from learning the references' phrasing, without getting better at the task. Evaluate **generated** outputs on held-out prompts, with task metrics, human review, or a validated judge, and choose checkpoints by that.

**Follow-ups you'll get**

- **Which checkpoint do you ship?** The one with the best generated-output eval, which is often earlier than the lowest validation loss.

</Choice>

<Choice id={"ft-chat-template"} q={"A fine-tuned chat model works in your training notebook but produces rambling text when served. What do you check first?"} answer={0} options={[{"text": "That the server formats prompts with exactly the chat template and special tokens used in training.", "why": "A mismatched template is the most common cause of this."}, {"text": "The learning rate.", "why": "It works in the notebook, so training itself was probably fine."}, {"text": "The GPU type.", "why": "Hardware doesn't change the text like this."}, {"text": "Temperature.", "why": "Worth checking, but rambling that ignores turn structure points at the prompt format first."}]}>

Chat models learn a precise format: role markers, special tokens, and an end-of-turn token. If the server's template differs, even by a missing end-of-turn token or a different system-prompt marker, the model sees an unfamiliar format and doesn't know where its turn ends. Use the tokenizer's chat template in training and serving, and test the served endpoint with a prompt from the training set.

**Follow-ups you'll get**

- **What makes the model stop generating?** The end-of-turn or end-of-sequence token it was trained to produce. If serving doesn't treat that token as a stop, output runs on.

</Choice>

<Choice id={"ft-dpo"} q={"How does DPO differ from RLHF with PPO?"} answer={2} options={[{"text": "DPO only works for classification tasks.", "why": "It's used for aligning generative chat models."}, {"text": "DPO trains a bigger reward model.", "why": "DPO has no explicit reward model at all."}, {"text": "DPO learns directly from preference pairs with a classification-style loss, with no separate reward model and no reinforcement learning loop.", "why": "It optimises the same kind of preference objective in closed form."}, {"text": "DPO needs no preference data.", "why": "It needs pairs of preferred and rejected answers, the same data RLHF's reward model learns from."}]}>

RLHF with PPO trains a reward model on preference pairs, then optimises the policy with reinforcement learning against it, with a KL penalty to stay near the reference model: complex and finicky. **DPO** shows the same KL-constrained objective can be optimised directly, by raising the likelihood of the preferred answer relative to the rejected one (against the reference model). It's simpler and more stable, and widely used.

**Follow-ups you'll get**

- **What can go wrong with DPO?** It can overfit to the preference data and drift towards longer or more stylised answers. Watch length and held-out quality, and tune beta, which sets how far it can move from the reference.

</Choice>

<Choice id={"ft-data-quality"} q={"You can fine-tune on 1,000 examples carefully written by experts, or on 100,000 scraped Q&A pairs of mixed quality. For teaching an instruction-following style, which is usually better?"} answer={1} options={[{"text": "The 100,000 pairs, because more data always wins.", "why": "More data helps when it's good. Noisy examples teach noisy behaviour."}, {"text": "The 1,000 expert examples. For style and format, quality and consistency matter more than volume.", "why": "Small, carefully curated instruction sets have done surprisingly well (the LIMA result)."}, {"text": "Neither. Fine-tuning can't change style.", "why": "Changing style and format is what fine-tuning is best at."}, {"text": "Mix them equally.", "why": "Mixing in mostly-noisy data dilutes the good examples."}]}>

For alignment-style tuning, the model already has the knowledge from pre-training. Fine-tuning mostly teaches the format and the manners. A small set of consistent, high-quality examples does that well, while large noisy sets teach inconsistency and errors. For teaching a genuinely new skill, you need more data, and quality still matters.

**Follow-ups you'll get**

- **How would you clean the 100,000?** Deduplicate, filter with heuristics and a quality classifier or judge, check a random sample by hand, and keep only what you'd be happy for the model to imitate.

</Choice>
