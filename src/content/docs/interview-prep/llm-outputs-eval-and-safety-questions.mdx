## Structured Outputs & Constrained Decoding

<Choice id={"so-json-mode-vs-schema"} q={"Your extraction pipeline uses plain JSON mode, yet downstream code fails with KeyError on 4% of invoices. Why does switching to strict JSON Schema enforcement fix this?"} context={"Every API response is valid JSON, but required fields are missing or types drift from floats to strings. Throughput target is 10,000 invoices per hour."} sourceRoute={"/docs/llms-genai/prompt-engineering"} answer={1} options={[{"text": "Plain JSON mode validates syntax only after the response finishes generating.", "why": "JSON mode constrains or retries syntax, yet imposes no constraints on which keys or value types appear."}, {"text": "Strict JSON Schema compiles the schema into token masks at each decode step, whereas plain JSON mode enforces only generic JSON syntax.", "why": "Masking disallowed tokens prevents missing required keys and mismatched primitive types, though semantic values still need checks."}, {"text": "Strict JSON Schema fine-tunes the model weights on your field names.", "why": "Schema constraints act at decoding time via logit masking rather than updating any weights."}, {"text": "Plain JSON mode disables temperature sampling, causing dropped keys.", "why": "Temperature controls randomness; missing keys occur because any valid JSON object satisfies generic JSON syntax."}]}>

Strict JSON Schema compiles your field definitions into a finite-state grammar that masks illegal tokens at every decode step, whereas plain JSON mode checks only generic JSON syntax. Because any syntactically valid object satisfies plain JSON mode, an invoice extractor can emit `{"amount": "forty"}` or omit `tax_id`, crashing downstream `float()` casts with `KeyError` or `ValueError` even though `json.loads()` succeeds. Constrained schema decoding guarantees field presence and primitive types, trading first-request schema compilation latency and the risk that non-nullable fields force the model to guess values when source text omits them.

</Choice>

<QA id={"so-schema-shape-not-truth"} q={"A strict JSON Schema guarantees every field parses without error, yet analysts still find wrong numbers in 6% of extracted contracts. Why does schema enforcement not prevent this?"} context={"The contract extractor outputs `{total_usd: number, renewal_date: string, auto_renews: boolean}` with 100% schema conformance."} sourceRoute={"/docs/llms-genai/prompt-engineering"}>

Schema enforcement guarantees syntactic shape, not factual accuracy or grounding in the document. Constrained decoding tracks structural tokens (braces, quotes, key names, number characters) and masks illegal syntax transitions, while the model still chooses digits and strings freely from its learned probability distribution. When a contract omits a renewal date or lists only a monthly fee, a strict non-nullable schema forces the model to emit *some* string or float, leading to fabricated dates or copied subtotals inside valid JSON. Adding cross-field arithmetic checks, explicit nullable types, and required verbatim quote spans catches hallucinations at the cost of extra tokens and human-review routing.

</QA>

<Calc id={"so-token-overhead-calc"} q={"Constrained JSON decoding inserts 28 formatting tokens (braces, keys, quotes) per record alongside 12 content tokens. On 50,000 daily records at $4.00 per million output tokens, what is the monthly (30-day) output cost of the formatting tokens alone? (USD.)"} context={"Assume 30 days per month, zero retries, and flat per-token output billing for generated schema scaffolding."} sourceRoute={"/docs/llms-genai/calling-the-llm-api"} answer={168} tolerance={0.0} unit={"USD"}>

28 formatting tokens × 50,000 records/day × 30 days = 42,000,000 tokens = 42 million tokens, so 42 × $4.00 = **$168** per month for JSON scaffolding alone. Constrained decoding still steps every key, quote, and colon through the autoregressive decode loop (unless engine jump-forward skips deterministic literals), so bandwidth and output token billing apply to syntax just like prose. Deeply nested verbose keys like `extracted_customer_billing_street_address` across high-volume short records more than triple output spend and cut serving throughput. Using compact keys or flat TSV arrays trims token cost at the cost of weaker self-documentation in logs.

</Calc>

<Choice id={"so-truncation-max-tokens"} q={"A strict-schema extraction call suddenly returns `Unterminated string` in `json.loads` on 3% of long customer emails. The provider returned HTTP 200. What do you inspect first?"} context={"Average output is 180 tokens, `max_tokens` is set to 512, and failures cluster on emails with 15 or more line items."} sourceRoute={"/docs/llms-genai/calling-the-llm-api"} answer={2} options={[{"text": "Increase temperature so the model closes strings earlier.", "why": "Higher temperature adds randomness and tends to lengthen outputs, worsening truncation."}, {"text": "Switch from JSON Schema to XML tags.", "why": "XML hits the exact same hard token cap mid-tag when output exceeds 512 tokens."}, {"text": "Check `stop_reason` or `finish_reason` for `length` (`max_tokens`), because decoding stopped mid-JSON before the closing brace.", "why": "Constrained decoding restricts only the next token; it cannot force the object to close before the hard `max_tokens` cut-off."}, {"text": "Lower the JSON parser recursion limit.", "why": "Recursion depth raises `RecursionError`, not an unterminated string on flat line-item arrays."}]}>

Inspect `stop_reason` (or `finish_reason`) first: `length` or `max_tokens` indicates generation hit the 512-token ceiling mid-response. Grammar constraints ensure every prefix up to step *t* is a valid partial JSON string, yet a hard output limit aborts decoding before the finite-state machine reaches its accepting closing `}`. On emails with 18 line items, generation runs past token 512 inside item 14 and returns HTTP 200 with a cut-off JSON string. Raising `max_tokens` or paginating long inputs prevents silent truncation, at the cost of higher worst-case latency and KV-cache memory reservation per request.

</Choice>

<QA id={"so-few-shot-order-bias"} q={"Your structured ticket classifier gets 92% accuracy in staging, yet in production it assigns `billing_dispute` to 68% of unrelated tickets after you add four few-shot examples. What caused the skew?"} context={"The prompt ends with three `billing_dispute` examples and one `bug_report` example across four total shots, with strict enum output."} sourceRoute={"/docs/llms-genai/prompt-engineering"}>

Unbalanced few-shot label counts and recency bias shifted the model's prior toward `billing_dispute`. In-context learning conditions next-token probabilities on label frequencies and prompt order, giving repeated and final-position labels higher logits even before reading the ticket; strict enum decoding sharpens that bias by renormalizing probabilities exclusively over the allowed strings. Putting three `billing_dispute` shots at the end pulls borderline shipping or account tickets into `billing_dispute`, flooding escalation queues. Balancing classes evenly, ordering shots consistently, and adding explicit abstain examples restores calibration while adding slight prefix cost (amortized with prompt caching).

</QA>

<Calc id={"so-retry-cost-calc"} q={"An unconstrained extraction prompt passes Pydantic validation on 85% of first attempts, and each independent retry (up to 3 total attempts) also passes with probability 0.85. What percentage of requests still fail after 3 attempts? (Two decimals.)"} context={"Assume independent failures across retries triggered by validation errors at temperature 0.4."} sourceRoute={"/docs/mlops/ml-and-llm-testing"} answer={0.3375} tolerance={0.02} unit={"%"}>

Each attempt fails with probability 1 − 0.85 = 0.15, so failing all 3 independent attempts is 0.15³ = 0.003375 = **0.34%**. Validator-guided retries feed the Pydantic traceback back so the model can repair missing fields or bad types, cutting random formatting drops. In practice, failures caused by unreadable PDFs or contradictory source tables are correlated rather than independent, so three retries repeat the exact same invalid output and burn 3× latency and tokens without clearing the error. Constrained decoding eliminates syntax retries up front, whereas bounded semantic retries handle value rules at the cost of tail-latency spikes.

</Calc>

<Choice id={"so-fsm-throughput-debug"} q={"After enabling dynamic regex-constrained JSON schemas per user request on your vLLM cluster, p99 time-to-first-token spikes from 180 ms to 2.4 s while GPU utilization drops. What is the bottleneck?"} context={"Each request sends a slightly different JSON Schema generated dynamically from user table columns across a 40,000-token vocabulary."} sourceRoute={"/docs/mlops/llm-inference-engines"} answer={0} options={[{"text": "Compiling each unique JSON Schema into a vocabulary token-mask finite-state machine on CPU blocks the request before prefill and misses the FSM cache.", "why": "Intersecting a grammar with 40,000 vocabulary tokens per DFA state is CPU-bound whenever every request changes field names."}, {"text": "Structured decoding doubles the size of the KV cache per token.", "why": "KV-cache memory depends on layers, KV heads, and sequence length, not logit masking."}, {"text": "Constrained decoding disables continuous batching across all requests.", "why": "Serving engines still batch decode steps, though per-step bitmask application adds small overhead."}, {"text": "JSON Schema forces greedy decoding, which is slower than nucleus sampling.", "why": "Argmax is at least as fast as sampling; the delay here occurs before decoding starts."}]}>

CPU-side finite-state machine compilation and cache misses on unique schemas stall requests before GPU prefill begins. Constrained decoders intersect the schema grammar with the tokenizer's full vocabulary (40k–128k tokens) to build per-state token bitmasks; when every tenant sends distinct dynamic property names, the FSM cache misses and CPU construction starves GPU scheduling. A multi-tenant table-extraction tool generating bespoke schemas per upload triggers multi-second TTFT spikes under load. Normalizing to a small set of static parameterized schemas (such as key-value arrays) restores cache hits and fast TTFT at the cost of moving per-column type checks into post-decode validation.

</Choice>

<QA id={"so-cot-before-field-design"} q={"Your structured output schema forces the model to emit `decision` (`approve` or `reject`) as the first JSON key, and accuracy on complex claims drops 11 points compared to free text. How do you redesign the schema?"} context={"Claims require verifying three policy clauses before deciding, and downstream callers require strict JSON."} sourceRoute={"/docs/llms-genai/prompt-engineering"}>

Place structured `clause_checks` or `reasoning_steps` fields before `decision` in the JSON schema and enforce key order. Autoregressive models decode left-to-right, conditioning each token only on earlier tokens; emitting `decision` first forces the model to commit to `"approve"` or `"reject"` in one forward pass before checking the three clauses, then rationalize that choice in subsequent keys. On borderline claims, locking `decision` early causes an 11-point accuracy drop as the model invents matching clause explanations afterward. Putting evidence fields first lets attention compute the verdict from explicit checks, trading extra output tokens and higher latency for better accuracy.

</QA>

<Calc id={"so-logit-bias-ceiling-calc"} q={"A structured extractor uses jump-forward grammar decoding: an average JSON output has 60 tokens total, of which 24 deterministic boilerplate tokens skip GPU decode passes, and 36 tokens take 18 ms/token on GPU. Including a fixed 90 ms prefill and 15 ms schema lookup, what is the end-to-end latency in ms?"} context={"Assume skipped literal tokens add negligible CPU time and the GPU decodes one variable token per 18 ms pass."} sourceRoute={"/docs/llms-genai/evaluation-and-serving"} answer={753} tolerance={0.0} unit={"ms"}>

End-to-end latency is 90 ms prefill + 15 ms lookup + (36 variable tokens × 18 ms/token = 648 ms) = **753 ms**, down from 90 + (60 × 18) = 1,170 ms without jump-forward compression. When a finite-state grammar transition allows only a single literal sequence (fixed key names, colons, quotes), serving engines append all deterministic tokens at once into the KV cache rather than paying memory-bandwidth-bound decode passes per token. Allowing optional whitespace or flexible key aliases introduces ambiguity that disables jump-forward skipping and restores the full 1,170 ms delay. Rigid key ordering maximizes speedup at the cost of engine coupling and strict prompt templates.

</Calc>

<QA id={"so-tool-vs-response-format-debug"} q={"You enforce strict JSON output via `response_format` on a chat model that also has two callable tools. Suddenly the model stops invoking tools and prints tool-call JSON inside the user-facing response. Why, and how do you fix it?"} context={"The model must look up customer account status via `get_account` before emitting the final `{status, summary}` JSON object."} sourceRoute={"/docs/agents/agent-fundamentals"}>

The global `response_format` grammar masked out the model's special tool-call tokens (`<tool_use>` or function role transitions), trapping every assistant turn inside the final JSON schema. When the finite-state mask forces output to start with `{` for `{status, summary}`, the model cannot emit the tool-invocation delimiter and instead serializes `"call get_account"` as plain JSON values, breaking downstream parsers with no lookup executed. Decoupling intermediate tool turns from final formatting—allowing tool calls freely during the loop and applying `response_format` only on the terminal pass, or defining `submit_final_answer` itself as a required tool—fixes the conflict at the cost of one explicit termination step.

</QA>

<QA id={"so-nullable-optional-design"} q={"Design a strict-schema clinical entity extractor for messy doctor notes where 40% of fields are genuinely absent in any given note, without inducing fabricated defaults."} context={"Downstream billing code rejects unparseable JSON and treats false-positive diagnoses as patient-safety incidents."} sourceRoute={"/docs/mlops/ml-and-llm-testing"}>

Make optional fields explicitly nullable (for example `["string", "null"]` or an enum containing `"not_documented"`), require a `source_quote` span alongside every extracted entity, and verify quotes deterministically against the note. Without `null`, strict schemas force the grammar decoder to choose some non-empty token when evidence is absent, turning missing clinical facts into plausible-looking fabricated diagnoses (`"Penicillin"` allergies or invented dates). Adding nullable schemas gives the model a low-loss escape path, while checking that `source_quote` is a literal substring of the input catches remaining hallucinations before billing runs. The trade-off is ~35% more output tokens and routing unmatched quotes to human review.

</QA>

<QA id={"so-streaming-partial-json-design"} q={"Design a real-time UI that streams structured JSON fields (`title`, `bullets`, `confidence`) to users under 300 ms TTFT while guaranteeing final schema validity and preventing partial-field XSS."} context={"Outputs average 450 tokens; the UI renders `title` and `bullets` progressively as tokens arrive."} sourceRoute={"/docs/llms-genai/calling-the-llm-api"}>

Pair server-side strict JSON Schema decoding with a state-aware streaming parser that auto-closes unclosed brackets locally for display previews while gating rendering and side effects per completed field. Strict decoding guarantees the complete output conforms to schema, while incremental parsing lets the client display `title` within 300 ms instead of buffering 450 tokens for 5 seconds; meanwhile, action-critical fields like `confidence` wait for their closing delimiter before triggering logic. Rendering raw partial strings mid-escape (`\"`) or before HTML sanitization leaks unescaped `<script>` payloads or breaks layouts when aborted mid-stream. Progressive field buffering cuts perceived latency at the cost of waiting until `stop_reason === "end_turn"` before persisting records.

</QA>

## Reference Scoring: Exact, Lexical & Semantic

<Choice id={"rs-bleu-rouge-trap"} q={"Against the reference \"Refunds arrive within 5 business days\", Model A outputs \"Money is returned in five working days\" and Model B outputs \"Refunds arrive within 30 business days\". Why do BLEU and ROUGE-L score Model B far higher?"} context={"Model A is factually accurate using synonyms; Model B changes 5 to 30, multiplying the refund delay by six."} sourceRoute={"/docs/mlops/llm-evaluation-and-ragops"} answer={3} options={[{"text": "BLEU and ROUGE penalize numbers written out in words.", "why": "Both treat all tokens as plain surface strings with no numeric semantics."}, {"text": "Model A is longer, and ROUGE penalizes longer outputs exponentially.", "why": "ROUGE-L computes precision-recall F1 over longest common subsequence; Model A simply shares few literal words."}, {"text": "BLEU uses dense embeddings that ignore digits.", "why": "BLEU computes clipped n-gram precision over exact string matches, without embeddings."}, {"text": "BLEU and ROUGE measure literal surface n-gram overlap, so one wrong digit inside copied phrasing outscores an accurate paraphrase.", "why": "Model B matches nearly every n-gram except a single digit, while Model A rewords almost the entire sentence."}]}>

BLEU (clipped n-gram precision) and ROUGE-L (longest common subsequence) measure literal token overlap rather than semantic equivalence. Because they ignore meaning, Model B keeps nearly every unigram, bigram, and trigram of the reference despite changing `5` to `30`, whereas Model A (`Money`, `returned`, `five`, `working`) shares almost zero surface tokens. In practice, a wrong `30 business days` reply can score over 75 BLEU / 0.90 ROUGE-L while a right paraphrase scores under 5 BLEU / 0.20 ROUGE-L, promoting a policy regression. Lexical scores are cheap and reproducible for drift checks or verbatim extraction, at the cost of missing paraphrases and critical single-token factual flips.

</Choice>

<QA id={"rs-exact-match-normalization"} q={"Your QA evaluator uses raw string equality (`pred == ref`) and reports 41% accuracy on a model that human raters score at 78%. What normalization bugs cause this gap, and where can normalization go too far?"} context={"Questions ask for dates, dollar amounts, and short entity names (`\"Dr. Alice Smith.\"` versus `\"Alice Smith\"`)."} sourceRoute={"/docs/mlops/llm-evaluation-and-ragops"}>

Raw `pred == ref` penalizes harmless formatting variations—casing, trailing punctuation, whitespace, articles, Markdown bolding, and numeric commas (`$1,200` vs `1200`). Standard QA Exact Match normalizes both strings (lowercasing, stripping outer punctuation and articles, converting number words or date formats into typed values) before matching. Without it, `"The answer is **42**."` scores 0 against `"42"`, hiding 37 points of real capability; conversely, blindly stripping all punctuation or negations collapses `"-5"` into `"5"` or `"not guilty"` into `"guilty"`, creating silent false passes. Typed parsers paired with restrained text cleanup avoid formatting false negatives without erasing polarity, at the cost of maintaining per-type normalizers.

</QA>

<Calc id={"rs-pass-at-k-calc"} q={"Using the unbiased `pass@k` estimator `1 - comb(n - c, k) / comb(n, k)`, you draw n = 10 samples for a coding task and c = 2 pass all unit tests. What is `pass@3`? (Three decimals.)"} context={"Use the finite-sample hypergeometric estimator rather than the biased `1 - (1 - c/n)^k` formula."} sourceRoute={"/docs/mlops/ml-and-llm-testing"} answer={0.5333333333333333} tolerance={0.01}>

With *n* = 10 total samples, *c* = 2 passing samples, and *k* = 3, the number of 3-sample subsets containing zero passing completions is C(8, 3) = 56 out of C(10, 3) = 120 subsets, so pass@3 = 1 − (56 ÷ 120) = 64 ÷ 120 = **0.533**. Drawing *n* greater than *k* and using combinations without replacement yields a low-variance, unbiased estimate. Using the naive plug-in `1 − (1 − 0.2)³ = 0.488` underestimates true `pass@3` by 4.5 points, while misreading `pass@3 = 53%` as single-shot user reliability (`pass@1 = 20%`) ships a brittle assistant. Increasing *n* lowers variance at *n*× sampling cost.

</Calc>

<Choice id={"rs-semantic-negation-bug"} q={"You switch from ROUGE to dense embedding cosine similarity (and BERTScore) to score support answers. Now \"Your warranty does NOT cover water damage\" scores 0.94 against \"Your warranty covers water damage.\" Why?"} context={"Both sentences use the same domain terms and phrasing, differing only by negation."} sourceRoute={"/docs/mlops/llm-evaluation-and-ragops"} answer={0} options={[{"text": "Contextual embeddings and BERTScore match topical word distributions closely, so single-token negations or antonym flips barely lower similarity.", "why": "Sentences about the exact same topic occupy nearly identical vector regions even when truth polarity flips."}, {"text": "Cosine similarity was computed without normalizing vector lengths.", "why": "Cosine similarity divides by L2 norms automatically, and dot products share the same topical overlap issue."}, {"text": "BERTScore strips stop words like \"not\" during tokenization.", "why": "BERTScore embeds every token, yet averaging across 7 matching content tokens drowns out one negated token."}, {"text": "The reference string was truncated before encoding.", "why": "A 7-word sentence fits easily inside any encoder's context window."}]}>

Dense similarity and BERTScore cluster text by topic rather than logical entailment or polarity. BERTScore greedily pairs contextual token embeddings and averages cosine similarity, while sentence encoders pool all token vectors; flipping `"covers"` to `"does NOT cover"` leaves most topical content unchanged, keeping cosine scores near 0.94. In policy, medical, or legal QA, pure embedding scoring cheerfully passes opposite advice (`"take two pills"` vs `"never take two pills"`). Semantic similarity solves synonym paraphrasing cheaply without an LLM judge, at the cost of missing contradictions—requiring NLI entailment checks or claim-level rubrics whenever polarity is safety-critical.

</Choice>

<QA id={"rs-auc-ties-concept"} q={"When computing ROC-AUC as a pairwise ranking probability over a model outputting quantized buckets (`0.1`, `0.5`, `0.9`), how must tied positive-negative scores be scored, and what fails if ties are broken by row order?"} context={"A scorer assigns 3 discrete levels across 10,000 examples, producing thousands of positive-negative ties."} sourceRoute={"/docs/machine-learning/model-evaluation-metrics"}>

Exact ties between a positive and a negative example must receive 0.5 credit in the pairwise sum, matching the diagonal segment of the trapezoidal ROC curve. Mathematically, ROC-AUC equals `P(score_pos > score_neg) + 0.5 × P(score_pos == score_neg)`, guaranteeing a constant classifier predicting `0.5` for every input scores exactly 0.50. If a custom evaluator sorts rows without tie correction on a dataset ordered with positives before negatives, ties receive 1.0 credit and a useless constant model can score 1.0 AUC, falsely passing CI gates. Proper tie handling ensures honest ranking comparison, though heavy bucket quantization still obscures probability calibration and top-k precision under class imbalance (where PR-AUC is sharper).

</QA>

<Calc id={"rs-bleu-brevity-penalty-calc"} q={"A translation candidate has c = 6 words against a reference of r = 12 words, achieving geometric mean n-gram precision 0.80. Using BLEU's brevity penalty `exp(1 - r/c)` for `c < r`, what is the final BLEU score (0 to 1 scale)? (Three decimals.)"} context={"Compute `BLEU = BP × 0.80`, where `exp(-1) ≈ 0.3679`."} sourceRoute={"/docs/mlops/llm-evaluation-and-ragops"} answer={0.2943035529371539} tolerance={0.02}>

Because candidate length *c* = 6 is shorter than reference *r* = 12, the brevity penalty is BP = exp(1 − 12 ÷ 6) = exp(−1) ≈ 0.3679, giving BLEU = 0.3679 × 0.80 = **0.294** (29.4 on a 0–100 scale). Because BLEU measures n-gram precision (matched n-grams divided by candidate length) rather than recall, emitting a single common word like `"the"` would get 1.0 precision without BP; the exponential penalty suppresses clipped fragments. Over-aggressive `max_tokens` caps or terse system prompts cut candidate length below references and halve BLEU even on accurate answers. BLEU prevents length-truncation gaming without computing recall, at the cost of punishing legitimately concise summaries.

</Calc>

<Calc id={"rs-auc-pairwise-calc"} q={"An eval scorer assigns scores `0.8` and `0.5` to two positive items, and `0.7`, `0.5`, `0.2` to three negative items. Counting ties as 0.5, what is the exact ROC-AUC?"} context={"Evaluate all 2 × 3 = 6 positive-negative pairs using Mann-Whitney pairwise probability."} sourceRoute={"/docs/machine-learning/model-evaluation-metrics"} answer={0.75} tolerance={0.01}>

Across all 2 × 3 = 6 positive-negative pairs: positive `0.8` outranks all 3 negatives (3.0 points), while positive `0.5` loses to `0.7` (0), ties with `0.5` (0.5), and beats `0.2` (1.0), totaling 4.5 ÷ 6 = **0.75**. ROC-AUC directly measures the probability a randomly sampled positive ranks above a randomly sampled negative, making it invariant to monotonic rescaling of probabilities. When models output coarse quantized scores or binary labels, excessive ties pull ROC-AUC downward and mask fine ranking differences. Pairwise ROC-AUC avoids arbitrary threshold selection, at the cost of ignoring probability calibration and underweighting false alarms when positives are rare.

</Calc>

<Choice id={"rs-rouge-tokenizer-mismatch-debug"} q={"Your RAG summarization score drops from 0.44 ROUGE-L to 0.19 overnight after a model swap, even though human reviewers rate the new summaries slightly better. Neither the reference set nor the prompt changed. What do you inspect?"} context={"The new model wraps key terms in Markdown bolding and Unicode punctuation while the scoring helper splits on plain spaces."} sourceRoute={"/docs/ai-evaluation/evaluation-fundamentals"} answer={1} options={[{"text": "Human reviewers suffer from length bias and missed a real factual collapse.", "why": "A 25-point ROUGE drop paired with higher human quality scores signals a surface mismatch, not sudden factual collapse."}, {"text": "Formatting or tokenizer mismatch (Markdown asterisks, smart quotes, or whitespace splitting) broke literal token matching against plain references.", "why": "ROUGE compares tokenized strings verbatim; `**refund**` fails to match `refund` if Markdown isn't stripped cleanly."}, {"text": "The reference summaries leaked into pretraining of the new model.", "why": "Benchmark contamination inflates overlap metrics rather than crashing them by 25 points."}, {"text": "ROUGE-L compares cryptographic hashes of paragraphs.", "why": "ROUGE-L computes longest common token subsequences, not hashes."}]}>

Inspect the scorer's text normalization and tokenization first: Markdown formatting (`**5 days**`), smart quotes, Unicode differences, or whitespace splitting break literal n-gram matching. Standard `rouge_score` uses a specific regex tokenizer and Porter stemmer, whereas naive `.split()` leaves punctuation attached so `"days."` fails to match `"days"` and `"**refund**"` misses `"refund"`. Swapping to a model that outputs clean Markdown bullets silently collapses unnormalized ROUGE-L from 0.44 to 0.19 and triggers false CI rollbacks. Locking a consistent pre-stripper and tokenizer keeps scores comparable over time, at the cost of ignoring intentional Markdown formatting bugs unless schema checks test formatting separately.

</Choice>

<QA id={"rs-exec-vs-lexical-code-eval"} q={"Why did code-generation benchmarks abandon BLEU and CodeBLEU as primary pass metrics in favor of execution-based `pass@k`, and when can execution scoring itself mislead?"} context={"Tasks generate 30-line Python functions graded against hidden unit tests inside a sandbox."} sourceRoute={"/docs/mlops/ml-and-llm-testing"}>

Execution grading tests functional equivalence across any valid algorithm, whereas BLEU and CodeBLEU penalize valid variable renames, helper functions, or iterative vs recursive rewrites that differ lexically from a single reference. Running candidate code inside a sandbox against unit tests verifies true input-output behavior. CodeBLEU can score 0.85 on code with a flipped `<` comparator that fails every boundary case while scoring 0.35 on a working clean rewrite; conversely, weak execution suites mislead when models hardcode visible examples or skip untested edge cases (empty inputs, concurrency, SQL injection). Execution `pass@k` reflects real software correctness at the cost of sandbox infra, slower CI runs, and needing property/adversarial tests.

</QA>

<QA id={"rs-passk-vs-passhatk-debug"} q={"Your coding agent boasts `pass@5 = 88%` on an internal SQL benchmark, yet production users see correct queries on under half of first runs and frequent retries. What scoring fallacy hid this problem?"} context={"Benchmark evaluation generates 5 independent samples at temperature 0.7 and marks a task solved if any 1 of 5 passes."} sourceRoute={"/docs/agents/agent-fundamentals"}>

Evaluating best-of-5 potential (`pass@5`) instead of single-shot accuracy (`pass@1`) or multi-run consistency (`pass^k`) masked a ~35% first-try pass rate behind five samples. Under independent sampling with per-try probability *p*, `pass@5 = 1 − (1 − p)⁵ = 0.88` implies `p ≈ 0.346`, meaning two out of three initial queries fail—and requiring reliability across 5 consecutive runs (`pass^5 = p⁵`) drops under 0.5%. Production users pay 4× wasted tokens and latency or abandon after the first broken SQL query rather than sampling five times. Reporting `pass@1` alongside `pass@k` and `pass^k` exposes variance versus peak capability at the cost of running multi-trial CI suites.

</QA>

<QA id={"rs-hybrid-eval-pipeline-design"} q={"Design a reference-scoring pipeline for medical-record summarization where missing a medication dose is critical, phrasing varies widely, and 2,000 test cases must run nightly in CI under $15."} context={"Each summary includes a structured medication list plus a 150-word clinical narrative with ground-truth chart notes."} sourceRoute={"/docs/ai-evaluation/llm-rag-agent-evaluation"}>

Tier deterministic entity checks ahead of targeted NLI and selective LLM-as-judge scoring rather than running ROUGE alone or judging every word with a frontier model. First, parse drugs, doses, and allergies from reference and candidate summaries into normalized records to compute exact precision/recall at zero API cost and zero negation blindness. Second, run fast local NLI entailment over narrative claims against source notes to flag contradictions or unsupported additions. Third, route only flagged or stratified sample subsets to a calibrated LLM rubric judge, keeping 2,000 nightly cases under $15. Relying on ROUGE misses `"50 mg"` vs `"500 mg"`, while judging everything breaks budget and adds variance. Tiering balances safety recall and cost while requiring maintenance of entity extractors.

</QA>

Small NLI models score `"neutral"` when an answer combines facts across two separate chunks or derives simple arithmetic (`"March + 30 days"`), causing hard blocks when evaluated chunk-by-chunk. Evaluating claims against the concatenated retrieved context, separating verifiable factual claims (amounts, dates, names) from connective prose, and switching uncertain claims from full deletion to inline source citations or soft caution tags recovers the lost 22% utility. Hard-blocking every NLI neutral score destroys helpfulness, while soft-flagging plus citation checks trades minor unverified prose risk for reliable user answers.

</QA>

<QA id={"gr-async-vs-sync-guardrail-design"} q={"Design a guardrail pipeline for a high-throughput enterprise assistant with a strict 150 ms guardrail latency budget, where full LLM-as-judge checks take 700 ms synchronously."} context={"Traffic is 1,000 QPS; 35% of queries are benign FAQs, while 5% trigger sensitive write tools."} sourceRoute={"/docs/mlops/production-reliability"}>

Split guardrails into a sub-150 ms synchronous fast-path and conditional/asynchronous deep evaluation reserved for uncertain or high-risk requests. On every request, run parallel checks under 40 ms: text normalization, deterministic regex/allowlist rules, and lightweight quantized encoder classifiers (safety + PII NER). Invoke the 700 ms deep judge synchronously *only* when the fast classifier scores in an ambiguous band or before the 5% of requests executing sensitive write tools; run deep hallucination/compliance judges asynchronously on sampled read-only logs to drive alerts and daily threshold updates. Running a 700 ms judge synchronously on all 1,000 QPS breaches every latency SLO and doubles GPU cost, while tiered gating hits budget on 95% of traffic at the cost of post-hoc detection on subtle read-only misses.

</QA>

<QA id={"gr-multi-turn-escalation-design"} q={"Red-teamers bypass your single-turn input guardrail by spreading a prohibited request across six innocent-looking conversation turns. How do you design stateful guardrails without blowing latency or context limits?"} context={"Conversations reach 30 turns; current filters inspect only the newest user message."} sourceRoute={"/docs/ai-security/ai-red-teaming"}>

Evaluate a compact rolling conversation risk state alongside recent turns instead of scanning only `messages[-1]` or feeding full 30-turn logs into heavy classifiers on every request. Store per-session state containing a cumulative risk score (with slow decay), count of prior borderline flags, and a concise 150-token rolling intent summary updated asynchronously; on each turn, classify `[intent_summary + last 2-3 turns]` inside ~250 tokens, and inspect accumulated model outputs too since partial earlier compliance weakens later refusals. Scanning only the newest message lets turn 6 (`"Now adapt those steps for target X"`) slip past innocently after turns 1–5 built the scaffold. Stateful rolling risk triggers progressive friction (disabling tools before hard blocking), trading minimal session state for multi-turn defense without locking out long benign chats.

</QA>
