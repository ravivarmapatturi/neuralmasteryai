# Model Catalog & Benchmarking Framework

Choosing a model for a system is a recurring decision this site's content can't make *for* you with a fixed answer — specific models and their benchmark scores change every few months, often faster than any static page can track responsibly. What stays durable is the **framework**: which categories of model exist, which attributes actually matter for choosing between them, and which benchmark dimensions matter for each type of system. This page is that framework — deliberately a methodology, not a snapshot leaderboard that would be stale within a quarter of being written.

## The Model Card Attribute Checklist

When evaluating *any* model against this checklist, whatever its category — the same attribute set the [Model Cards](/docs/mlops/legal-licensing-and-governance#model-cards-and-data-cards) standard formalizes:

- **Architecture**: what family it belongs to (decoder-only, encoder-decoder, diffusion, etc.) — see [Attention & Transformers](/docs/deep-learning/attention-transformers) and [Generative Models](/docs/deep-learning/generative-models) for the architectural vocabulary.
- **Parameters**: total and (for MoE models, see [Foundation Model Internals — MoE](/docs/llms-genai/foundation-model-internals#mixture-of-experts-moe)) active parameter count — active parameters, not total, determine per-token inference compute cost.

<ActiveVsTotalParamsDiagram />
- **Context length**: maximum sequence length supported — directly bounds [KV cache memory](/docs/mlops/llm-inference-optimization#kv-cache) requirements at serving time.
- **Modalities**: what input/output types the model actually supports (text-only, text+image-in, text+image+audio, etc.).
- **Training data and recency**: what it was trained on, and its effective knowledge cutoff — directly relevant to the [RAG vs. fine-tuning](/docs/interview-prep/technology-comparisons#rag-vs-fine-tuning) decision.
- **License**: see [Legal, Licensing & Governance — Model Licenses](/docs/mlops/legal-licensing-and-governance#model-licenses) — check the actual current terms before commercial use, every time, since terms have changed between versions of the same model family.
- **Benchmark scores**: reported scores on standard benchmarks — read alongside [AI Evaluation — Benchmark Design](/docs/ai-evaluation/evaluation-fundamentals#benchmark-design)'s contamination/saturation cautions before trusting a number at face value.
- **Hardware requirements**: VRAM needed to serve at a given precision — see [LLM Inference Optimization — GGUF Ecosystem](/docs/mlops/llm-inference-optimization#the-gguf-ecosystem) for concrete size-math worked examples.
- **Inference support**: which engines support it (see [LLM Inference Engines](/docs/mlops/llm-inference-engines)) — a model with narrow engine support is a real operational constraint, not just a technical footnote.
- **Fine-tuning support**: whether LoRA/QLoRA tooling has mature support for the architecture — see [Training Pipeline — PEFT](/docs/llms-genai/training-pipeline#parameter-efficient-fine-tuning-peft).
- **Quantization support**: whether pre-quantized versions (GGUF, AWQ, GPTQ) are readily available, or quantization has to be done in-house.
- **Use cases**: what the model card/provider explicitly states it's suited (and *not* suited) for — the out-of-scope-uses section is often more informative than the intended-use section.

## Freeze the workload before benchmarking

A benchmark is a comparison only when every candidate performs the same job. Changing prompt length, output length, concurrency, precision, hardware, or warm-up changes the bottleneck. A model can appear faster simply because it received shorter prompts or ran with fewer simultaneous requests.

Write a **workload plan** before running either candidate. It fixes the following fields and makes the result reproducible:

| Field | Record before the run | Why it changes the result |
| --- | --- | --- |
| Model | id, revision, tokenizer, serving engine | A moving model or engine is a different system |
| Precision | weight, activation, and KV-cache dtypes | Memory traffic, capacity, and quality change |
| Lengths | measured input and requested output-token distributions | Prefill and decode stress different resources |
| Load | concurrency or arrival-rate schedule | Queueing changes latency and throughput |
| Warm-up | discarded requests or duration | First-run compilation and cache fills distort results |
| Repeats | requests per cell and random seed | Small runs hide tail events |
| Percentiles | p50, p95, and p99 for TTFT, TPOT, and end-to-end latency | A mean hides user-visible stalls |
| Hardware | accelerator, count, memory, interconnect, CPU, and software versions | Results do not transfer across machines unchanged |
| Units | requests/s, output tokens/s, milliseconds, GiB, and cost/request | Ambiguous “tokens/s” can mean incompatible quantities |

The planner below treats the workload as data, validates the fields that people most often omit, and emits a decision record. Its candidate results are explicitly illustrative; replace them with measurements from one controlled run. The final line records what evidence would overturn the choice, so the decision can be revisited instead of becoming folklore.

<RunnableCode code={`plan = {
    'model_revision': 'candidate revision pinned by digest',
    'precision': 'int8 weights, bf16 activations, bf16 KV cache',
    'input_tokens': [128, 2048],
    'output_tokens': [128, 512],
    'concurrency': [1, 16, 64],
    'warmup_requests': 20,
    'repeats_per_cell': 50,
    'percentiles': [50, 95, 99],
    'hardware': '1 accelerator; exact SKU, memory, driver recorded with run',
    'units': ['ms TTFT', 'ms TPOT', 'requests/s', 'output tokens/s', 'GiB', 'cost/request'],
}

required = set(plan)
expected = {'model_revision', 'precision', 'input_tokens', 'output_tokens',
            'concurrency', 'warmup_requests', 'repeats_per_cell',
            'percentiles', 'hardware', 'units'}
assert required == expected and plan['warmup_requests'] > 0
cells = len(plan['input_tokens']) * len(plan['output_tokens']) * len(plan['concurrency'])
print(f'workload cells: {cells}; measured requests: {cells * plan["repeats_per_cell"]}')

# Illustrative results from the SAME workload plan; replace with measured data.
results = {
    'small-int8': {'quality': 0.87, 'p95_ttft_ms': 410, 'p95_tpot_ms': 22, 'cost': 0.18},
    'large-fp16': {'quality': 0.91, 'p95_ttft_ms': 790, 'p95_tpot_ms': 38, 'cost': 0.44},
}
limits = {'quality': 0.88, 'p95_ttft_ms': 800, 'p95_tpot_ms': 40, 'cost': 0.50}

def passes(row):
    return (row['quality'] >= limits['quality'] and
            row['p95_ttft_ms'] <= limits['p95_ttft_ms'] and
            row['p95_tpot_ms'] <= limits['p95_tpot_ms'] and row['cost'] <= limits['cost'])

eligible = [name for name, row in results.items() if passes(row)]
decision = min(eligible, key=lambda name: results[name]['cost'])
print('decision:', decision, '- cheapest candidate that passes every gate')
print('overturn if: small-int8 quality reaches 0.88, or large-fp16 exceeds 800 ms TTFT, 40 ms TPOT, or $0.50/request')

# Try it: raise small-int8 quality to 0.89. It passes every gate and becomes
# the decision because its illustrative cost/request is lower.`} />

Store the plan, raw request-level results, summary script, decision, date, and owner together. Do not compare a provider's advertised token rate with your measured goodput; units and load shape differ. Re-run when the model revision, serving engine, hardware, traffic distribution, or acceptance threshold changes.

## How to Use This Page

When choosing a model for a real system: pull the current, specific candidates from primary sources (the model provider's own documentation, the inference engine's supported-models list, current leaderboards — treated with the [benchmark design](/docs/ai-evaluation/evaluation-fundamentals#benchmark-design) skepticism this site teaches, not at face value) and evaluate them against the attribute checklist and benchmark dimensions above. The checklist and dimensions are what stay true regardless of which specific models exist when you're reading this — that durability is the point.
