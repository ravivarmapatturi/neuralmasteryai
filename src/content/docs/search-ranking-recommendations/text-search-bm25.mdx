# Text Search & Inverted Indexes

<ELI5>
Imagine looking up recipes in the back index of a 1,000-page cookbook. Instead of reading every page from front to back to see if it contains the word "vanilla", you turn straight to the letter V, locate "vanilla", and look at the list of recipe page numbers printed beside it. If you search for "vanilla AND sugar", you take the page list for vanilla and the page list for sugar and keep only the page numbers that appear on both lists. An inverted index does the exact same thing for computer search.
</ELI5>

## Why Lexical Retrieval Matters

Dense neural embeddings and semantic vector models excel at capturing broad concepts, but they frequently fail when exact precision matters: error codes (`ERR_CONNECTION_REFUSED`), SKU model numbers (`WH-1000XM5`), medical identifiers (CPT, ICD-10), and proper nouns. If a user searches for an exact five-digit flight code, semantic models often retrieve flights with similar destinations rather than the literal identifier.

Lexical retrieval solves this by evaluating exact string tokens. Rather than embedding documents into dense continuous vectors, lexical systems index the exact vocabulary. The central engineering challenge of lexical search is twofold:
1. **Finding candidate documents in sub-millisecond time** without scanning millions of document text files sequentially.
2. **Structuring terms and postings efficiently** so that multi-term Boolean filters execute via fast list operations.

The foundation of production search engines—powering Apache Lucene, Elasticsearch, OpenSearch, and Vespa—is the **Inverted Index**.

## The Text Normalization Pipeline

Before text can be indexed or searched, raw document strings pass through a deterministic text normalization pipeline:

```
[Raw Document Text]
        │
        ▼ (Stage 1: Tokenization)
["Search,", "ranking", "&", "recs!"]
        │
        ▼ (Stage 2: Case Normalization)
["search,", "ranking", "&", "recs!"]
        │
        ▼ (Stage 3: Punctuation & Character Filtering)
["search", "ranking", "recs"]
        │
        ▼ (Stage 4: Stemming / Lemmatization)
["search", "rank", "rec"]
```

1. **Tokenization**: Splitting continuous character streams into discrete term tokens (e.g. `"Search, ranking & recs"` $\to$ `["search,", "ranking", "&", "recs!"]`). Language-specific rules handle hyphenated words, URLs, and compound nouns.
2. **Case Normalization (Case Folding)**: Converting all tokens to lowercase so that `"Search"`, `"SEARCH"`, and `"search"` map to the same dictionary entry.
3. **Punctuation & Stop-Word Filtering**: Stripping symbols and optionally removing high-frequency grammatical glue words (`"the"`, `"and"`, `"of"`). In modern engines, stop-words are frequently retained to support exact phrase matching (`"to be or not to be"`), but down-weighted during scoring.
4. **Stemming or Lemmatization**: Reducing inflected word variants to a base root (e.g. `"ranking"`, `"ranked"`, and `"ranks"` $\to$ `"rank"` via the algorithmic Porter or Snowball stemmer; lemmatization uses morphological vocabularies to map `"better"` $\to$ `"good"`).

## Forward Index vs. Inverted Index

A traditional **forward index** stores documents and lists the words contained within each document:
- Document 1 $\to$ `["search", "ranking", "engine"]`
- Document 2 $\to$ `["search", "ranking", "neural"]`
- Document 3 $\to$ `["neural", "search", "recommendation"]`

Evaluating a search query like `"engine"` against a forward index requires scanning every document in the catalog sequentially ($O(N)$ full table scan).

An **inverted index** flips this relationship. It builds a dictionary of all distinct vocabulary terms across the corpus. Each term points to a **posting list** containing every document ID where that term appears, alongside metadata such as the term frequency ($\text{tf}$) within that document:

```
Term Dictionary          Posting Lists
"engine"         ───►   [ (D1, tf=1) ]
"learning"       ───►   [ (D4, tf=1) ]
"neural"         ───►   [ (D2, tf=1), (D3, tf=1) ]
"ranking"        ───►   [ (D1, tf=1), (D2, tf=2) ]
"recommendation" ───►   [ (D3, tf=1), (D4, tf=1) ]
"search"         ───►   [ (D1, tf=1), (D2, tf=1), (D3, tf=1) ]
```

When a user submits a query, the search engine does not touch document text. It performs $O(1)$ dictionary lookups to retrieve the posting lists for each query word, then intersects or merges the posting lists.

## Boolean Retrieval Algorithms

Boolean retrieval evaluates logical queries using set operations over sorted posting lists:

### 1. Boolean AND (List Intersection)
To evaluate `"search AND ranking"`, we fetch the posting list for `"search"` ($[D1, D2, D3]$) and the posting list for `"ranking"` ($[D1, D2]$). Because postings are stored in strictly ascending order of document ID, we find matching documents using a two-pointer merge algorithm in $O(L_1 + L_2)$ time:

```
Pointer 1 on "search":   [ D1,  D2,  D3 ]
                           ▲
Pointer 2 on "ranking":  [ D1,  D2 ]
                           ▲
Match found: D1. Advance both pointers.

Pointer 1 on "search":   [ D1,  D2,  D3 ]
                                ▲
Pointer 2 on "ranking":  [ D1,  D2 ]
                                ▲
Match found: D2. Advance both pointers.

Pointer 2 reaches end. Intersection result: [ D1, D2 ].
```

<GoDeeper title="Accelerating Intersections with Skip Pointers">
For long posting lists with millions of entries, linear scanning remains bottlenecked by sequential memory reads. Search engines augment posting lists with **skip pointers** placed at regular intervals of $\sqrt{L}$ elements.

If pointer 1 is at $D12$ and pointer 2 is at $D85$, pointer 1 inspects its next skip pointer ($D90$). Because $D90 > D85$, the engine skips directly to $D90$ without decoding the intermediate documents ($D13$ through $D89$). This reduces worst-case comparisons from $O(L_1 + L_2)$ to $O(L_1 + L_2 / \sqrt{L_1})$.
</GoDeeper>

### 2. Boolean OR (List Union)
To evaluate `"ranking OR recommendation"`, the engine performs a parallel merge scan, outputting every document that appears in at least one list without duplicates:
- `"ranking"`: $[D1, D2]$
- `"recommendation"`: $[D3, D4]$
- Union result: $[D1, D2, D3, D4]$

### 3. Boolean NOT (Set Difference)
To evaluate `"search AND NOT neural"`, the engine scans the `"search"` postings and filters out any document present in the `"neural"` posting list:
- Candidate list (`"search"`): $[D1, D2, D3]$
- Negation list (`"neural"`): $[D2, D3]$
- Difference result: $[D1]$

## The Limits of Pure Boolean Retrieval

While Boolean matching is blazing fast, it has severe limitations for human search:

1. **No Ranked Relevance**: Boolean retrieval is binary: a document either matches (1) or does not match (0). If a query matches 10,000 documents, Boolean retrieval cannot tell us which document is the most relevant.
2. **The Feast or Famine Problem**:
   - If a query is too specific (`"wireless noise cancelling over ear headphones travel case blue"`), a Boolean `AND` often returns 0 results (**famine**).
   - If a query is too general (`"headphones"`), a Boolean `OR` returns 500,000 results with no ordering (**feast**).
3. **Term Specificity Blindness**: Boolean retrieval treats all words equally. In the query `"how to fix python indentation error"`, the word `"error"` is treated as equally important as `"indentation"`, even though `"indentation"` is far more specific.

To solve these problems, search systems transition from binary Boolean matching to continuous **relevance scoring**:
- **Chapter 3**: [TF-IDF from First Principles](/docs/search-ranking-recommendations/tf-idf) introduces term frequency and inverse document frequency to score matches based on word rarity.
- **Chapter 4**: [BM25: Term Saturation & Length Normalization](/docs/search-ranking-recommendations/bm25) introduces non-linear saturation curves and document-length normalizers that power production search engines.

## Run It Yourself: Building an Inverted Index in Pure Python

Execute the complete text normalization and inverted index implementation below. Notice how the index extracts postings and evaluates Boolean queries directly in Python.

<RunnableCode code={`from collections import defaultdict
import re

def tokenize(text):
    # Lowercase and extract alphanumeric tokens
    return re.findall(r'\\b[a-z0-9]+\\b', text.lower())

class InvertedIndex:
    def __init__(self):
        # term -> list of (doc_id, term_frequency)
        self.postings = defaultdict(list)
        self.doc_lengths = {}
        self.docs = {}

    def add_document(self, doc_id, text):
        tokens = tokenize(text)
        self.docs[doc_id] = text
        self.doc_lengths[doc_id] = len(tokens)
        
        # Count term frequencies within this document
        tf_counts = defaultdict(int)
        for token in tokens:
            tf_counts[token] += 1
            
        for token, count in tf_counts.items():
            self.postings[token].append((doc_id, count))

    def get_postings(self, term):
        term_clean = term.lower()
        return [doc_id for doc_id, tf in self.postings.get(term_clean, [])]

    def boolean_and(self, term1, term2):
        list1 = self.get_postings(term1)
        list2 = self.get_postings(term2)
        # Linear two-pointer intersection
        i, j = 0, 0
        matches = []
        while i < len(list1) and j < len(list2):
            if list1[i] == list2[j]:
                matches.append(list1[i])
                i += 1
                j += 1
            elif list1[i] < list2[j]:
                i += 1
            else:
                j += 1
        return matches

    def boolean_or(self, term1, term2):
        set1 = set(self.get_postings(term1))
        set2 = set(self.get_postings(term2))
        return sorted(list(set1 | set2))

# Index sample corpus
idx = InvertedIndex()
idx.add_document("D1", "search ranking engine")
idx.add_document("D2", "search ranking neural ranking")
idx.add_document("D3", "neural search recommendation system")
idx.add_document("D4", "recommendation deep learning model")

print("Dictionary Terms:", sorted(list(idx.postings.keys())))
print("Postings for 'ranking':", idx.postings["ranking"])

# Execute Boolean Queries
print("\\nQuery: search AND ranking")
print("Matches:", idx.boolean_and("search", "ranking"))

print("\\nQuery: ranking OR recommendation")
print("Matches:", idx.boolean_or("ranking", "recommendation"))
`} />

## When Not to Use Pure Lexical Indexing

| Scenario | Recommended Alternative | Core Reason |
| :--- | :--- | :--- |
| **Broad thematic or conceptual queries** (`"how to improve health"`) | Dense semantic retrieval (Bi-encoders / DPR) | Conceptual queries share zero literal keywords with high-quality answers. |
| **Multimodal assets** (images, audio waveforms, video) | Multimodal embeddings (CLIP, SigLIP) | Media files lack natural text tokens for inverted indexing without upstream OCR/ASR. |
| **High typo and phonetic variance in mobile queries** | Character n-gram tokenization or vector search | Exact token matching fails when words are misspelled (`"iphnoe case"`). |
| **Small in-memory collections (&lt;500 items)** | Linear regex scan or JavaScript `Array.filter` | Building and maintaining an inverted index adds unnecessary memory and runtime overhead. |

## Remember

| Architectural Element | Definition | Systems Role |
| :--- | :--- | :--- |
| **Normalization Pipeline** | Tokenization, case folding, punctuation stripping, stemming | Converts raw text into canonical dictionary terms. |
| **Forward Index** | Mapping from document IDs to word tokens ($D \to [w]$) | Natural document representation; inefficient for search. |
| **Inverted Index** | Mapping from vocabulary terms to posting lists ($w \to [D]$) | Enables sub-millisecond candidate retrieval over millions of documents. |
| **Posting List** | Sorted array of document IDs and term frequencies | Enables linear merge intersections and skip-pointer lookups. |
| **Boolean Retrieval** | Binary set logic (AND, OR, NOT) over posting lists | Fast candidate filtering; lacks ranked relevance scoring. |
