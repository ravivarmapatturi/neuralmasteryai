# Harness Architecture & Sandboxing

A production harness must bridge two conflicting requirements: granting an autonomous agent enough system access to inspect repositories and execute test suites while strictly bounding its **blast radius** to prevent host corruption, resource exhaustion, or credential exfiltration.

<ELI5>

Think of a foundation model as a high-powered racecar engine, and the **Harness** as the entire vehicle around it: the chassis, steering rack, hydraulic brakes, and roll cage. If you mount a raw engine on a workbench and ignite the fuel line, it will spin out of control, shake itself apart, or set fire to the room.

The harness wraps the model in a closed feedback loop. It decides what files the model reads, inspects its tool calls before execution, runs commands inside a sealed box where rogue scripts cannot touch your machine, and forces the model to verify its own work before claiming victory.

</ELI5>

## Why This Exists

Early agent implementations executed model-generated commands directly in the host shell using simple Python `subprocess.run(command, shell=True)` wrappers. In local development or multi-tenant evaluation, this naked execution pattern produces three distinct systemic failures:

1. **Unbounded Destruction**: When resolving merge conflicts or debugging test failures, models regularly generate aggressive cleanup scripts such as `rm -rf *` or `find . -name "*.pyc" -delete`. Without path jails, a model operating in an unexpected directory deletes parent project directories or host configuration files.
2. **Credential Exfiltration**: Autonomous agents tasked with debugging network requests frequently attempt to inspect environment variables (`env`), read cloud credentials (`cat ~/.aws/credentials`), or cat SSH keys (`cat ~/.ssh/id_ed25519`). If untrusted prompts or malicious dependencies inject instructions into the context, the model becomes an unwitting channel for exfiltration.
3. **Orphaned Process Freezes (Fork Bombs)**: When an agent issues a long-running process (like `python train.py` or `while true; do sleep 1; done`), a naive timeout sent to the parent process only terminates the immediate shell. Grandchild processes remain alive in the background, consuming 100% of host CPU cores and locking file handles.

The harness architecture replaces direct execution with a multi-layered boundary: an outer cybernetic loop, strict JSON Schema parameter validation, user-space namespace sandboxing, and POSIX process-group supervision.

### The Turn Contract

Each turn in the execution loop satisfies a formal three-part contract:

1. **Pre-turn Invariant**: The repository workspace is clean or has a known diff recorded in the git staging index. Any uncommitted files from previous failed turns are isolated in scratch branches.
2. **Action Invariant**: The model may only emit structured tool calls conforming to a declared JSON Schema. Unstructured natural language containing shell snippets is rejected before dispatch.
3. **Post-turn Invariant**: Execution output (`stdout`, `stderr`, `exit_code`) is captured, truncated to a strict byte limit, stripped of ANSI escape sequences, and sanitized before re-entering the prompt window.

## Sandboxing Tiers: Containing Blast Radius

When an autonomous agent writes and executes code, running commands directly on the host machine is a catastrophic vulnerability. A production architecture selects an isolation tier based on cold-start latency requirements and tenant trust boundaries.

<SubprocessSandboxVisualizer />

### Isolation Tiers Compared

The three standard tiers balance boot latency against kernel isolation:

| Tier | Technology | Boot Latency | Isolation Boundary | Target Workload |
| :--- | :--- | :--- | :--- | :--- |
| **Tier 1: OS-Level Jail** | Linux namespaces + Bubblewrap (`bwrap`) | ~8-15 ms | Unprivileged user namespaces, read-only root mounts | Local developer CLI tools (Claude Code, Codex CLI) |
| **Tier 2: User-Space Kernel** | Docker with `gVisor` (`runsc`) | ~150-250 ms | Sentry kernel intercepts syscalls in user space | Cloud evaluation harnesses, multi-tenant agent pools |
| **Tier 3: Hardware MicroVM** | AWS Firecracker / KVM | ~120-180 ms | Hardware virtualization boundary (KVM hypervisor) | Untrusted code execution, untrusted third-party webhooks |

<GoDeeper title="Go deeper: How bubblewrap and cgroups v2 enforce isolation in userspace">

Local developer CLI tools cannot afford the 3-5 second cold-start overhead of spinning up full virtual machines for every bash invocation. They rely on **Bubblewrap (`bwrap`)**, an unprivileged user-namespace container utility:

1. **Mount Namespaces (`CLONE_NEWNS`)**: Bubblewrap constructs a temporary virtual filesystem where `/` is mounted read-only, `/tmp` is a transient `tmpfs`, and only `/workspace/repo` is mounted read-write. Sensitive host directories like `~/.ssh`, `~/.aws`, and `/etc/shadow` are unmapped and inaccessible.
2. **Network Namespaces (`CLONE_NEWNET`)**: Unsharing the network namespace creates an isolated network stack containing only loopback (`lo`). Any outbound `socket()` syscall immediately fails with `ENETUNREACH`.
3. **cgroups v2 Resource Accounting**: Linux control groups restrict maximum memory (`memory.max = 2G`) and maximum threads/processes (`pids.max = 64`). If an agent triggers an out-of-memory error or fork bomb, the kernel OOM killer terminates only the sandbox jail, leaving the supervisor running.

</GoDeeper>

### Production Sandbox Configurations

To execute a command inside a Tier 1 Bubblewrap sandbox, the harness constructs an invocation with explicit filesystem bindings:

```bash
# Real production Bubblewrap invocation for Python test execution
bwrap \
  --ro-bind /usr /usr \
  --ro-bind /lib /lib \
  --ro-bind /lib64 /lib64 \
  --ro-bind /bin /bin \
  --ro-bind /sbin /sbin \
  --ro-bind /etc/resolv.conf /etc/resolv.conf \
  --dir /tmp \
  --tmpfs /tmp \
  --dev /dev \
  --proc /proc \
  --unshare-all \
  --unshare-net \
  --bind /home/runner/workspace /workspace \
  --chdir /workspace \
  --setenv PATH "/usr/local/bin:/usr/bin:/bin" \
  --setenv VIRTUAL_ENV "/workspace/.venv" \
  -- pytest tests/unit/test_router.py -v
```

For Tier 2 cloud execution, configure Docker to route system calls through Google gVisor (`runsc`):

```bash
# Register runsc runtime and execute container with bounded resources
docker run --rm \
  --runtime=runsc \
  --network none \
  --memory 2048m \
  --cpus 2.0 \
  --pids-limit 64 \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --volume /srv/agent/workspaces/job-42:/workspace:rw \
  --workdir /workspace \
  agent-test-runner:latest \
  pytest tests/unit/test_router.py -v
```

## A Full Worked Example: Process Supervision & Interception

Consider an autonomous coding agent evaluating a pull request. The agent proposes three distinct commands across its trajectory:
1. `pytest tests/unit/test_router.py -v` (a valid test suite run taking 312 ms and 48 MB RAM)
2. `cat /etc/shadow || cat ~/.ssh/id_ed25519` (an illegal credential probe)
3. `rm -rf / --no-preserve-root` (a catastrophic deletion command)

The harness supervisor intercepts each command, applies static AST and regex heuristics, and dispatches only valid commands into the sandbox jail while enforcing process-group timeouts.

### Run It Yourself

Execute this self-contained Python implementation of the supervisor. It validates commands against forbidden patterns, isolates execution, and reports structured telemetry:

        return None

## Common Problems & Fixes

When implementing a custom harness, engineers encounter four recurring operational defects:

1. **Zombie Subprocesses Locking Workspace Files**: When an agent runs a dev server (`npm run dev`) or test watcher, the supervisor's timeout leaves background workers holding file descriptors.
   - *Fix*: Call `os.setsid()` in the child `preexec_fn` and send `os.killpg(os.getpgid(proc.pid), signal.SIGKILL)` on timeout.
2. **Context Window Flooding from Verbose Compiler Logs**: An agent runs `find /` or `pip list`, emitting 100,000 tokens of output that exceeds model limits.
   - *Fix*: Hard-truncate `stdout` at 8,000 characters (~2,000 tokens) with a message: `[TRUNCATED: Output exceeded 8000 bytes. Retaining last 40 lines]`.
3. **Pseudo-Terminal (TTY) Expectation Freezes**: Commands like `git rebase -i` or `apt-get install` block indefinitely waiting for user keyboard interaction.
   - *Fix*: Export `DEBIAN_FRONTEND=noninteractive` and `CI=true`, set `TERM=dumb`, and pass `/dev/null` as stdin.

<NotebookCallout color="amber" title="Subprocess Signal Handling Invariant">
Never invoke `subprocess.run(shell=True)` without an explicit process group ID. When a timeout occurs in Python, `proc.kill()` terminates only `/bin/sh`, leaving child compilers or fork bombs running indefinitely as orphaned processes.
</NotebookCallout>

## When *Not* to Use It

Sandboxing introduces operational complexity and overhead. Match the architecture to your deployment:

| Situation | Better Choice | Why |
| :--- | :--- | :--- |
| Read-only documentation retrieval (RAG) | Simple API gateway / direct function call | Read-only vector searches execute no user code; namespace sandboxing adds unnecessary latency. |
| Deterministic CI/CD workflow | Standard GitHub Actions / GitLab CI runner | If the pipeline steps are predefined and fixed, an autonomous agent harness adds non-deterministic overhead. |
| Low-latency interactive autocomplete | IDE Language Server Protocol (LSP) | LSP completions require sub-50 ms response times; sandbox process initialization introduces latency lag. |

## Remember

| Idea | Core Rule |
| :--- | :--- |
| **Blast Radius** | Constrain filesystems to read-only mounts with an isolated temporary write layer. |
| **Process Groups** | Always execute subshells with `os.setsid()` and kill via `os.killpg()`. |
| **Bubblewrap (`bwrap`)** | Use for sub-15 ms local sandboxing with unprivileged user namespaces. |
| **gVisor (`runsc`)** | Use for multi-tenant cloud runners to intercept kernel system calls in user space. |
| **Output Truncation** | Never pass unbounded terminal output into context; enforce byte limits per turn. |
| **Schema Gate** | Reject unstructured command text; validate every parameter against strict schemas. |
