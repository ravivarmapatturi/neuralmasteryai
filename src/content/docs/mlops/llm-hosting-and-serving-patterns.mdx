# LLM Hosting, Serving Patterns & LLMOps Monitoring, In Full Depth

[LLM Inference Engines](/docs/mlops/llm-inference-engines) covered the software that runs a language model efficiently: vLLM, SGLang, TensorRT-LLM, llama.cpp. An engine still needs hardware to run on, a model to load, a way to receive traffic, and someone watching it. This page covers those decisions: whether to call an API or host a model at all, the hosting stack, how much GPU memory a model really needs (weights *and* KV cache, computed), what self-hosting costs per million tokens at different utilizations, serverless and local hosting, the handoff from fine-tuning to serving, serving many fine-tunes on one GPU, embedding and reranker models for RAG, and the metrics that tell you whether it's working, measured on a real model.

<ELI5>

A company that needs deliveries can hire a courier service, lease its own vans, or keep one van on call that it only pays for when it's used. The courier is simplest. Owning vans is cheapest per parcel, but only if the vans are busy; an idle van still costs money. The on-call van suits occasional deliveries but takes a while to show up.

Running a language model is the same choice: call a provider's API, run your own GPUs, or use serverless GPUs that start when needed. Most of this page is about how to work out which is cheaper and faster for your traffic, and what to watch once it's running.

</ELI5>

## 1. API or Self-Host?

The first decision isn't *where* to host a model, it's whether to host one at all. Calling a provider's API (Anthropic, OpenAI, Google, or an open-model API from Together, Fireworks or a cloud provider) means no GPUs, no engines, no capacity planning, and access to the most capable models. Self-hosting an open-weight model makes sense for specific reasons:

- **Data control:** inputs can't leave your environment, for regulatory or contractual reasons.
- **Cost at high, steady volume:** a busy GPU can be much cheaper per token than an API (section 4), but only if it stays busy.
- **Customization:** a fine-tuned model, or many fine-tunes served side by side (section 7).
- **Latency or availability control:** dedicated capacity in your own region, no shared rate limits.
- **Offline or edge use:** no network at all.

If none of those applies, an API is usually the right answer, and this page is background. If one does, the rest of the page is the work involved.

**Read the data terms either way.** Before sending real user data to any API, check four things in the contract and settings, not the marketing page: whether inputs and outputs may be used to **train** the provider's models (business tiers usually exclude this by default); how long they're **retained**, and whether **zero data retention** is available for your use; which **region** processes and stores them, since data residency rules (EU customers, healthcare, government) may require a specific one, and several providers and the major clouds offer regional or in-country processing; and what the provider's **subprocessors** are. Record the answers next to each provider in the gateway configuration (section 9), so that routing can never send a regulated tenant's request to a provider or region that isn't allowed to see it.

## 2. The Hosting Stack

### Cloud GPU Hosting

Whatever the provider, a self-hosted model sits in the same layers:

<HostingStackDiagram />

1. **Model artifact:** weights (ideally `safetensors`), tokenizer and configuration, pinned by revision or hash.
2. **Container:** the inference engine plus the CUDA libraries it needs, pinned by digest ([Containers](/docs/mlops/containers)).
3. **GPU machine:** a VM or Kubernetes node with the right GPU and enough GPU memory (section 3).
4. **Inference engine:** vLLM, SGLang or TensorRT-LLM, exposing an OpenAI-compatible HTTP API.
5. **Gateway and load balancer:** authentication, rate limits, routing between replicas and models, and request logging.

Where those layers run is a spectrum of control against effort:

| Option | Examples | You manage | Fits |
|---|---|---|---|
| **General clouds, self-managed** | GPU VMs or Kubernetes on AWS, Google Cloud, Azure | Everything above the hardware | Large, steady workloads with platform engineers |
| **Managed endpoints** | SageMaker, Vertex AI, Azure ML, Hugging Face Inference Endpoints | The model and its configuration | Teams on one cloud who want less operations |
| **GPU clouds and serverless GPU** | RunPod, Modal, Baseten, Lambda, CoreWeave | Container and scaling settings | Faster access to GPUs, often lower prices, pay-per-second options |
| **Hosted open-model APIs** | Together AI, Fireworks, cloud model gardens, custom-chip providers such as Groq and Cerebras | Nothing but the API call | Open models without hosting them; some offer dedicated deployments |

The trade-off is the usual one: the more the platform manages, the faster you start and the less you can tune cost and behaviour. Whichever you choose, the sizing question comes first.

## 3. Sizing GPU Memory: Weights and KV Cache

A model doesn't just need room for its weights. Every active request also holds a **KV cache**: the attention keys and values for every token processed so far, kept so that each new token doesn't recompute them ([LLM Inference Optimization](/docs/mlops/llm-inference-optimization#kv-cache) explains why). Both are easy to compute:

$$\text{weights} = N_{\text{params}} \times \text{bytes per parameter}$$

$$\text{KV cache per token} = 2 \times n_{\text{layers}} \times n_{\text{kv heads}} \times d_{\text{head}} \times \text{bytes per value}$$

The 2 is for keys and values. For Llama 3.1 8B (32 layers, 8 key-value heads thanks to grouped-query attention, head dimension 128):

```python
GiB = 1024 ** 3

def weights_gib(params_b, bytes_per_param):
    return params_b * 1e9 * bytes_per_param / GiB

def kv_cache_gib(tokens, layers, kv_heads, head_dim, bytes_per_value=2):
    """K and V, per layer, per KV head, per token."""
    return 2 * layers * kv_heads * head_dim * bytes_per_value * tokens / GiB

# Llama 3.1 8B: 32 layers, 8 KV heads (grouped-query attention), head dim 128
per_token_kib = kv_cache_gib(1, 32, 8, 128) * 1024 * 1024
print(f"KV cache per token (BF16): {per_token_kib:.0f} KiB")
for precision, b in [("BF16", 2), ("FP8", 1), ("INT4", 0.5)]:
    print(f"8B weights in {precision:<4}: {weights_gib(8.03, b):5.1f} GiB")

for users, ctx in [(1, 8_192), (32, 8_192), (32, 32_768)]:
    print(f"{users:>2} concurrent requests x {ctx:>6} tokens: KV cache {kv_cache_gib(users * ctx, 32, 8, 128):5.1f} GiB")
```

```text
KV cache per token (BF16): 128 KiB
8B weights in BF16:  15.0 GiB
8B weights in FP8 :   7.5 GiB
8B weights in INT4:   3.7 GiB
 1 concurrent requests x   8192 tokens: KV cache   1.0 GiB
32 concurrent requests x   8192 tokens: KV cache  32.0 GiB
32 concurrent requests x  32768 tokens: KV cache 128.0 GiB
```

The weights fit easily on a 24 GB GPU; the problem is concurrency. Thirty-two simultaneous 8K-token conversations need 32 GiB of KV cache on top of 15 GiB of weights, more than a 40 GB GPU holds, and long contexts multiply it again: 32 users at 32K tokens need 128 GiB of cache. That's why engines manage the cache in pages (PagedAttention), why they queue requests when cache space runs out, and why FP8 KV-cache quantization, which halves these numbers, is widely used.

**The practical rule:** choose the GPU from weights *plus* KV cache for your target concurrency and context length, plus a few gigabytes of overhead for activations and the CUDA runtime. Undersize it and the engine serves few requests at once, so throughput and cost per token suffer.

## 4. What Self-Hosting Costs

The cost of a self-hosted model is dominated by one ratio: how much of the GPU-time you pay for is spent generating tokens.

$$\text{cost per token} = \frac{\text{GPU price per hour}}{\text{tokens per hour}} = \frac{\text{GPU price per hour}}{\text{peak tokens/s} \times 3600 \times \text{utilization}}$$

With illustrative numbers, a GPU at \$2.50 an hour serving an 8B model at an aggregate 2,500 output tokens a second when fully batched:

```python
# Self-hosting cost per million output tokens, as a function of how busy the GPU is.
gpu_per_hour = 2.50              # an on-demand H100-class GPU, USD/hour (varies widely by provider)
peak_tokens_per_s = 2_500        # aggregate output tokens/s at full batch for an 8B model (benchmark yours)

for utilization in [1.0, 0.5, 0.2, 0.05]:
    tokens_per_hour = peak_tokens_per_s * 3600 * utilization
    print(f"utilization {utilization:4.0%}: ${gpu_per_hour / tokens_per_hour * 1e6:6.2f} per 1M output tokens")
```

```text
utilization 100%: $  0.28 per 1M output tokens
utilization  50%: $  0.56 per 1M output tokens
utilization  20%: $  1.39 per 1M output tokens
utilization   5%: $  5.56 per 1M output tokens
```

At full use, self-hosting is very cheap per token. At 5% utilization, an internal tool used during office hours, it's twenty times more expensive, and likely more than an API charges for a comparable model. **Self-hosting pays when traffic is high and steady;** for spiky or low traffic, an API or serverless GPUs win. The inputs here are assumptions: benchmark your own model, engine and request mix, since peak throughput depends heavily on prompt and output lengths, and price in the engineers who run it. [AI Cost Engineering](/docs/mlops/ai-cost-engineering) covers the wider cost picture.

## 5. Serverless and Local Hosting

### Serverless Inference

**Serverless GPU** platforms start a GPU container when requests arrive and stop it when traffic stops, billing by the second. They solve the utilization problem from section 4, at the price of **cold starts**: the first request after idle waits for a machine, the container, and the model weights to load into GPU memory, from several seconds for a small model to a minute or more for a large one.

<ServerlessColdStartDiagram />

Platforms reduce cold starts with warm pools, cached images, fast weight loading from local NVMe, and memory snapshots of a loaded process. The fit is spiky or low-volume traffic where a slow first request is acceptable: internal tools, batch jobs, demos, evaluation runs. Steady production traffic is usually cheaper on always-on capacity sized for it, often with a small serverless overflow for peaks.

**Local hosting** runs models on a laptop, workstation or on-premises server, for development, privacy, or offline use. **Ollama** wraps model download and serving behind a simple command line and a local HTTP API (built on llama.cpp, with its own engine for some model families); **LM Studio** offers the same in a desktop app; **llama.cpp's `llama-server`** gives direct control, including grammar-constrained output. These run quantized GGUF models efficiently on CPUs and consumer GPUs. For real multi-user throughput on your own GPUs, the step up is vLLM or SGLang, the same engines used in the cloud.

## 6. From Fine-Tuning to Serving

### The Fine-Tuning → Inference Pipeline

Fine-tuning and serving are separate jobs done by separate tools, and mixing them up is a common mistake:

<FineTuningToInferenceHandoffDiagram />

```text
Base model → fine-tuning framework (Unsloth, TRL, Axolotl; LoRA or QLoRA) → adapter or merged weights → inference engine → endpoint
```

Fine-tuning frameworks like **Unsloth** make training adapters faster and lighter on memory; that's their job. They're not built to serve production traffic. The output, either a small **LoRA adapter** or a **merged** model with the adapter folded into the base weights, is handed to an inference engine. The handoff deserves the same discipline as any model release: register the adapter with its base model's exact revision (an adapter is meaningless on a different base), evaluate it with the serving engine and the serving precision, since quantizing for serving can change behaviour, and promote it through the registry and a gate ([CI/CD & ML CI/CD](/docs/mlops/cicd-and-ml-cicd)).

**Merge or keep separate?** Merging gives the simplest, fastest serving for one fine-tune. Keeping adapters separate makes the next pattern possible.

## 7. Many Fine-Tunes on One GPU

### Multi-LoRA Serving

A LoRA adapter changes a model's behaviour by adding small low-rank matrices to some of its weight matrices. For a weight matrix of size $d \times d$, a rank-$r$ adapter adds $2rd$ parameters. With $d = 4096$ and $r = 16$ that's about 131,000 parameters per adapted matrix against 16.8 million in the matrix itself, under 1%. A whole adapter for an 8B model is typically tens of megabytes.

<MultiLoraServingDiagram />

So instead of deploying one full model per customer or task, an engine can keep **one base model in GPU memory and many adapters beside it**, applying the right adapter per request. vLLM does this with `--enable-lora` and named adapters (`--lora-modules support-tone=./adapters/support-tone`); a request selects one by passing its name as the `model`. Requests for different adapters still batch together, using kernels designed for mixed-adapter batches (the approach introduced by S-LoRA and Punica). Dozens of fine-tunes then cost little more than one, which changes the economics of per-customer or per-task models.

## 8. Embeddings, Rerankers and Multimodal Models

### Embedding & Reranker Inference for Production RAG

RAG systems ([LLM Evaluation & RAGOps](/docs/mlops/llm-evaluation-and-ragops)) need two more model types, each with its own serving needs:

<EmbeddingRerankerPipelineDiagram />

- **Embedding models** (for example BGE, E5, GTE, Nomic and the Sentence Transformers family) turn text into vectors. They're small and fast, and they run in two very different modes: bulk embedding of the whole corpus (a batch job where throughput is all that matters) and query embedding at request time (a few milliseconds, on the critical path). Changing the embedding model means re-embedding the whole corpus, since vectors from different models can't be compared.
- **Rerankers** (cross-encoders) score each query-document pair jointly, which is far more accurate than comparing vectors and far more expensive, so they only rescore the top few dozen candidates from the first-stage retrieval.

Hugging Face's **Text Embeddings Inference** (TEI) is a dedicated server for both, with dynamic batching; Triton, Ray Serve or a FastAPI service with batching ([APIs & Model Serving](/docs/mlops/model-serving#6-dynamic-batching)) are common alternatives. Small embedding models run well on CPUs, which keeps GPUs for the generator.

### Multimodal / VLM Inference

**Vision-language models** (Qwen-VL, Llama vision models, Gemma and many others) add an image encoder whose output is projected into the language model's token space, so each image becomes hundreds or thousands of extra input tokens. For serving, that means larger prefills, more KV cache per request, and image preprocessing on the request path. vLLM and SGLang serve the common open VLMs directly; budget memory and latency for the image tokens as if they were text.

## 9. The AI Gateway and Load Balancing

Once an organization has more than one model, provider or team, every application calling models directly becomes a problem: API keys scattered across services, no shared view of cost, a different retry policy in every codebase, and no way to switch provider without changing all of them. The common answer is an **AI gateway**: one entry point that every model call goes through. It's an ordinary reverse proxy with LLM-specific features, and open-source (LiteLLM, Envoy AI Gateway, Kong) and managed options exist. A gateway typically handles:

- **Credentials:** applications get gateway keys; provider keys live only in the gateway, and can be rotated in one place.
- **Routing and fallbacks:** one OpenAI-compatible API in front of several providers and self-hosted engines, with the cascades and fallbacks from [AI Cost Engineering](/docs/mlops/ai-cost-engineering#5-routing-the-right-model-for-each-request) and [Production Reliability](/docs/mlops/production-reliability#5-graceful-degradation-and-fallbacks) configured once, plus policy routing such as "tenant X only to EU-hosted models" (section 1).
- **Limits and budgets:** rate limits and token budgets per team, customer and feature.
- **Logging and cost attribution:** every request, with tokens, cost, latency and model version, sent to the observability stack.
- **Prompt resolution:** applications ask for a named, versioned prompt and the gateway or a prompt registry supplies the text, so prompts can change without redeploying applications ([ML & LLM Testing](/docs/mlops/ml-and-llm-testing#3-prompts-are-code-version-review-replay) covers versioning them against evaluations).
- **Batch traffic:** non-interactive work (nightly enrichment, evaluations) goes to providers' **batch APIs**, which process requests asynchronously within a time window, typically within 24 hours, at a large discount, or to a self-hosted engine's offline mode, instead of competing with interactive traffic.

**Load balancing self-hosted replicas** is where LLM serving differs most from ordinary web services. Round-robin or least-connections balancing assumes requests cost about the same. LLM requests don't: one wants 10 output tokens, the next 2,000, and a replica's real load is the tokens it still has to generate and the KV cache it holds. Two smarter policies are common:

- **Least outstanding tokens** (or least KV-cache usage) sends each request to the replica with the least work queued, using metrics the engines export.
- **Prefix-aware routing** sends requests that share a prompt prefix (the same system prompt, the same tenant's instructions, the same conversation) to the replica that already holds that prefix in its KV cache, so prefill is skipped. **Sticky sessions** are the simple version for chat: keep a conversation on one replica so its growing history stays cached.

This simulation shows why prefix awareness matters. Eight tenants each have a 2,000-token system prompt; four replicas can each keep only two tenants' prefixes cached. Round robin sprays every tenant across every replica, so prefixes keep getting evicted; prefix-aware routing sends each tenant to a home replica, falling back to the least-loaded one when its home is overloaded:

```python
import heapq
from collections import OrderedDict
import numpy as np

rng = np.random.default_rng(0)
N_REPLICAS, N_REQUESTS = 4, 4_000
TOKENS_PER_S = 40                                 # decode speed per request on a replica
PREFILL_PER_TOKEN = 0.0005                        # seconds per prompt token not already cached

# Requests: 8 tenants, each with a long shared system prompt; output lengths are heavy-tailed
tenants = rng.integers(0, 8, N_REQUESTS)
prompt_tokens = 2_000 + rng.integers(0, 200, N_REQUESTS)          # mostly the tenant's shared prefix
output_tokens = np.minimum(rng.lognormal(4.5, 1.0, N_REQUESTS).astype(int) + 10, 2_000)
arrivals = np.cumsum(rng.exponential(0.1, N_REQUESTS))

def simulate(policy):
    busy_until = [[] for _ in range(N_REPLICAS)]        # per replica: heap of (finish time, output tokens)
    cached_prefixes = [OrderedDict() for _ in range(N_REPLICAS)]   # KV cache holds 2 tenants' prefixes
    ttfts, tpots, rr = [], [], 0
    for t, tenant, p, o in zip(arrivals, tenants, prompt_tokens, output_tokens):
        for heap in busy_until:                           # retire finished requests
            while heap and heap[0][0] <= t:
                heapq.heappop(heap)
        outstanding = [sum(tok for _, tok in heap) for heap in busy_until]   # tokens still to generate (approx.)
        if policy == "round robin":
            r = rr % N_REPLICAS; rr += 1
        else:                                             # prefix-aware: tenant's home replica unless overloaded
            home = tenant % N_REPLICAS
            r = home if outstanding[home] < 1.5 * (min(outstanding) + 500) else int(np.argmin(outstanding))
        prefill = 0.05 if tenant in cached_prefixes[r] else p * PREFILL_PER_TOKEN
        cached_prefixes[r][tenant] = True; cached_prefixes[r].move_to_end(tenant)
        if len(cached_prefixes[r]) > 2:
            cached_prefixes[r].popitem(last=False)          # evict the least recently used prefix
        slowdown = 1 + len(busy_until[r]) / 16             # more concurrent requests, slower each step
        ttft, tpot = prefill * slowdown, slowdown / TOKENS_PER_S
        heapq.heappush(busy_until[r], (t + ttft + o * tpot, o))
        ttfts.append(ttft); tpots.append(tpot)
    return np.percentile(ttfts, 50), np.percentile(ttfts, 99), np.percentile(tpots, 99)

for policy in ["round robin", "prefix-aware"]:
    t50, t99, tpot99 = simulate(policy)
    print(f"{policy:<26} TTFT p50 {t50 * 1000:5.0f} ms  p99 {t99 * 1000:5.0f} ms   time per token p99 {tpot99 * 1000:3.0f} ms")
```

```text
round robin                TTFT p50  3329 ms  p99  4817 ms   time per token p99 114 ms
prefix-aware               TTFT p50   134 ms  p99  3125 ms   time per token p99  88 ms
```

The median time to first token falls from 3.3 seconds to 0.13, because most requests now land where their prefix is already cached and skip a 2,000-token prefill. The tail improves less: some requests still overflow to a replica without their prefix. The simulation is simplified (no request queue, an approximate load signal), but the effect is the one production routers such as the vLLM production stack's router, SGLang's router and NVIDIA Dynamo's KV-aware routing are built to capture. The trade-off to watch is hot spots: pure stickiness can overload the replica that owns a popular tenant, which is why the policy falls back to the least-loaded replica past a threshold.

## 10. LLMOps Monitoring: Measuring What Users Feel

LLM serving has its own latency metrics, because a response streams out token by token:

- **Time to first token (TTFT):** from request to the first token. Dominated by **prefill**, processing the whole prompt, so it grows with prompt length. This is what makes a chat feel responsive.
- **Time per output token (TPOT)**, also called inter-token latency: the gap between later tokens, set by the **decode** step. Reading speed is roughly 5 to 10 tokens a second, so anything faster than that streams faster than people read.
- **End-to-end latency:** $\text{TTFT} + (n_{\text{out}} - 1) \times \text{TPOT}$.
- **Throughput:** total tokens per second across all requests, which is what determines cost.

To see the prefill and decode phases separately, here's a measurement on a deliberately tiny model (SmolLM2, 135 million parameters) running on a laptop CPU, streaming 64 output tokens after prompts of increasing length:

```python
import threading, time

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, TextIteratorStreamer

torch.set_num_threads(4)
name = "HuggingFaceTB/SmolLM2-135M-Instruct"          # tiny, so this runs on a laptop CPU
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, torch_dtype=torch.float32)

def measure(prompt_tokens, new_tokens=64):
    prompt = "word " * prompt_tokens
    inputs = tok(prompt, return_tensors="pt")
    streamer = TextIteratorStreamer(tok, skip_prompt=True)
    args = dict(**inputs, max_new_tokens=new_tokens, min_new_tokens=new_tokens, do_sample=False, streamer=streamer)
    start = time.perf_counter()
    threading.Thread(target=model.generate, kwargs=args).start()
    stamps = [time.perf_counter() for _ in streamer]  # a timestamp per streamed piece of text
    ttft = stamps[0] - start
    tpot = (stamps[-1] - stamps[0]) / (new_tokens - 1)   # exactly new_tokens are generated
    print(f"prompt {inputs['input_ids'].shape[1]:>5} tokens: TTFT {ttft * 1000:6.0f} ms   "
          f"time per output token {tpot * 1000:5.1f} ms   ({1 / tpot:4.0f} tokens/s)")

measure(32)                                            # warm-up
for n in [32, 512, 2048]:
    measure(n)
```

After the warm-up run (PyTorch 2.14 on CPU, Transformers):

```text
prompt    33 tokens: TTFT    124 ms   time per output token  53.8 ms   (  19 tokens/s)
prompt   513 tokens: TTFT    978 ms   time per output token  55.2 ms   (  18 tokens/s)
prompt  2049 tokens: TTFT   4598 ms   time per output token  79.9 ms   (  13 tokens/s)
```

The two phases behave differently. **TTFT grows with the prompt**: 62 times more prompt tokens (33 to 2,049) took 37 times longer before the first token, because prefill processes every prompt token (and attention over a longer prompt costs more per token). **TPOT grows only slowly**, from 54 to 80 ms, because each decode step generates one token, though it does read a longer KV cache. On a GPU with a production engine every number is far smaller, but the shape is the same, which is why long-prompt applications such as RAG with many retrieved passages, and long chat histories, show high TTFT first, and why prefix caching (reusing the KV cache of a shared system prompt or document) is one of the most effective optimizations ([LLM Inference Optimization](/docs/mlops/llm-inference-optimization)).

<GoDeeper title="Go deeper: setting latency targets and routing between models">

Service targets for LLM endpoints are usually written per phase: for example p95 TTFT under 800 ms and p95 TPOT under 50 ms for interactive chat, with looser targets for batch summarization. Engines expose the measurements (vLLM publishes Prometheus histograms for TTFT, inter-token latency, queue time and KV-cache usage), so the burn-rate alerting from [Observability](/docs/mlops/observability#7-slos-error-budgets-and-alerts-that-mean-something) applies unchanged.

Two signals predict trouble before latency does: **queue time** (requests waiting for batch or cache space) and **KV-cache utilization**. When the cache is near full, engines delay or preempt requests, and TTFT climbs sharply, the same $1/(1-\rho)$ behaviour as any queue ([APIs & Model Serving](/docs/mlops/model-serving#5-latency-throughput-and-queues)). Autoscale on those, not on GPU utilization, which reads near 100% whenever anything is running.

A **model router** in the gateway sends each request to the cheapest model likely to handle it well: short, simple requests to a small model; hard ones to a large model or an external API. Routing by request type, prompt length or a small classifier often cuts cost substantially, and it needs per-route quality monitoring so savings don't quietly cost accuracy.

</GoDeeper>

Beyond latency, an LLM service needs the signals no classical service has:

| Signal | Why it matters |
|---|---|
| Input and output tokens per request, by route and customer | Cost attribution and capacity planning; sudden growth often means a prompt or retrieval change |
| Cost per request and per successful task | Catches expensive regressions, such as an agent looping through tool calls |
| Refusal, error and truncation rates | Truncation at `max_tokens` silently cuts answers |
| Sampled quality scores from a calibrated judge | Faithfulness and helpfulness drift after model, prompt or corpus changes ([LLM Evaluation & RAGOps](/docs/mlops/llm-evaluation-and-ragops)) |
| User feedback and escalations | The ground truth that judges approximate |
| Model and adapter version per response | Lets every other metric be split by version during rollouts |

## 11. When *Not* to Self-Host

| Situation | Better choice |
|---|---|
| Low or unpredictable traffic | A provider API, or serverless GPUs with accepted cold starts |
| You need frontier-model quality | A frontier provider's API; open models may trail on the hardest tasks |
| No one to run GPU infrastructure | A managed endpoint or hosted open-model API |
| Experimenting with prompts and models | APIs first; self-host once the model, volume and requirements are settled |
| Strict data residency but low volume | A provider's regional or private deployment option, before building your own stack |

## Remember

| Idea | In one line |
|---|---|
| First question | Use an API unless data control, steady volume, customization or latency demands self-hosting |
| Stack | Pinned weights, engine container, GPU machine, OpenAI-compatible API, gateway |
| KV cache | $2 \times$ layers $\times$ KV heads $\times$ head dim $\times$ bytes per token; 128 KiB/token for Llama 3.1 8B |
| Sizing | Weights plus KV cache for target concurrency and real context lengths |
| Cost | GPU price over tokens served; utilization dominates, 5% busy costs 20x more per token |
| Serverless | Pays only when used; cold starts of seconds to minutes |
| Fine-tune handoff | Training frameworks produce adapters; inference engines serve them; pin the base revision |
| Multi-LoRA | One base model, many small adapters, batched together |
| Latency metrics | TTFT grows with the prompt (prefill); TPOT is the decode speed |
| AI gateway | One entry point for keys, routing, fallbacks, budgets, logging, prompts and batch traffic |
| LLM load balancing | Route by outstanding tokens and shared prefixes, not round robin |
| Data terms | Check training use, retention, region and subprocessors before sending real data |
