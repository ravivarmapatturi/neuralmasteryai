# LLM Inference Engines, In Full Depth

[APIs & Model Serving](/docs/mlops/model-serving) built a service around a classical model: load it once, validate requests, batch them, return a prediction. Language models break several of that page's assumptions. Each response is generated one token at a time, so a request occupies the hardware for seconds rather than milliseconds; responses vary in length by a factor of a hundred; and each in-progress request carries gigabytes of attention state. Specialized **inference engines** exist to handle exactly this. This page covers the layers of an LLM serving stack, the vocabulary that keeps engines, servers and platforms apart, why naive batching wastes most of a GPU (measured on a real model and simulated at scale), the two ideas at the heart of modern engines, continuous batching and paged KV memory, and how the main engines compare as of late 2026.

<ELI5>

Picture a printing press that can print eight books side by side. A naive printer loads eight books, and the press runs until the *longest* one is finished, even though most are done after a few pages and their slots sit empty. A smarter printer slots a new book in the moment any slot frees up, so the press is always full.

There's also the paper. The naive printer reserves enough paper for the thickest possible book for every slot, and most of it is never used. The smarter one hands out paper a few pages at a time as each book needs it.

Inference engines are the smarter printer: they keep the GPU full of work and hand out memory as it's needed. Everything below is how.

</ELI5>

## 1. Why Language Models Need Their Own Engines

Three properties of autoregressive generation make LLM serving its own problem:

- **Generation is sequential.** A response of 500 tokens takes 500 forward passes, each depending on the last. A request holds the model for seconds.
- **Work per request varies enormously.** One request needs 10 output tokens and the next 2,000, and the length isn't known in advance.
- **Each request carries a large, growing state.** The KV cache, the stored attention keys and values for every token so far, grows by tens to hundreds of kilobytes per token ([LLM Hosting & Serving Patterns](/docs/mlops/llm-hosting-and-serving-patterns#3-sizing-gpu-memory-weights-and-kv-cache) computes it), so a few long conversations can fill a GPU's memory.

The cost of a decode step is dominated by reading the model's weights from GPU memory, and that cost is nearly the same whether the step produces one token or a token for each of 64 requests. So the central job of an engine is to **keep many requests in flight at once**, while handling their different lengths and their memory without waste. A plain `model.generate()` loop does none of that, and the gap is large.

## 2. The Serving Stack and Its Vocabulary

A request to a self-hosted LLM passes through several layers:

<InferenceStackLayersDiagram />

1. **Gateway:** authentication, rate limits, routing between models and replicas, logging ([LLM Hosting & Serving Patterns](/docs/mlops/llm-hosting-and-serving-patterns#9-the-ai-gateway-and-load-balancing)).
2. **Serving layer:** the HTTP API (usually OpenAI-compatible), request queueing and streaming of tokens back to the client.
3. **Inference engine:** schedules which requests run in each step, manages the KV cache, and runs the optimized forward passes.
4. **Kernels and runtime:** attention and matrix-multiply kernels (FlashAttention, FlashInfer, cuBLAS, Triton-language kernels), CUDA graphs, PyTorch or a compiled runtime.
5. **Hardware:** GPUs or other accelerators, and the interconnect between them.

Four terms get mixed up, and the confusion leads to picking the wrong tool:

<EngineTerminologyDiagram />

- An **inference engine** *executes* a model efficiently: vLLM, SGLang, TensorRT-LLM, llama.cpp.
- A **serving framework** *exposes* models as an API and manages requests. Often the same tool as the engine (vLLM and SGLang ship their own servers), but not always: NVIDIA Dynamo-Triton can serve several engines as backends.
- A **hosting platform** *provides* the machines: a GPU cloud, a Kubernetes cluster, a managed endpoint.
- A **fine-tuning framework** *trains* or adapts a model, as Unsloth, TRL and Axolotl do. It produces weights for an engine; it isn't one.

## 3. The Baseline: Batching a Plain Model

Before any engine, here's what batching alone buys. This measures a small model (SmolLM2, 135 million parameters, on a laptop CPU with PyTorch) generating 48 tokens for each of 16 prompts, sent one at a time, four at a time, and all sixteen at once:

```python
import time

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

torch.set_num_threads(4)
name = "HuggingFaceTB/SmolLM2-135M-Instruct"
tok = AutoTokenizer.from_pretrained(name, padding_side="left")
model = AutoModelForCausalLM.from_pretrained(name, torch_dtype=torch.float32)
prompts = [f"Write one sentence about the number {i}." for i in range(16)]
NEW = 48

def generate(batch):
    inputs = tok(batch, return_tensors="pt", padding=True)
    model.generate(**inputs, max_new_tokens=NEW, min_new_tokens=NEW, do_sample=False, pad_token_id=tok.eos_token_id)

generate(prompts[:2])                                       # warm-up
for batch_size in [1, 4, 16]:
    start = time.perf_counter()
    for i in range(0, len(prompts), batch_size):
        generate(prompts[i:i + batch_size])
    elapsed = time.perf_counter() - start
    print(f"batch size {batch_size:>2}: {len(prompts) * NEW / elapsed:6.0f} tokens/s for 16 requests ({elapsed:.1f} s)")
```

```text
batch size  1:     19 tokens/s for 16 requests (39.6 s)
batch size  4:     36 tokens/s for 16 requests (21.1 s)
batch size 16:     98 tokens/s for 16 requests (7.8 s)
```

Serving the same 16 requests together is five times faster than one at a time, on the same hardware, because each forward pass does useful work for 16 sequences instead of one. On a GPU, where weight reads dominate even more, the gap at larger batch sizes is wider still.

<BaselineVsEngineDiagram />

But this experiment hides the hard part: every request here was forced to produce exactly 48 tokens. Real requests stop at different times, and that's where plain batching breaks down.

## 4. Continuous Batching

With ordinary (**static**) batching, a batch of requests starts together and the batch occupies the GPU until its *longest* request finishes. Short requests finish early and their slots sit empty; new requests wait for the whole batch. **Continuous batching** (also called in-flight or iteration-level batching, introduced by the Orca system in 2022) re-forms the batch at every decoding step: a finished sequence leaves immediately and a waiting request takes its slot at the next step.

This simulation runs 400 requests with realistic, heavy-tailed output lengths through both schedulers, with room for 8 sequences per step:

```python
import numpy as np

rng = np.random.default_rng(0)
BATCH = 8                                       # sequences the GPU decodes together per step
outputs = np.minimum(rng.lognormal(4.5, 1.0, 400).astype(int) + 1, 1_500)   # output lengths, heavy-tailed

def static_batching(lengths):
    """Batch fills, runs until its LONGEST sequence finishes, then the next batch starts."""
    steps, finish = 0, []
    for i in range(0, len(lengths), BATCH):
        batch = lengths[i:i + BATCH]
        finish += [steps + max(batch)] * len(batch)      # results returned when the batch ends
        steps += max(batch)
    return steps, np.array(finish)

def continuous_batching(lengths):
    """Iteration-level scheduling: a finished sequence leaves and a waiting one joins at the next step."""
    queue, running, steps, finish = list(lengths), [], 0, []
    while queue or running:
        while queue and len(running) < BATCH:
            running.append(queue.pop(0))
        steps += 1
        running = [r - 1 for r in running]
        finish += [steps] * sum(r == 0 for r in running)
        running = [r for r in running if r > 0]
    return steps, np.array(finish)

for name, fn in [("static batching", static_batching), ("continuous batching", continuous_batching)]:
    steps, finish = fn(outputs)
    print(f"{name:<20} {steps:>6} decode steps for {outputs.sum():,} tokens "
          f"(slot use {outputs.sum() / (steps * BATCH):.0%}), median completion at step {np.median(finish):,.0f}")
```

```text
static batching       21716 decode steps for 56,698 tokens (slot use 33%), median completion at step 9,362
continuous batching    7373 decode steps for 56,698 tokens (slot use 96%), median completion at step 3,500
```

Static batching keeps only a third of its slots busy, because every batch waits for its longest member; continuous batching keeps 96% busy, generates the same tokens in a third of the steps, and returns the median request almost three times sooner. Since a decode step costs roughly the same however many slots are filled, slot use translates directly into throughput and cost per token.

## 5. Paged KV Memory

Continuous batching needs memory for whichever requests are running, and their KV caches grow by an unpredictable amount. Early servers reserved one contiguous block per request, sized for the maximum possible length, because a contiguous block can't grow in place. Most of that reservation is never used. **PagedAttention**, introduced with vLLM in 2023, borrows the operating system's solution: split the KV cache into fixed-size **blocks** (pages) of, say, 16 tokens, allocate blocks only as a sequence grows, and keep a per-sequence table mapping logical positions to physical blocks.

```python
import numpy as np

rng = np.random.default_rng(0)
MAX_LEN, BLOCK = 8_192, 16                      # context limit; page size in tokens
lengths = np.minimum(rng.lognormal(6.5, 1.0, 1_000).astype(int) + 50, MAX_LEN)   # real sequence lengths

used = lengths.sum()
contiguous = len(lengths) * MAX_LEN             # reserve the maximum for every request up front
paged = (np.ceil(lengths / BLOCK) * BLOCK).sum()   # allocate fixed-size blocks as the sequence grows
print(f"median sequence {np.median(lengths):,.0f} tokens; tokens actually stored {used:,}")
print(f"contiguous max-length reservation: {contiguous:,} slots, {used / contiguous:.1%} used")
print(f"paged blocks of {BLOCK} tokens:      {paged:,.0f} slots, {used / paged:.1%} used")
```

```text
median sequence 666 tokens; tokens actually stored 1,055,109
contiguous max-length reservation: 8,192,000 slots, 12.9% used
paged blocks of 16 tokens:      1,062,352 slots, 99.3% used
```

With an 8K context limit and a median sequence of 666 tokens, max-length reservation leaves 87% of KV memory empty; paging wastes under 1%, only the unfilled part of each sequence's last block. The memory saved becomes room for more concurrent requests, which (section 4) becomes throughput. Paging also enables **sharing**: sequences with the same prefix, such as a common system prompt, or parallel samples from one prompt, can point at the same physical blocks, copying only when they diverge. That's the basis of prefix caching, which SGLang's RadixAttention organizes as a tree of shared prefixes.

## 6. The Engines in 2026

The two ideas above are now table stakes; engines differ in performance tuning, hardware support, features and operational fit. As of late 2026:

| Engine | Strengths | Fits |
|---|---|---|
| **vLLM** | The broadest model and hardware support (NVIDIA, AMD, Intel, TPU and others), PagedAttention, prefix caching, OpenAI-compatible server, multi-LoRA, quantization, speculative decoding, a large community; the default backend of many platforms | The default choice for self-hosted serving |
| **SGLang** | RadixAttention prefix sharing, a fast scheduler, structured-output support; strong on multi-turn and prefix-heavy workloads such as agents | High-concurrency chat and agent traffic, shared-prefix workloads |
| **TensorRT-LLM** | NVIDIA's engine: compiled, fused kernels and the latest NVIDIA hardware features first | Maximum performance on NVIDIA GPUs, accepting a heavier build process |
| **NVIDIA Dynamo** | A distributed serving framework over engines such as vLLM, SGLang and TensorRT-LLM, with KV-aware routing and prefill-decode disaggregation | Large multi-node deployments |
| **llama.cpp** | C/C++, runs quantized GGUF models on CPUs, Apple Silicon and consumer GPUs; the basis of Ollama and LM Studio | Local, edge and CPU deployments |
| **Hugging Face TGI** | Formerly a common production server | In maintenance mode since December 2025; Hugging Face recommends vLLM or SGLang for new deployments |

For general-purpose or non-LLM models served next to LLMs, **Dynamo-Triton** (formerly Triton Inference Server) and **ONNX Runtime** remain the multi-framework options; [APIs & Model Serving](/docs/mlops/model-serving#7-serving-frameworks) covers them.

**Choosing.** Start with vLLM unless there's a reason not to. Benchmark SGLang if your traffic shares long prefixes or is multi-turn at high concurrency, and TensorRT-LLM if you're committed to NVIDIA hardware and need the last increment of performance. Benchmark on *your* model, quantization, GPU and request mix, measuring time to first token, time per output token and throughput at your target concurrency; published benchmarks change with every release and rarely match a given workload.

**How to run that benchmark.** Replay a sample of real requests, or synthetic ones with the same distribution of prompt and output lengths, against the engine at increasing concurrency (1, 4, 16, 64 in-flight requests), using the engines' own benchmark scripts or a load generator such as GuideLLM or LLMPerf. At each level record p50 and p99 time to first token, p50 and p99 time per output token, and total output tokens per second. Throughput rises with concurrency until the GPU saturates, while latency stays flat and then climbs steeply; the useful operating point is the highest concurrency at which both latency percentiles still meet your targets, sometimes called **goodput**: throughput counting only requests that met the latency target. Repeat with prefix caching on and off, and with your real quantization, because each changes the curve. Keep the results with the engine version and configuration, since an engine upgrade can move the curve noticeably in either direction.

<GoDeeper title="Go deeper: what else the engines do">

Beyond continuous batching and paging, modern engines implement a stack of further optimizations, most covered in [LLM Inference Optimization](/docs/mlops/llm-inference-optimization):

- **Chunked prefill** splits a long prompt's prefill into pieces interleaved with other requests' decode steps, so one huge prompt doesn't stall everyone else's token stream.
- **Prefix caching** keeps KV blocks of common prefixes across requests, skipping their prefill entirely.
- **Speculative decoding** uses a small draft model, or extra prediction heads, to propose several tokens that the large model verifies in one pass.
- **Quantization** of weights (8- and 4-bit) and of the KV cache (FP8) cuts memory and raises throughput.
- **Parallelism** across GPUs: tensor parallelism inside a node, pipeline and expert parallelism across nodes for very large and mixture-of-experts models.
- **Structured output** constrains decoding to a grammar or JSON schema, so outputs always parse.
- **CUDA graphs** capture the sequence of GPU kernel launches for a decode step and replay it, removing per-step launch overhead, which matters most for small batches.

</GoDeeper>

## 7. On-Device and Edge Inference

A different target altogether: running the model on the user's phone, laptop or an embedded device, with no server.

<EdgeVsServerDeploymentDiagram />

Throughput barely matters there, since there's one user and one request at a time. What matters is fitting in limited memory, power draw, and latency on modest hardware, in exchange for privacy (data never leaves the device), offline use and zero per-request cost. The common runtimes, chosen by platform:

- **llama.cpp** with 4- to 6-bit GGUF models, for broad CPU and GPU reach across operating systems.
- **MLX** on Apple Silicon, using its unified memory; **Core ML** for shipping models inside iOS and macOS apps, with access to the Neural Engine.
- **ExecuTorch** for PyTorch models on Android, iOS and embedded targets; **ONNX Runtime Mobile** and **LiteRT** (formerly TensorFlow Lite) as cross-platform alternatives.
- Operating-system models: both Apple and Google ship on-device models that applications can call through system APIs, which avoids bundling a model at all.

Small models (one to a few billion parameters), aggressive quantization and careful context limits are what make this practical.

## 8. When *Not* to Run an Inference Engine

| Situation | Better choice |
|---|---|
| Low volume, or still exploring which model to use | A hosted API; self-hosting pays once traffic is steady and high |
| A handful of internal users | A quantized model on existing hardware (llama.cpp, Ollama) or a managed endpoint |
| Prototyping a new model architecture | Plain PyTorch `generate()` until it works; adopt an engine once it supports the architecture |
| Embedding or classification models | A general serving framework or TEI; LLM engines are built for autoregressive generation |
| No one to operate GPU infrastructure | A managed endpoint or a hosted open-model API, which run these same engines for you |

## Remember

| Idea | In one line |
|---|---|
| Why engines | Sequential generation, wildly varying lengths, large per-request KV state |
| Vocabulary | Engine executes; serving framework exposes; platform hosts; fine-tuning framework trains |
| Batching | Same 16 requests: 19 tokens/s one at a time, 98 tokens/s batched |
| Continuous batching | Re-form the batch every step: slot use 33% to 96% in the simulation |
| Paged KV memory | Allocate fixed blocks as sequences grow: 13% to 99% of KV memory used |
| Engines in 2026 | vLLM default, SGLang for prefix-heavy traffic, TensorRT-LLM for peak NVIDIA performance; TGI is in maintenance |
| On-device | llama.cpp, MLX, Core ML, ExecuTorch; small quantized models |
