# Multi-Armed & Contextual Bandits

<ELI5>

The name comes from slot machines ("one-armed bandits") — imagine a row of them, each with a different, unknown payout rate, and you get a limited number of pulls total. Every pull teaches you a little about that one machine, but pulling it costs you the chance to learn about (or profit from) a different one instead. That's the entire problem: balancing trying machines you're unsure about against sticking with the one that's paid off so far, when you only find out a machine's true payout rate by actually pulling it.

</ELI5>

[RL Fundamentals](/docs/reinforcement-learning/rl-fundamentals) opened with an MDP: state, action, reward, *new state* — the loop repeats, and what happens next depends on where the agent ends up. A bandit is what's left when you delete the "new state" part entirely: one state, forever. Pick an action, get a reward, the world doesn't change underneath you, repeat. That sounds like a simplification, and it is one — but it's also the actual formal name for a problem this site has already described twice without naming it: [Reinforcement Learning — Overview](/docs/reinforcement-learning/overview) calls out "a recommender system choosing what to show a user across a session" as a real RL instance, and [ML System Design Case Studies — Cold Start](/docs/ml-system-design/case-studies#case-study-personalized-recommendations-for-a-50-million-item-catalog) describes "exploration strategies (deliberately show some uncertain-but-promising items to gather signal)" without ever calling it what it is. It's a bandit problem, and bandits are the actual production answer, not full MDP machinery.

## The Explore/Exploit Problem, Stripped to Its Purest Form

$k$ arms (options), each with an unknown, fixed reward distribution. Pull one arm per round, observe only that arm's reward, repeat for $T$ rounds. **Regret** is the formal way to score a strategy: the gap between what you'd have earned always pulling the single best arm (known only in hindsight) and what your strategy actually earned. A strategy that keeps trying to learn forever (never fully commits to the best arm) accumulates regret linearly, forever — the entire game is finding a strategy whose regret grows *sublinearly*, so it effectively "solves" the problem given enough time.

Three real strategies, run against the same fixed 3-arm bandit, real cumulative regret, not illustrative curves:

<BanditRegretRaceDiagram />

- **ε-greedy**: with probability $\varepsilon$, pick a random arm (explore); otherwise pick the current best-estimated arm (exploit). Simple, but $\varepsilon$ never decays in this version — it keeps exploring at a constant rate forever, which is exactly why its regret line never stops climbing at roughly the same rate: a real, structural property, not a tuning artifact.
- **UCB1 (Upper Confidence Bound)**: pick $\arg\max_a \left[ \hat{Q}(a) + \sqrt{\dfrac{2\ln t}{N(a)}} \right]$ — an arm's estimated value *plus* a bonus that shrinks as that arm gets pulled more (and grows for arms that haven't been tried in a while) — "optimism in the face of uncertainty." The bonus term is provably enough to guarantee **logarithmic** regret, which is what the diagram's flattening UCB1 curve actually is, not an approximation of it.

<GoDeeper title="Go deeper: why that specific √(2 ln t / N(a)) term, and not some other bonus?">

The bonus comes directly from **Hoeffding's inequality**, a real concentration bound: for $N(a)$ independent samples of a value bounded in $[0,1]$, the true mean $Q(a)$ and the sample mean $\hat Q(a)$ satisfy $P\big(Q(a) > \hat Q(a) + \epsilon\big) \le e^{-2N(a)\epsilon^2}$ — the probability the true value exceeds the estimate by more than $\epsilon$ shrinks exponentially as more samples come in. Setting that failure probability to shrink at rate $t^{-4}$ (small enough that the total failure probability across all $t$ rounds, summed, still converges) and solving for $\epsilon$ gives exactly $\epsilon = \sqrt{2\ln t / N(a)}$ — the bonus isn't a tuned hyperparameter, it's the $\epsilon$ that makes "the true value is above my upper confidence bound" a genuinely rare event at every round simultaneously. That's the actual mechanism behind "optimism in the face of uncertainty": UCB1 acts as if every arm's true value equals its upper confidence bound, which is very likely to either be roughly correct (informative) or get corrected fast (the bound shrinks the moment that arm gets pulled again) — and it's this same Hoeffding argument, applied per-round, that sums to the provable $O(\log t)$ regret bound.

</GoDeeper>
- **Thompson Sampling**: maintain a Beta$(\alpha, \beta)$ posterior per arm (starting at Beta$(1,1)$, the uniform prior), sample once from each arm's posterior, pull whichever arm's sample is highest, then update that arm's posterior — Beta$(\alpha+1, \beta)$ on a win, Beta$(\alpha, \beta{+}1)$ on a loss. A genuinely Bayesian answer to the same question UCB1 answers with a hand-derived bound.

Worth sitting with what the diagram actually shows, because it's a real, slightly counter-intuitive result, not a foregone conclusion: **UCB1 looks worse than plain ε-greedy for a long stretch.** Its $\sqrt{2\ln t}$ confidence bound front-loads exploration hard. Only once the horizon gets long enough for "regret grows like $\log t$" to actually beat "regret grows like $t$" does UCB1 pull ahead — watch it happen by dragging the horizon slider past a few thousand pulls. Thompson Sampling, in this run and in the empirical literature generally, wins throughout — a big part of why it's the default choice in most real deployed bandit systems today, despite UCB1's cleaner textbook regret proof.

### Run It Yourself: The Three Strategies on One Bandit

Three arms with click rates 0.30, 0.50 and 0.55, 3,000 pulls, averaged over 10 seeds. Epsilon-greedy (with $\varepsilon = 0.1$) ends with a regret of about 47 and puts 85% of its pulls on the best arm. UCB1 is worse at this horizon, about 79, because its confidence bonus still pays for exploring arm 1, whose rate is only 0.05 below the best. Thompson sampling ends near 21 and spends 91% of pulls on the best arm.

<RunnableCode code={`import numpy as np

true_p = np.array([0.30, 0.50, 0.55])     # click rates of three arms; arm 2 is best
T, runs = 3_000, 10

def run(strategy, seed):
    rng = np.random.default_rng(seed)
    k = len(true_p)
    n, wins = np.zeros(k), np.zeros(k)
    regret = 0.0
    for t in range(1, T + 1):
        if strategy == "eps-greedy":
            a = rng.integers(k) if rng.random() < 0.1 else int(np.argmax(wins / np.maximum(n, 1)))
        elif strategy == "ucb1":
            if t <= k:
                a = t - 1
            else:
                a = int(np.argmax(wins / n + np.sqrt(2 * np.log(t) / n)))
        else:  # thompson
            a = int(np.argmax(rng.beta(wins + 1, n - wins + 1)))
        r = rng.random() < true_p[a]
        n[a] += 1; wins[a] += r
        regret += true_p.max() - true_p[a]
    return regret, n[2] / T

for s in ("eps-greedy", "ucb1", "thompson"):
    res = np.array([run(s, seed) for seed in range(runs)])
    print(f"{s:10}  mean regret after {T} pulls: {res[:, 0].mean():6.1f}   share of pulls on best arm: {res[:, 1].mean():.2f}")

# Try it: change true_p to [0.30, 0.54, 0.55]. The top two arms are nearly
# tied, so the share of pulls on the best arm drops to about 0.6, yet regret
# falls for every strategy, because each wrong pull now costs only 0.01.`} />

## Contextual Bandits: When "Which Arm" Depends on Who's Asking

Plain multi-armed bandits assume every round is the same decision — but a real recommendation isn't "which of these 5 articles is best, in general," it's "which of these 5 articles is best *for this specific user, right now*." **Contextual bandits** add a feature vector $x_t$ (user features, time of day, device, whatever context is available) at each round, and the reward model becomes a function of that context, not a fixed per-arm constant.

**LinUCB** is the standard, still-deployed answer: model each arm's expected reward as *linear* in the context, $\mathbb{E}[r \mid x, a] = x^\top \theta_a$, and extend UCB1's same "estimate plus confidence bound" logic into that linear model — pick the arm maximizing $x^\top \hat\theta_a + \alpha \sqrt{x^\top A_a^{-1} x}$, where $A_a^{-1}$ (the inverse of that arm's running feature-covariance matrix) is what makes the confidence bound shrink specifically in the directions of feature space that arm has actually been tested in, not just shrink overall the more it's pulled.

This isn't a hypothetical: [Li, Chu, Langford & Schapire's original LinUCB paper](https://arxiv.org/abs/1003.0146) (WWW 2010) ran it against 33 million real events from Yahoo's Front Page Today Module and measured a **12.5% click-through lift** over a context-free bandit baseline — the concrete, quantified value of "which arm" actually depending on context, not just in theory.

## Why Not Just Use Full RL?

Nothing stops you from modeling a recommendation problem as a full MDP with states — but if the "state" you'd define doesn't actually carry forward any consequence from action to action (showing user A article 3 today doesn't change what article is best for user B tomorrow, or even for user A tomorrow, if there's no real session-to-session memory being modeled), you're paying for machinery — Bellman backups, discounting, credit assignment across time steps — that isn't solving anything a bandit doesn't already solve, at real algorithmic and engineering cost. The dividing line is concrete: if the current round's outcome depends on the current round's context and nothing else's action history, it's a bandit problem, however sophisticated the context; the moment an action today provably changes what's optimal in a *future* round beyond just refining the context, that's genuinely sequential, and you're back to [RL Fundamentals](/docs/reinforcement-learning/rl-fundamentals)' full MDP.

## Evaluating a New Policy From Logged Data

A bandit in production logs every decision: the context, the arm shown, the reward, and the probability with which the logging policy chose that arm. That last number makes it possible to estimate how a *different* policy would have done, without deploying it. **Inverse propensity scoring** (IPS) reweights each logged round by $\pi_{\text{new}}(a \mid x) / \pi_{\text{log}}(a \mid x)$: rounds where the old policy chose what the new one would choose count more, the rarer the old policy made that choice.

In the example below the old policy showed article 0 90% of the time and each other article 5% of the time, for a logged click rate of 0.040. Evaluating "always show article 1" uses only the 2,482 rounds that showed it, each with weight 20, and estimates 0.055 against a true 0.060. The variance comes from those large weights, and it is why logging policies keep some exploration: an arm the old policy never shows can never be evaluated.

<RunnableCode code={`import numpy as np

# Off-policy evaluation with inverse propensity scoring (IPS).
# Logged data came from an epsilon-greedy policy that showed article 0 most of the time.
rng = np.random.default_rng(5)
true_ctr = np.array([0.04, 0.06, 0.05])
k, n, eps = 3, 50_000, 0.15

logging_probs = np.full(k, eps / k)
logging_probs[0] += 1 - eps                # P(show 0) = 0.90, others 0.05 each
actions = rng.choice(k, size=n, p=logging_probs)
clicks = rng.random(n) < true_ctr[actions]

# New policy to evaluate offline: always show article 1
def target_prob(a):
    return (a == 1).astype(float)

w = target_prob(actions) / logging_probs[actions]   # importance weights
ips = np.mean(w * clicks)
naive = clicks.mean()
print(f"logged click rate (old policy):   {naive:.4f}")
print(f"IPS estimate for 'always show 1': {ips:.4f}   true value {true_ctr[1]:.4f}")
print(f"logged rounds that showed 1: {int((actions == 1).sum())} of {n}; each carries weight {1 / logging_probs[1]:.0f}")

# Try it: set eps = 0.0. Article 1 is never logged, every weight is zero,
# and IPS estimates 0: you cannot evaluate an action the old policy never took.`} />

## Common Problems & Fixes

| Problem | Cause | Fix |
| --- | --- | --- |
| A once-best arm keeps winning after it got worse | Rewards change over time | Discount old observations or use a sliding window |
| Estimates are biased towards fast feedback | Rewards arrive hours later | Delayed-feedback corrections; update on a schedule |
| New items never get shown | Exploitation dominates; no prior | Optimistic priors for new arms; a minimum exploration rate |
| Offline estimates swing wildly | Large importance weights | Clip weights, use self-normalised IPS or doubly robust estimators |
| Clicks go up, long-term satisfaction goes down | Click is a proxy reward | Reward a later signal, such as dwell time or retention |

## When *Not* to Use It

| Situation | Better choice |
| --- | --- |
| Today's action changes tomorrow's options | Full RL with states; see [RL Fundamentals](/docs/reinforcement-learning/rl-fundamentals) |
| Two variants, a fixed decision date, and a need for clean statistics | A classic A/B test |
| Hundreds of thousands of arms | A learned ranking model with exploration on top |
| No way to observe the reward | Bandits need feedback on every round |

## Remember

| Idea | One line |
| --- | --- |
| Bandit | An MDP with a single state: act, get reward, repeat |
| Regret | Best-arm reward minus what you earned, summed over rounds |
| Epsilon-greedy | Constant exploration gives linear regret |
| UCB1 | Estimate plus $\sqrt{2 \ln t / N}$; logarithmic regret |
| Thompson sampling | Sample from each arm's posterior, play the best sample |
| LinUCB | Linear reward in the context, plus a confidence bound in feature space |
| IPS | Reweight logged rewards by new over old action probability |
| Propensity | Log it on every decision, or offline evaluation is impossible |
