# Vision Tasks & Models

<ELI5>

Show a photo to five people and ask five different questions: what is it, where are the people, where are their elbows, what does the sign say, how far away is the wall. Each question needs a different kind of answer: a word, boxes, dots, text, a distance per pixel. Computer vision is that list of questions, and each one has its own kind of model.

</ELI5>

## Why This Exists

"Computer vision" is not one task. It is a family of problems that share an image as input but differ in what they must output, and the output shape decides the model. A classifier returns one label; a pose model returns a fixed set of points per person; a tracker must return the *same* ID for the same object across hundreds of frames; a depth model returns a number for every pixel. This page covers the tasks beyond the core three, explains the mechanism each one depends on, and works two of them (tracking and stereo depth) through with real numbers, because those two are where most production bugs live.

## The Core Three (Recap)

These are covered in full in [Vision Architectures](/docs/deep-learning/vision-architectures):

- **Classification** assigns one label to a whole image. It is the original CNN task, from LeNet to ConvNeXt (see [CNNs](/docs/deep-learning/cnns)).
- **Detection** finds and labels several objects as bounding boxes: the R-CNN family, YOLO, SSD, DETR.
- **Segmentation** labels every pixel. Semantic segmentation gives a class per pixel; instance segmentation also separates individual objects (U-Net, Mask R-CNN).

## Pose Estimation

Pose estimation locates fixed keypoints on a subject, most often the 17 human joints of the COCO keypoint format (nose, eyes, shoulders, elbows, wrists, hips, knees, ankles). Models usually predict one heatmap per keypoint and take the peak. There are two ways to handle several people:

- **Top-down** detects each person first, then runs a pose model on each crop. Accuracy per person is high, but cost grows with the number of people.
- **Bottom-up** finds every keypoint in the image in one pass, then groups them into skeletons (OpenPose uses part affinity fields for the grouping). Cost stays roughly constant however crowded the frame is, at the price of a harder grouping step.

<PoseEstimationApproachDiagram />

Pose accuracy is measured with object keypoint similarity (OKS), which scores each keypoint's error relative to the person's size and to how precisely humans can annotate that joint. A 10-pixel error on a hip counts for less than on an eye.

## OCR (Optical Character Recognition)

OCR is two problems in sequence:

- **Text detection** finds where text is, as boxes or polygons around words or lines.
- **Text recognition** reads the characters in each crop. The classic recogniser is a CNN followed by a recurrent layer trained with CTC loss, which learns a character sequence without needing each character's position labelled. Newer recognisers (TrOCR) treat it as image-to-text generation with a transformer.

<OcrPipelineDiagram />

For documents with tables and forms, layout matters as much as characters, and end-to-end models increasingly read the page in one pass. General VLMs (see [Modern Vision & Multimodal](/docs/computer-vision/modern-vision-and-multimodal)) can do this too, but a dedicated OCR model is still cheaper and more exact on plain scanned text.

## Object Tracking

A tracker keeps a consistent identity for each object across video frames: the car in frame 47 is the same car as in frame 12. The standard design is **tracking by detection**. Run a detector on every frame, then solve an **association** problem: match this frame's detections to the existing tracks.

<TrackingAssociationDiagram />

### A Full Worked Example: Matching by IoU

SORT, the classic tracker, scores every (track, detection) pair by intersection over union (IoU) and picks the one-to-one assignment with the highest total, using the Hungarian algorithm. Take two tracks and three new detections. Track `car_7` overlaps detection 1 with IoU 0.746; `car_9` overlaps detection 0 with IoU 0.737; detection 2 overlaps nothing. Both matches clear SORT's threshold of 0.3, and detection 2 starts a new track.

Now suppose `car_7` moved fast and its new box is 80 pixels to the right. Its IoU with the old box drops to 0.111, the match is rejected, and the tracker ends `car_7` and starts a new ID for the same car: an **ID switch**. SORT's answer is a Kalman filter that predicts where each box should be from its velocity, and compares detections against the prediction instead of the last position. DeepSORT adds an appearance embedding, so a car that disappears behind a truck can be recognised when it comes back.

<RunnableCode code={`import numpy as np
from itertools import permutations

# Boxes are (x1, y1, x2, y2). Two tracks from frame t, three detections in frame t+1.
tracks = {"car_7": (100, 100, 200, 180), "car_9": (300, 120, 380, 190)}
detections = [(305, 125, 388, 196), (108, 104, 210, 186), (500, 50, 540, 90)]

def iou(a, b):
    ix = max(0, min(a[2], b[2]) - max(a[0], b[0]))
    iy = max(0, min(a[3], b[3]) - max(a[1], b[1]))
    inter = ix * iy
    area = lambda r: (r[2] - r[0]) * (r[3] - r[1])
    return inter / (area(a) + area(b) - inter)

names = list(tracks)
M = np.array([[iou(tracks[n], d) for d in detections] for n in names])
print("IoU matrix (rows = tracks, cols = detections):\\n", np.round(M, 3))

# Best one-to-one assignment. SORT uses the Hungarian algorithm; with 2 tracks
# we can simply try every assignment.
best = max(permutations(range(len(detections)), len(names)),
           key=lambda cols: sum(M[r, c] for r, c in enumerate(cols)))
IOU_MIN = 0.3
for r, c in enumerate(best):
    ok = M[r, c] >= IOU_MIN
    print(f"{names[r]} -> detection {c}  IoU {M[r, c]:.3f}  {'matched' if ok else 'rejected'}")
unmatched = set(range(len(detections))) - set(best)
print("unmatched detections start new tracks:", sorted(unmatched))

# Try it: move detection 1 to (180, 100, 280, 180), as if car_7 moved fast.
# Its IoU with car_7 drops below 0.3, so the match is rejected; this is why
# SORT adds a Kalman filter to predict where each box should be.`} />

## Depth Estimation

Depth estimation predicts how far each pixel is from the camera.

**Stereo depth** uses two cameras a known distance apart (the baseline $B$). A point appears shifted between the two images by a disparity $d$ pixels, and by similar triangles its depth is

$$
Z = \frac{f B}{d}
$$

where $f$ is the focal length in pixels. Learning is only needed to find which pixels correspond; the depth itself is geometry.

<StereoDepthDiagram />

### Run It Yourself: How Stereo Error Grows With Distance

With $f = 700$ pixels and $B = 0.12$ m (a typical small stereo camera), a disparity of 84 pixels means 1 m and 8.4 pixels means 10 m. Differentiating $Z = fB/d$ gives an error of about $Z^2 / (fB)$ per pixel of disparity error: 1 cm at 1 m, but 1.19 m at 10 m.

**Monocular depth** predicts depth from a single image. In principle this is impossible, since one image fits infinitely many 3D scenes, so networks learn strong priors from images paired with measured depth. Models such as MiDaS and Depth Anything predict *relative* depth (which pixel is nearer), which is enough for portrait-mode blur; metric depth in metres needs either camera information or fine-tuning on metric data.

## Optical Flow

Optical flow estimates per-pixel motion between two frames: a vector $(dx, dy)$ for every pixel. Classical methods (Lucas-Kanade, Horn-Schunck) assume a point keeps its brightness between frames and solve for the motion that best explains the pixel changes. That assumption breaks under large motion, occlusion and lighting change. RAFT instead builds a correlation volume between all pixel pairs and refines the flow with a recurrent update, and it is far more accurate on those hard cases. Flow is used in video compression, frame interpolation and action recognition, and as a motion cue for tracking.

<GoDeeper title="Go deeper: why the Hungarian algorithm, and not greedy matching?">

Greedy matching takes the highest-IoU pair, removes both, and repeats. It is fast but can be wrong. Suppose track A overlaps detection 1 at 0.6 and detection 2 at 0.5, and track B overlaps only detection 1, at 0.55. Greedy matches A to 1 (0.6), and B is left with nothing. The optimal assignment matches A to 2 and B to 1, for a total of 1.05 instead of 0.6, and keeps both tracks alive. The Hungarian algorithm finds the optimal assignment in $O(n^3)$ time, which is negligible for the tens of objects in a typical frame. ByteTrack adds a second matching pass for low-confidence detections, which recovers objects that are partly occluded.

</GoDeeper>

## Common Problems & Fixes

| Problem | Cause | Fix |
| --- | --- | --- |
| IDs switch when objects move fast | Low IoU between frames | Kalman prediction (SORT); higher frame rate |
| IDs switch after occlusion | Track dropped while hidden | Appearance embeddings (DeepSORT); keep lost tracks for a few frames |
| Pose fails in crowds | Top-down crops overlap | Bottom-up grouping, or better person detection |
| Stereo depth is noisy far away | Error grows with $Z^2$ | Wider baseline, higher resolution, or LiDAR at long range |
| Monocular depth has the wrong scale | Model predicts relative depth | A metric depth model, or scale from a known object |

## When *Not* to Use It

| Situation | Better choice |
| --- | --- |
| Static camera, slow objects | Simple IoU tracking without appearance models |
| Accurate long-range depth | LiDAR or radar, not stereo |
| Reading a few fields from one known form | Template matching plus OCR on fixed regions |
| Open-ended questions about an image | A vision-language model |

## Remember

| Idea | One line |
| --- | --- |
| Pose | Heatmap per keypoint; top-down vs bottom-up for crowds |
| OCR | Detect text regions, then recognise characters (CTC or seq2seq) |
| Tracking by detection | Detect every frame, then associate |
| Association | IoU matrix plus Hungarian assignment, threshold 0.3 in SORT |
| ID switch | The failure that matters most; Kalman and appearance features fix it |
| Stereo | $Z = fB/d$; error grows with $Z^2$ |
| Monocular depth | Learned priors; relative unless trained for metric |
| Optical flow | Dense per-pixel motion; RAFT for hard cases |
