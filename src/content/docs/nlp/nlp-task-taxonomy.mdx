# NLP Task Taxonomy

Every major NLP task predates Transformers, and every one of them is now dominated by Transformer-based approaches — but the classical approach to each is worth knowing, both for historical grounding and because classical methods are sometimes still the right, cheaper tool for a well-defined production task.

## Intuition: Constrained vs. Open-Ended Output

The tasks on this page split cleanly along one axis: does the model select from a fixed, small set of outputs (sequence labeling, classification, extractive QA), or does it generate genuinely new text (translation, abstractive summarization, generative QA)? Constrained tasks are structurally safer — a classifier can't hallucinate a label that doesn't exist, extractive QA can't hallucinate an answer not present in the source — at the cost of being unable to produce anything the fixed output space doesn't already contain. Every classical/modern contrast below is really a version of this same trade-off.

## Sequence Labeling

The general framing behind [POS tagging and NER](/docs/nlp/classical-nlp): assign a label to every token in a sequence, where the labels of nearby tokens are dependent on each other (not independent per-token classification). Classical: **HMMs/CRFs**, modeling the label sequence's transition structure explicitly (see the real Viterbi decode on [Classical NLP](/docs/nlp/classical-nlp#part-of-speech-pos-tagging)). Modern: a BiLSTM or Transformer encoder with a classification head per token, letting the model learn label dependencies implicitly through its own representations rather than an explicit transition matrix.

## Text Classification & Sentiment Analysis

Assigning a label (or set of labels) to an entire document/sentence rather than per-token. Classical: bag-of-words or TF-IDF features feeding a [Logistic Regression](/docs/machine-learning/logistic-regression), [Naive Bayes](/docs/machine-learning/naive-bayes-lda-qda), or [SVM](/docs/machine-learning/support-vector-machines) classifier. Still a completely reasonable, fast, interpretable baseline for well-scoped classification tasks with limited labeled data. Modern: fine-tuning a BERT-style encoder (see [Attention & Transformers](/docs/deep-learning/attention-transformers#encoder-only-the-bert-lineage)) or prompting an LLM directly (see [Prompt Engineering](/docs/llms-genai/prompt-engineering)) — better accuracy, especially on nuanced/context-dependent sentiment (exactly the negation-scope case above), at higher compute cost per prediction.

### Classifying With an LLM

**What it is.** A fine-tuned classifier has a fixed set of labels baked into its output layer. An LLM can classify into labels it has never seen, because the labels arrive as text in the input. There are three common ways to get the label out, and they behave differently.

**How it works.**

1. **Generate.** List the labels in the prompt and ask the model to answer with one of them. Parse the reply. Simple, and it works with any chat API, but the reply can be a label that isn't on the list, or a sentence instead of a label, and there is no probability attached unless you ask for one (and a probability the model writes as text is usually not calibrated).
2. **Score each label.** Run the model once per label and read the log-probability it assigns to that label's text, or ask an entailment model whether "This text is about *label*" follows from the input ([Yin, Hay and Roth, 2019](https://arxiv.org/abs/1909.00161)). Softmax over the scores gives a distribution over exactly the allowed labels, so off-list answers are impossible. The cost is one forward pass per label.
3. **Embed and compare.** Encode the input and each label separately with a [bi-encoder](/docs/llms-genai/retrieval-and-reranking-architectures#bi-encoder-independent-encoding-pooled-to-one-vector) and pick the nearest label. Label embeddings are computed once and reused for every request, which makes this the cheapest option at large label counts, but the input and the labels never interact before the final dot product, so fine distinctions suffer.

**Why it matters.** The choice decides what you can promise downstream code. Methods 2 and 3 always return a valid label and a number you can threshold. Method 1 needs validation and a retry path. Method 3 is the only one whose cost barely grows as the label set grows.

**Where it stops working.**

- **Order bias.** When labels are listed as A, B, C, D in a prompt, models prefer some letters regardless of content. [Zheng et al. (2023)](https://arxiv.org/abs/2309.03882) found this selection bias in 20 LLMs and traced it mainly to the model's prior over the option letters. Shuffle the options on a sample of your data and check whether answers change.
- **No "none of these".** A softmax over the supplied labels always sums to one, so it ranks the labels against each other and says nothing about whether any of them fits. You need a separate threshold, or an explicit "other" class that is calibrated on held-out data.
- **Uncalibrated scores.** Log-probabilities from a generative model are rarely calibrated out of the box. Check them with a reliability diagram and recalibrate as described in [Model Evaluation & Metrics](/docs/machine-learning/model-evaluation-metrics#4-judging-probabilities-proper-scoring-and-calibration).

Newer **decision models** build these properties into the architecture: options encoded independently so they can be cached, an order-independent aggregation step, and a separate output for "no option fits". The blog post [Jeva and the decision model](/blog/jeva-decision-models) walks through one such design.

**Remember:** an LLM classifier is only as reliable as the way you read the label out of it; prefer scoring a fixed label set over parsing free text, and test for order bias before trusting it.

## Machine Translation

Translating text from one language to another — the task that originally motivated the encoder-decoder Transformer architecture ([Attention & Transformers — The T5 Lineage](/docs/deep-learning/attention-transformers#encoder-decoder-the-t5-lineage)):

- **Statistical Machine Translation (SMT)**: pre-neural approaches built from explicit translation probability tables (phrase-to-phrase translation likelihoods learned from parallel corpora) combined with a language model scoring fluency — a pipeline of separately-optimized components, not end-to-end trained.
- **Neural Machine Translation (NMT)**: end-to-end sequence-to-sequence models (originally RNN encoder-decoder with attention, see [Sequence Models — Seq2Seq with Attention](/docs/deep-learning/sequence-models#named-variants-worth-knowing), now Transformer encoder-decoder) trained directly on parallel text — a single model learns the entire mapping, substantially outperforming SMT's pipeline once enough training data and compute were available.
- **Evaluation**: **BLEU** (n-gram precision overlap against reference translations) remains the standard automatic metric despite well-known limitations. Real BLEU-style precision, computed live, on exactly the case that exposes the limitation:

## Summarization

- **Extractive summarization**: select and concatenate existing sentences/phrases directly from the source document — guaranteed factually grounded, but can read disjointedly since it's a selection, not a composition.
- **Abstractive summarization**: generate genuinely new sentences that convey the source's meaning — reads more naturally, but introduces real risk of hallucination. Toggle between the two on the same source below — one of them contains a deliberately planted factual error, exactly the faithfulness/groundedness concern covered in [LLM Evaluation & RAGOps](/docs/mlops/llm-evaluation-and-ragops):

Modern LLMs perform abstractive summarization by default when prompted to summarize — the extractive/abstractive distinction remains relevant for understanding *why* a summary might be unfaithful to its source (an abstractive method structurally can be, an extractive one structurally cannot).

## Question Answering

- **Extractive QA**: given a question and a passage, identify the exact span of the passage that answers it — framed as predicting a start and end token position, a structurally different (and simpler, more constrained) task than free-form generation. - **Generative/open-domain QA**: generate a free-form answer, potentially synthesizing information across multiple sources or requiring knowledge not explicitly present in any single retrieved passage — the task framing behind [RAG](/docs/llms-genai/rag), which combines retrieval (find relevant passages) with generative QA (compose an answer from them) rather than either extractive matching or ungrounded generation alone.

## Code: A Real Extractive-QA Span Predictor

The exact computation the diagram above runs, in the form a real fine-tuned model's head actually takes:

```python
import torch
import torch.nn.functional as F

def predict_span(start_logits: torch.Tensor, end_logits: torch.Tensor, tokens: list[str]) -> str:
    start_probs = F.softmax(start_logits, dim=-1)
    end_probs = F.softmax(end_logits, dim=-1)
    start_idx = torch.argmax(start_probs).item()
    end_idx = torch.argmax(end_probs).item()
    return " ".join(tokens[start_idx:end_idx + 1])  # can only ever point INTO the passage
```
