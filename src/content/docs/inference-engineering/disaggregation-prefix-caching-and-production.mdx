# Disaggregated Serving, Prefix Caching & Distributed Inference

When scaling LLMs to thousands of concurrent users, traditional monolithic serving engines hit a fundamental physical bottleneck: **the structural conflict between Prefill and Decode**.

Prefill is compute-bound, processing thousands of input tokens in parallel with high operational intensity. Decode is memory-bandwidth bound, generating one token at a time with near-zero operational intensity. When both run on the same GPU, long prefills cause severe **head-of-line blocking**, inducing massive Inter-Token Latency (ITL) jitter for active users.

In this chapter, we engineer the modern distributed serving architectures that solve this bottleneck: **Prefill-Decode (PD) Disaggregation**, **Radix Tree Prefix Caching**, and **Topology-Aware Model Parallelism** (Tensor, Pipeline, and Expert Parallelism for frontier MoE architectures).

<ELI5>

Imagine a high-end coffee shop that only has one worker. One customer orders 50 catered drinks for an office meeting (a giant prompt / prefill), while five other customers are standing in line waiting for a single sip of espresso (token decoding). If the barista stops to brew all 50 catered drinks, the five espresso drinkers wait 20 minutes for their next sip.

**Disaggregated Serving** separates the shop into two specialized stations: a high-capacity brewing station dedicated solely to large catering orders (Prefill nodes), and rapid-fire espresso machines dedicated solely to pouring one cup at a time (Decode nodes). The brewing station makes the coffee concentrate (KV cache) and pipes it across the counter (over high-speed NVLink/RDMA) to the espresso team.

**Prefix Caching** is having pre-brewed signature blends ready to pour: if 100 customers order the exact same specialty drink (shared system prompt or documents), the barista skips brewing entirely and serves it instantly.

</ELI5>

## Why This Exists

In traditional monolithic serving (e.g., standard vLLM or Hugging Face TGI), incoming requests enter a shared continuous batch:

```
Monolithic Co-located Batch (Severe ITL Jitter):
Iter 1: [Req A: decode tok 12] [Req B: decode tok 45] [Req C: PREFILL 4,096 tokens!] 
         └───────────────────────┬──────────────────────────────────────────┘
                                 │
                   GPU Tensor Cores 100% saturated with GEMM;
                   Req A and Req B experience an ITL latency spike of 450ms!
```

### The Two Contrasting Regimes

| Metric / Attribute | Prefill Phase (Prompt Processing) | Decode Phase (Token Generation) |
| :--- | :--- | :--- |
| **Operational Bottleneck** | **Compute-Bound** (Matrix-Matrix GEMM) | **Memory-Bandwidth-Bound** (Matrix-Vector GEMV) |
| **Arithmetic Intensity** | High (~100 to 250 FLOP/byte) | Extremely Low (~1 to 2 FLOP/byte) |
| **Primary User Metric** | **Time-To-First-Token (TTFT)** | **Inter-Token Latency (ITL)** / Tokens-Per-Sec |
| **Optimal Hardware Setup** | High compute density, lower Tensor Parallelism | Maximum HBM bandwidth, higher Tensor Parallelism |

When a 4,096-token prefill shares a forward pass with ongoing decode requests, the forward pass time jumps from 15ms to 400ms. To the user reading streamed text, generation suddenly freezes, violating real-time streaming Service Level Objectives (SLOs).

## Prefill-Decode (PD) Disaggregated Serving Architecture

Disaggregated serving (pioneered by systems like Splitwise, DistServe, Mooncake, and NVIDIA Dynamo) physically splits the inference pipeline across specialized hardware nodes:

<DisaggregatedServingArchDiagram />

### How Disaggregation Works

1. **Prompt Ingestion**: The router receives an incoming prompt sequence.
2. **Dedicated Prefill Execution**: A prefill worker executes the full causal prompt pass in parallel, computing the prompt KV cache and sampling the first output token.
3. **KV Cache Transfer**: The prefill worker transfers the completed KV cache across the high-speed network fabric (InfiniBand, RoCE v2, or NVLink) directly into the decode worker's physical memory pool.
4. **Isolated Decode Loop**: The decode worker appends the first token, assumes ownership of the request, and performs continuous autoregressive decoding with zero compute interference.

### Conditional Disaggregation

In production clusters, transferring small KV caches introduces network serialization overhead. Systems use **Conditional Disaggregation**:
- **Short prompts ($< 256$ tokens)**: Executed locally on the decode worker to avoid network transfer latency.
- **Long prompts ($\ge 256$ tokens)**: Dispatched to dedicated prefill workers to protect decode workers from head-of-line blocking.

### Production Serving Configuration

To serve models with prefix caching and memory-bound optimizations in production, engineers launch `vllm` with explicit cache allocation flags:

```bash
# Production vLLM serving configuration with automatic prefix caching
vllm serve meta-llama/Llama-3.1-70B-Instruct \
  --tensor-parallel-size 4 \
  --enable-prefix-caching \
  --block-size 16 \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.92 \
  --swap-space 16 \
  --port 8000
```

## Radix Tree Prefix Caching

In agent workflows and multi-turn conversations, consecutive prompts share massive prefixes (system instructions, tool schemas, repository maps, and document context). Recomputing attention over 10,000 tokens of static prompt on every single turn burns GPU hours and increases TTFT.

Traditional LRU caches struggle with branching conversation histories: if two users branch from the same document, an LRU cache duplicates or evicts blocks.

### The Radix Tree Solution (SGLang & vLLM)

A **Radix Tree** (compressed trie) structures KV cache memory at token-sequence boundaries. Common prefixes are retained as tree nodes, and branching queries allocate new child nodes:

<RadixTreePrefixDiagram />

When an agent prompt arrives:
1. The engine tokenizes the input and traverses the Radix Tree.
2. Reusable KV cache blocks are matched and mapped directly into the GPU Page Table.
3. Only the non-overlapping token suffix is dispatched to Tensor Cores for prefill.
4. On a 10,000-token prompt with 9,500 tokens of cached prefix, **TTFT drops from 420ms to 15ms** (illustrative benchmark profile on an 8x H100 cluster; a 28× acceleration).

- **Turn 2 (Warm Turn)**: 3,004 total tokens ($1,000 + 2,000 + 4$). Cache hits: 3,000 tokens! Only 4 new tokens are computed. TTFT drops to 1.52 ms (**158× speedup**).

<RunnableCode code={`class RadixNode:
    def __init__(self, token_chunk):
        self.chunk = list(token_chunk)
        self.children = {}

class RadixPrefixCache:
    """Simulates a Radix Tree prefix cache with dynamic node splitting."""

    def __init__(self, cost_per_token_ms: float = 0.08):
        self.root = RadixNode([])
        self.cost_per_token_ms = cost_per_token_ms
        self.total_tokens_saved = 0
        self.total_tokens_processed = 0

    def query_and_insert(self, token_sequence):
        curr = self.root
        matched_tokens = 0
        remaining = list(token_sequence)

        while remaining:
            first_tok = remaining[0]
            if first_tok in curr.children:
                child = curr.children[first_tok]
                # Find common prefix length
                common = 0
                max_len = min(len(remaining), len(child.chunk))
                while common < max_len and remaining[common] == child.chunk[common]:
                    common += 1

                if common == len(child.chunk):
                    # Full child matched: advance deeper
                    matched_tokens += common
                    remaining = remaining[common:]
                    curr = child
                else:
                    # Partial match: split child node
                    matched_tokens += common
                    split_token = child.chunk[common]
                    split_child = RadixNode(child.chunk[common:])
                    split_child.children = child.children

                    child.chunk = child.chunk[:common]
                    child.children = {split_token: split_child}

                    remaining = remaining[common:]
                    curr = child
                    break
            else:
                break

        # Insert new branch for unshared suffix
        if remaining:
            new_node = RadixNode(remaining)
            curr.children[remaining[0]] = new_node

        total_seq_len = len(token_sequence)
        tokens_to_compute = total_seq_len - matched_tokens
        self.total_tokens_saved += matched_tokens
        self.total_tokens_processed += total_seq_len

        ttft_uncached_ms = total_seq_len * self.cost_per_token_ms
        ttft_cached_ms = (tokens_to_compute * self.cost_per_token_ms) + 1.2
        speedup = ttft_uncached_ms / max(ttft_cached_ms, 0.1)

        return {
            "total_tokens": total_seq_len,
            "cache_hit_tokens": matched_tokens,
            "tokens_computed": tokens_to_compute,
            "ttft_ms": round(ttft_cached_ms, 2),
            "baseline_ttft_ms": round(ttft_uncached_ms, 2),
            "speedup": round(speedup, 2)
        }

# Simulate realistic multi-turn agent interaction
system_prompt = [101, 2045, 3012, 4050, 1100] * 200 # 1,000 tokens
doc_context   = [5001, 5002, 5003, 5004] * 500       # 2,000 tokens
user_turn_1   = [9001, 9002, 9003]                   # 3 tokens
user_turn_2   = [9004, 9005, 9006, 9007]             # 4 tokens

cache = RadixPrefixCache(cost_per_token_ms=0.08)

print("=== Radix Prefix Caching Execution Log ===\\n")

# Turn 1: Cold start
prompt_1 = system_prompt + doc_context + user_turn_1
res1 = cache.query_and_insert(prompt_1)
print(f"Turn 1 -> Hit: {res1['cache_hit_tokens']} tok | TTFT: {res1['ttft_ms']}ms | Speedup: {res1['speedup']}x")

# Turn 2: Exact same system prompt + doc context + new query (Cache HIT!)
prompt_2 = system_prompt + doc_context + user_turn_2
res2 = cache.query_and_insert(prompt_2)
print(f"Turn 2 -> Hit: {res2['cache_hit_tokens']} tok | TTFT: {res2['ttft_ms']}ms | Speedup: {res2['speedup']}x")

hit_rate = (cache.total_tokens_saved / cache.total_tokens_processed) * 100
print(f"\\nAggregate Cache Efficiency: {hit_rate:.1f}% tokens reused from KV cache.")

## Common Problems & Fixes

1. **KV Cache Network Transfer Saturation**: RDMA networks choke when hundreds of concurrent requests transmit 32k-token KV caches simultaneously.
   - *Fix*: Compress KV tensors using FP8 quantization before network transfer, cutting serialization bytes by 50%.
2. **Cache Thrashing under Memory Pressure**: Under high concurrency, Radix tree eviction discards frequently used system prefixes.
   - *Fix*: Pin immutable system prompt nodes with a reference counter lock, preventing eviction regardless of LRU pressure.
3. **Imbalanced Worker Utilization**: Prefill workers sit idle during conversational turn waves, while decode workers become saturated.
   - *Fix*: Deploy dynamic role switching where idle prefill GPUs temporarily accept decode batches during peak conversational traffic.

<NotebookCallout color="green" title="Architectural Golden Rule">
Decouple compute-bound prefill from memory-bound decode. As context windows scale to 128k+ tokens, monolithic serving guarantees severe tail-latency violations. Deploy disaggregated architectures and Radix prefix caching to achieve deterministic, stable sub-20ms streaming latency.
</NotebookCallout>

## When *Not* to Use It

| Situation | Better Choice | Why |
| :--- | :--- | :--- |
| Single GPU workstation or local laptop serving | Monolithic serving (Ollama / llama.cpp) | Network disaggregation requires InfiniBand/RDMA fabrics; local setups have no network layer to disaggregate. |
| Short single-turn prompts (< 128 tokens) | Standard continuous batching | Prefill overhead is negligible; network transfer latency exceeds local compute time. |
| Completely random, unrepeated prompts | Standard vLLM without prefix caching | Prefix caching incurs tree traversal overhead without yielding any cache hits. |

## Remember

| Idea | Core Rule |
| :--- | :--- |
| **Prefill vs Decode** | Prefill is compute-bound (TFLOPS); decode is memory-bandwidth bound (GB/s). |
| **Disaggregation** | Split workers into dedicated prefill and decode pools connected by RDMA. |
| **Head-of-Line Blocking** | A 4k prefill in a monolithic batch spikes ITL latency from 15ms to 400ms. |
| **Radix Tree Cache** | Retain KV blocks in a prefix tree to eliminate redundant prefill compute. |
| **Conditional PD** | Execute prompts under 256 tokens locally on decode nodes to avoid network cost. |
