# Continuous Batching & Speculative Decoding

In cloud AI serving, static request batching introduces severe latency penalties: fast 10-token queries sit stranded in memory waiting for slow 1,000-token queries to complete, creating massive "inference bubbles" where GPUs burn energy transferring weights for half-empty batches.

This chapter details the two core algorithmic breakthroughs that solve this bottleneck: **Continuous Batching** (iteration-level scheduling) and **Speculative Decoding** (draft-verify acceleration).

<ELI5>

Imagine a restaurant where the kitchen refuses to serve anyone at a table until every single person has finished dessert. If one guest orders a 7-course meal while others just wanted a coffee, everyone is trapped sitting at the table for two hours. That is **Static Batching**.

**Continuous Batching** is a restaurant that brings the bill to the coffee drinker immediately, cleans the chair in 10 seconds, and seats a new guest right away, keeping every seat occupied at every minute.

**Speculative Decoding** is a clever waiter who knows you always order coffee after dinner: they bring the cup out before you even ask. If you wanted coffee, you save 5 minutes. If you say no, they take it back and bring tea, with zero harm done.

</ELI5>

## Why This Exists

Traditional deep learning frameworks (such as TorchServe or early Triton serving engines) inherited request batching paradigms from computer vision and classification models. In those architectures, every input produces an output of fixed dimension in a single forward pass.

Autoregressive language models break this paradigm completely:
1. **Long-Tailed Output Lengths**: One user asks for a simple boolean check (generating 2 tokens); another asks for a full codebase refactoring (generating 2,048 tokens).
2. **Padding Bubble Inefficiencies**: In static batching, all sequences in a batch must pad their dimensions to match the longest active sequence. When a short sequence finishes at step 10, it consumes GPU memory and compute cycles as empty padding for the remaining 2,038 steps. In typical production traffic, **padding bubbles waste 60% to 75% of GPU FLOPs**.
3. **The Memory-Bandwidth Wall in Generation**: During autoregressive decoding, generating each token requires streaming every single model parameter from high-bandwidth memory (HBM) into on-chip cache. For a 70B parameter model in FP16, this means loading **140 GB across the memory bus for every single token**.

## The Shape of It

Continuous batching and speculative decoding address both ends of this bottleneck: continuous batching saturates GPU memory allocation across requests, while speculative decoding converts memory-bound token decoding into parallel compute-bound verification.

## The Bubble Problem in Static Batching vs Iteration-Level Scheduling

In static batching, requests enter a lockstep batch:

```
Static Batch (Request Level):
Req 1 (3 tokens):   [Tok 1][Tok 2][Tok 3][PAD  ][PAD  ][PAD  ] (Trapped idle!)
Req 2 (6 tokens):   [Tok 1][Tok 2][Tok 3][Tok 4][Tok 5][Tok 6] (Finishes batch)
                       ▲                     ▲
                       │                     │
                Tokens Generated      Wasted Padding Bubbles
```

### Continuous Batching (Iteration-Level Scheduling)

Introduced in the Orca paper (Yu et al., OSDI 2022) and popularized by vLLM, **Continuous Batching** operates at the granularity of individual forward pass iterations:

```
Iteration-Level Continuous Batching:
Step 1:  [Req A (tok 1)] [Req B (tok 1)] [Req C (tok 4)]
Step 2:  [Req A (tok 2)] [Req B (tok 2)] [Req C (tok 5)] -> Req B completes!
Step 3:  [Req A (tok 3)] [Req D (prefill)] [Req C (tok 6)] -> Req D inserted!
```

Whenever a sequence emits an `<EOS>` (end of sentence) token, its physical memory blocks are reclaimed, and a new waiting request's prefill or decode step is immediately scheduled in the very next iteration. Hardware utilization remains consistently above 80%.

## Speculative Decoding: Overcoming the Memory Bandwidth Bottleneck

While continuous batching optimizes cluster-wide concurrency, individual user latency (TPOT) remains bound by memory bandwidth. At batch size 1, an NVIDIA H100 GPU generates tokens at a fraction of its theoretical compute capacity because it must stream 140 GB of model weights for each generated token.

**Speculative Decoding** (Leviathan et al., Chen et al.) overcomes this by pairing the large target model with a lightweight, high-speed draft model:
1. **Draft Phase**: A small, fast draft model (e.g. LLaMA-3-8B) generates a speculative horizon of $K$ candidate tokens sequentially. Because the draft model is 10× smaller, it generates tokens at sub-3ms latency.
2. **Verify Phase**: The large target model (e.g. LLaMA-3-70B) accepts all $K$ candidate tokens simultaneously. Because all $K$ tokens are known, the target model processes them in parallel as a single causal prompt pass (compute-bound GEMM).
3. **Acceptance Evaluation**: The target model evaluates each token in sequence. If all $K$ tokens match target probabilities, the system advances by $K+1$ tokens in the time of a single target forward pass.

## Mathematical Proof: Exact Distributional Match

A common misconception is that Speculative Decoding is an approximation technique that degrades model quality. **It does not.** The output probability distribution is mathematically identical to sampling directly from the target model.

### The Modified Rejection Sampling Algorithm

Let $p(x)$ be the probability distribution of the large target model, and $q(x)$ be the probability distribution of the small draft model.

For each candidate token $x_i$ proposed by the draft model:
1. Sample a random uniform number $r \sim U(0, 1)$.
2. If $r \le \min\left(1, \frac{p(x_i)}{q(x_i)}\right)$, **ACCEPT** $x_i$.
3. If $r > \min\left(1, \frac{p(x_i)}{q(x_i)}\right)$, **REJECT** $x_i$ and halt verification.
4. Resample the replacement token from the normalized positive residual distribution:
   $$p'(x) = \frac{\max(0, p(x) - q(x))}{\sum_y \max(0, p(y) - q(y))}$$

<GoDeeper title="Go deeper: Mathematical proof that marginal distribution equals p(x)">

Let $P(x)$ be the net probability that token $x$ is emitted by the combined draft-verify system:

$$P(x) = q(x) \min\left(1, \frac{p(x)}{q(x)}\right) + \left(1 - \sum_y q(y) \min\left(1, \frac{p(y)}{q(y)}\right)\right) p'(x)$$

Note that $q(x) \min\left(1, \frac{p(x)}{q(x)}\right) = \min(q(x), p(x))$.

The probability of rejection is:
$$1 - \sum_y \min(q(y), p(y)) = \sum_y (p(y) - \min(q(y), p(y))) = \sum_y \max(0, p(y) - q(y))$$

Multiplying by $p'(x)$ cancels the denominator:
$$P(x) = \min(q(x), p(x)) + \max(0, p(x) - q(x)) = p(x)$$

**Conclusion**: The output distribution $P(x)$ is identically equal to $p(x)$! Speculative decoding is an **exact lossless acceleration**.

</GoDeeper>

## Tree Attention & Medusa Heads

While standard Speculative Decoding drafts a linear sequence of $K$ tokens, modern production architectures expand the draft space into a tree structure:

```
Linear Draft:
[Token 1] ───► [Token 2] ───► [Token 3] ───► [Token 4]

Tree Attention (Medusa / EAGLE):
                 ┌───► [Branch A: token 2a] ───► [Token 3a]
[Token 1] ───────┤
                 └───► [Branch B: token 2b] ───► [Token 3b]
```

Using custom **Tree Attention Masks**, the target model verifies multiple candidate paths simultaneously in a single forward pass, raising the average accepted tokens per step from $2.1$ to over $3.6$.

## A Full Worked Example: Expected Speedup Analysis

Consider serving LLaMA-3-70B (target model, 30 ms per forward pass) paired with LLaMA-3-8B (draft model, 3 ms per forward pass).
- Draft horizon: $K = 4$ tokens.
- Empirical acceptance rate: $\alpha = 0.75$.

The expected number of accepted tokens $\mathbb{E}[N]$ is the geometric sum:
$$\mathbb{E}[N] = \sum_{i=0}^K \alpha^i = 1 + 0.75 + 0.75^2 + 0.75^3 + 0.75^4 = 1 + 0.75 + 0.5625 + 0.4219 + 0.3164 = 3.05 \text{ tokens}$$

Total step latency:
$$\text{Latency}_{\text{step}} = \text{Latency}_{\text{target}} + (K \times \text{Latency}_{\text{draft}}) = 30 + (4 \times 3) = 42.0 \text{ ms}$$

Baseline autoregressive execution time for 3.05 tokens:
$$\text{Latency}_{\text{baseline}} = 3.05 \times 30.0 = 91.5 \text{ ms}$$

Wall-clock speedup:
$$\text{Speedup} = \frac{91.5}{42.0} = 2.18\times$$

The serving system generates over **2.18× more tokens per second** with mathematical equivalence to the 70B model.

## Common Problems & Fixes

1. **Vocabulary / Tokenizer Mismatches**: The draft model was trained with a different byte-pair encoding than the target model, producing invalid candidate indices.
   - *Fix*: Both models must share the identical tokenizer configuration and vocabulary size. Verify token alignment in pre-flight checks.
2. **Draft Model Slowdown Under High Concurrency**: Under heavy cluster batching ($B \ge 64$), the GPU becomes compute-bound, reducing the latency gap between draft and target models.
   - *Fix*: Disable speculative decoding dynamically when serving concurrency exceeds the compute saturation threshold ($B > 32$).
3. **Low Acceptance Rates on Code Syntax**: A generic draft model proposes incorrect indentation or imports, causing acceptance rates to plummet below 40%.
   - *Fix*: Fine-tune the draft model on the target domain (e.g. code repositories) to boost candidate alignment.

<NotebookCallout color="amber" title="Production Serving Principle">
Pair architectures with matching tokenizers. Speculative decoding requires the draft model and target model to share the exact same vocabulary and tokenizer byte-mapping. If tokens do not align, candidate tokens cannot be evaluated directly in target embeddings.
</NotebookCallout>

## When *Not* to Use It

| Situation | Better Choice | Why |
| :--- | :--- | :--- |
| Heavy batch serving ($B \ge 64$) | Standard continuous batching without speculation | At large batch sizes, the GPU is already compute-saturated; draft verification overhead slows throughput. |
| Memory-constrained single GPU | INT4 quantized target model | Running draft and target models concurrently requires VRAM allocation for two separate weight sets. |
| Highly stochastic creative writing (high temperature) | Autoregressive sampling | Low sampling overlap degrades acceptance rate $\alpha$, rendering speculation slower than baseline. |

## Remember

| Idea | Core Rule |
| :--- | :--- |
| **Continuous Batching** | Iteration-level scheduling eliminates padding bubbles and evicts finished requests instantly. |
| **Speculative Decoding** | Draft $K$ tokens fast; verify in parallel in one target forward pass. |
| **Lossless Quality** | Modified rejection sampling guarantees identical output distribution to the target model. |
| **Tree Attention** | Verify branching candidates simultaneously to raise tokens-per-step above 3.5. |
| **Acceptance Threshold** | Speculation yields speedup only when acceptance rate $\alpha > \text{Latency}_{\text{draft}} / \text{Latency}_{\text{target}}$. |
