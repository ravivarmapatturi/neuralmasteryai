# Edge AI & TinyML Architecture

While datacenter inference operates in an environment of high-bandwidth memory (HBM3), 80-gigabyte VRAM pools, and kilowatt power supplies, the physical frontier of embedded AI lives at the opposite extreme: **Edge AI and TinyML**.

**TinyML** is the technical discipline of running machine learning inference on **ultra-low-power microcontrollers** (MCUs)—such as ARM Cortex-M4, Cortex-M7, ESP32, and RISC-V:
- **Compute Budget**: 40 MHz to 200 MHz single-core clocks.
- **Memory Envelope**: **64 KB to 256 KB of volatile SRAM** (working memory) and **512 KB to 2 MB of Flash ROM**.
- **Power Envelope**: **Milliwatts or microwatts** (operating on coin-cell batteries or energy harvesting for years without human intervention).
- **Zero Operating System**: Bare-metal C++ execution without virtual memory management units (MMUs), paging, or swap files.

This chapter details the systems architecture of microcontroller inference engines, zero-copy Flash execution, memory planning algorithms, and hardware DSP vector instructions.

<ELI5>

Imagine trying to park an 18-wheel cargo truck inside a tiny one-car residential garage. That is what running deep learning on a microcontroller chip feels like.

If you bring the whole truck in, it simply will not fit. You have to disassemble the truck: take off the heavy steel panels, shrink the engine block, and remove anything non-essential.

In **TinyML**, the 18-wheel truck is a convolutional neural network, and the one-car garage is a 128 KB microcontroller chip. We fit the model by converting all numbers to 8-bit integers (INT8), storing the blueprint on a chip that uses zero electricity (Flash ROM), and reusing a single piece of scratchpad paper for every intermediate calculation (the Static Tensor Arena).

</ELI5>

## Why This Exists

Engineers trained on desktop or cloud Python environments take automatic memory management for granted: if a layer requires a 50-megabyte tensor, the runtime calls `malloc()` or `cudaMalloc()`. Virtual memory managers allocate virtual pages, and garbage collectors reclaim memory when tensors fall out of scope.

On bare-metal microcontrollers, this paradigm triggers fatal hardware crashes:
1. **The Absence of a Memory Management Unit (MMU)**: Microcontrollers feature physical memory addressing only. There is no virtual memory, no page translation, and no swap space.
2. **Fatal Heap Fragmentation**: When a program repeatedly allocates and frees variable-sized activation buffers (`malloc` followed by `free`), memory breaks into non-contiguous gaps. After several hours of continuous sensor polling, `malloc()` inevitably fails to locate a contiguous block, triggering an unrecoverable **Hard Fault exception** and resetting the device.
3. **Severe Static Current Leakage**: Volatile SRAM requires continuous electrical current to retain charge. Microcontrollers minimize battery drain by keeping SRAM sizes tiny (e.g. 128 KB). Storing static neural network weights in SRAM drains battery cells within days.

To achieve multi-year battery life and deterministic operational reliability, production TinyML architectures enforce two systems invariants: **Zero Dynamic Heap Allocation** and **eXecute In Place (XIP)**.

### The Embedded Memory Split

In an embedded microcontroller, physical silicon is partitioned into two distinct physical memories:

| Attribute | Flash ROM (Non-Volatile) | SRAM (Volatile RAM) |
| :--- | :--- | :--- |
| **Physical Capacity** | 512 KB to 2 MB | **64 KB to 256 KB total** |
| **Standby Power** | **Zero current** | High static transistor leakage |
| **Access Latency** | ~30-50 ns (wait states apply) | ~5 ns (single-cycle core clock) |
| **Contents Stored** | Model graph, INT8 weights, bias vectors | Input sensor samples, layer activations |
| **Access Paradigm** | **eXecute In Place (XIP)** via AHB/SPI bus | **Static Tensor Arena** |

Under the **eXecute In Place (XIP)** architecture, model weights are memory-mapped directly into the processor's read-only address space. When executing a convolutional layer, the processor streams weights directly from Flash pins into internal registers. Weights are **never copied into SRAM**, preserving precious RAM for mutable activations.

## The Static Tensor Arena: Zero Dynamic Allocation

To eliminate heap fragmentation, **TensorFlow Lite for Microcontrollers (TFLite Micro)** allocates a single static byte buffer in the global `BSS` segment at compile time:

```cpp
// Static allocation in global BSS segment -- zero heap malloc()!
#include "tensorflow/lite/micro/micro_interpreter.h"
#include "tensorflow/lite/micro/micro_mutable_op_resolver.h"

// 48 KB static arena budget aligned to 16-byte boundary for SIMD loads
constexpr int kTensorArenaSize = 48 * 1024;
alignas(16) uint8_t tensor_arena[kTensorArenaSize];

// Initialize TFLite Micro runtime on bare metal
void setup_inference() {
    const tflite::Model* model = tflite::GetModel(g_model_data); // Stored in Flash ROM
    static tflite::MicroMutableOpResolver<4> resolver;
    resolver.AddConv2D();
    resolver.AddDepthwiseConv2D();
    resolver.AddMaxPool2D();
    resolver.AddFullyConnected();

    static tflite::MicroInterpreter interpreter(
        model,
        resolver,
        tensor_arena,
        kTensorArenaSize
    );
    interpreter.AllocateTensors();
}
```

### Ping-Pong Memory Planning

Because neural networks execute layers sequentially, Layer $i$'s output becomes Layer $i+1$'s input. Once Layer $i+1$ finishes executing, the memory occupied by Layer $i$'s output can be immediately reclaimed.

By alternating between two offset buffers (Buffer A and Buffer B) within the same static arena, the runtime achieves continuous memory reuse without runtime overhead:

```
Step 1 (Conv2D):        Read Input (Buffer B)   ───► Write 24 KB (Buffer A: 0..24k)
Step 2 (Depthwise):     Read 24 KB (Buffer A)   ───► Write 24 KB (Buffer B: 24..48k)
Step 3 (Pointwise):     Read 24 KB (Buffer B)   ───► Write 16 KB (Buffer A: 0..16k)
Step 4 (MaxPool):       Read 16 KB (Buffer A)   ───► Write 8 KB  (Buffer B: 24..32k)
Step 5 (Dense Softmax): Read 8 KB  (Buffer B)   ───► Write 1 KB  (Buffer A: 0..1k)
```

## System-Algorithm Co-Design: MCUNet & Depthwise Convolutions

Standard 2D convolutions require $H \times W \times C_{\text{in}} \times C_{\text{out}} \times K^2$ operations, quickly exceeding the 50-100 MHz clock limit of microcontrollers.

In **Depthwise-Separable Convolutions** (Lin et al., MCUNet):
1. **Depthwise Step**: Applies a single $K \times K$ spatial filter per input channel independently ($H \times W \times C_{\text{in}} \times K^2$).
2. **Pointwise Step**: Applies a $1 \times 1$ linear projection across channels ($H \times W \times C_{\text{in}} \times C_{\text{out}}$).

$$\text{Compute Ratio} = \frac{H W C_{\text{in}} K^2 + H W C_{\text{in}} C_{\text{out}}}{H W C_{\text{in}} C_{\text{out}} K^2} = \frac{1}{C_{\text{out}}} + \frac{1}{K^2}$$

For standard $3 \times 3$ kernels ($K=3$) with 32 output channels, depthwise separation slashes computational load by **nearly 9×**:
$$\frac{1}{32} + \frac{1}{9} \approx 0.031 + 0.111 = 0.142 \implies \mathbf{7\times \text{ to } 9\times \text{ fewer FLOPs!}}$$

<GoDeeper title="Go deeper: ARM Cortex-M DSP assembly acceleration with CMSIS-NN">

On ARM Cortex-M4 and Cortex-M7 processors, integer arithmetic is accelerated using ARM DSP SIMD instructions.

The **`__SMLAD`** instruction (Signed Multiply Accumulate Dual) performs two 16-bit integer multiplications and accumulates the result into a 32-bit register in a **single clock cycle**:

```c
// CMSIS-NN kernel inner loop executing 2 MACs per cycle
int32_t acc = 0;
// Load two 16-bit packed weights and two 16-bit packed activations
uint32_t w_pair = *__SIMD32(weight_ptr)++;
uint32_t a_pair = *__SIMD32(act_ptr)++;
// Multiply two pairs and accumulate in one cycle
acc = __SMLAD(w_pair, a_pair, acc);
```

By packing two INT8 values into a 32-bit word, CMSIS-NN doubles the arithmetic throughput of microcontroller cores, allowing voice wake-word and keyword spotting models to execute in under 12 milliseconds.

</GoDeeper>

## A Full Worked Example: Microcontroller Arena Memory Planning

Consider a TinyML image classifier running on an STM32 MCU (128 KB total SRAM, 512 KB Flash):
- Layer 1 (Conv2D): Input 12 KB, Output 24 KB, Flash Weights 48 KB
- Layer 2 (Depthwise): Input 24 KB, Output 24 KB, Flash Weights 16 KB
- Layer 3 (Pointwise): Input 24 KB, Output 16 KB, Flash Weights 32 KB
- Layer 4 (MaxPool): Input 16 KB, Output 8 KB, Flash Weights 0 KB
- Layer 5 (Dense): Input 8 KB, Output 1 KB, Flash Weights 14 KB

Total Model Weights stored in Flash ROM:
$$\text{Weights}_{\text{Flash}} = 48 + 16 + 32 + 0 + 14 = \mathbf{110 \text{ KB}}$$

If each layer allocated independent memory on the heap, total activation memory would be:
$$\text{Memory}_{\text{Naive}} = 12 \text{ (Input)} + 24 + 24 + 16 + 8 + 1 = \mathbf{85 \text{ KB}}$$

Using the **Ping-Pong Static Arena**:
- Buffer A (24 KB, offset `0..24 KB`)
- Buffer B (24 KB, offset `24..48 KB`)
- **Total Peak Arena Memory**: $\mathbf{48 \text{ KB}}$, saving **37 KB (43.5% reduction)**.
The remaining 80 KB of SRAM remains unallocated and free for the RTOS kernel, networking stack, and peripheral DMA buffers.

## Common Problems & Fixes

1. **Stack Overflow Colliding with Static Tensor Arena**: On bare metal, the call stack grows downwards towards the global BSS segment. If deep recursion occurs, the stack overwrites tensor activations.
   - *Fix*: Place the `tensor_arena` at the absolute bottom of RAM or configure the hardware Memory Protection Unit (MPU) to generate a bus fault on stack boundary breaches.
2. **Flash Read Latency Stalling CPU Execution**: Reading weights from SPI Flash over slow peripheral buses starves the ALU.
   - *Fix*: Enable microcontroller internal instruction and data caches (I-Cache / D-Cache) or use Quad-SPI / Octal-SPI memory controllers with 4-bit parallel data lines.
3. **Accuracy Degradation on Depthwise Layers**: Depthwise layers have few parameters per channel, making them vulnerable to INT8 quantization noise.
   - *Fix*: Use per-channel quantization scales for depthwise weights instead of per-tensor scales.

<NotebookCallout color="cobalt" title="Embedded Deployment Rules">
1. **Never allocate heap dynamically (`malloc`)**: Use static byte arrays in the BSS segment.
2. **Quantize to INT8 symmetrically**: Eliminates cross-term corrections and allows single-cycle ARM Cortex-M DSP instructions (`__SMLAD`).
3. **Keep Model Weights in Flash (XIP)**: Never copy weights into SRAM.
</NotebookCallout>

## When *Not* to Use It

| Situation | Better Choice | Why |
| :--- | :--- | :--- |
| Generative text generation (LLMs $> 1\text{B}$) | Edge Linux SBC (Raspberry Pi 5 / Jetson) | Microcontrollers with 256 KB RAM cannot hold billion-parameter KV caches or token vocabularies. |
| Multi-task applications with dynamic batching | Cloud API or local server | Microcontrollers operate strictly at batch size $B=1$ on real-time hardware sensor streams. |
| Frequent continuous learning / on-device training | Federated edge server | Flash ROM write cycles are limited (typically ~10,000 to 100,000 writes); repeated training runs wear out Flash silicon. |

## Remember

| Idea | Core Rule |
| :--- | :--- |
| **SRAM vs Flash** | Flash ROM stores read-only weights (XIP); SRAM stores mutable activations only. |
| **No Malloc** | Banning dynamic heap allocation eliminates fatal memory fragmentation faults. |
| **Static Tensor Arena**| Pre-plan buffer offsets offline so non-overlapping layer activations share memory. |
| **Ping-Pong Buffers** | Alternate between two memory blocks to cut peak activation SRAM by 40% to 75%. |
| **CMSIS-NN & SIMD** | Use DSP instructions (`__SMLAD`) to execute two INT8 multiply-accumulates per clock cycle. |
