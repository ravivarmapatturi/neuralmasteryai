# Hardware Acceleration & Custom Kernels

In high-throughput deep learning inference, standard high-level frameworks (such as uncompiled PyTorch) introduce severe latency penalties: every elementary operation (such as a matrix multiplication followed by a bias addition and a GeLU activation) writes intermediate tensors back to slow off-chip memory (HBM/DRAM), only to read them back immediately in the subsequent kernel launch.

This chapter details the systems architecture of **Hardware Acceleration**: GPU physical memory hierarchies, **FlashAttention** SRAM tiling and online softmax mathematics, writing custom GPU kernels in **OpenAI Triton**, and compiling static execution graphs with **TensorRT-LLM** and **CUDA Graphs**.

<ELI5>

Imagine a chef preparing a gourmet meal.

A **naive chef** walks to the pantry to grab a tomato, walks all the way across the kitchen to the prep counter, chops the tomato, carries the slices all the way back to the pantry to store them, then walks back to grab a cucumber, chops it, and carries the slices back to the pantry. They spend 90% of their day walking back and forth across the kitchen floor (Memory Bandwidth Roundtrips).

A **master chef** brings all required ingredients onto the prep counter at once, chops everything in one continuous sequence, tosses the dish in a bowl right there, and plates the final meal.

In GPU programming, that is **Kernel Fusion and FlashAttention**: keeping intermediate tensors inside the ultra-fast on-chip prep counter (SRAM) and never walking back to the slow pantry (HBM) until the final output matrix is computed.

</ELI5>

## Why This Exists

Modern GPU compute capabilities have outpaced memory transfer bandwidth by an order of magnitude. On an NVIDIA H100 SXM5 GPU:
- **FP16 Tensor Core Compute**: 989 TFLOPS ($989 \times 10^{12}$ floating-point operations per second).
- **HBM3 Memory Bandwidth**: 3.35 TB/s ($3.35 \times 10^{12}$ bytes per second).

This creates an operational ratio: to keep Tensor Cores fully saturated, an algorithm must execute nearly **300 floating-point operations for every single byte loaded from HBM**. 

Standard transformer implementations fail this threshold miserably:
1. **The Attention Memory Wall**: Standard attention calculates $S = QK^T$, writes the entire $N \times N$ score matrix to HBM, reads it back to compute $\text{softmax}(S)$, writes the attention probabilities $P$ to HBM, and reads $P$ back to multiply by $V$. For a sequence of 16,384 tokens across 32 heads in FP16, this requires **over 32 GB of memory bandwidth per layer** just to shuffle intermediate activations that are discarded immediately afterwards.
2. **Launch Latency Overhead**: Launching dozens of tiny CUDA kernels from Python incurs 3 to 5 microseconds of CPU driver latency per launch, leaving the GPU idle while waiting for the next instruction.
3. **Register Spilling**: Unoptimized kernel compilers exceed the 256 KB per-Streaming-Multiprocessor (SM) register file, spilling local variables into slower memory and cutting arithmetic throughput by half.

## The GPU Memory Hierarchy: SRAM vs HBM

To author performant kernels, an engineer must program against the physical hierarchy of the accelerator:

| Memory Level | Capacity (H100) | Bandwidth | Latency (Clock Cycles) | Programming Scope |
| :--- | :--- | :--- | :--- | :--- |
| **Registers (RF)** | ~256 KB per SM (~32 MB total) | ~300 TB/s | ~1 cycle | Private to single thread |
| **Shared Memory (SRAM)** | ~228 KB per SM (~30 MB total) | ~33 TB/s | ~15-25 cycles | Shared across thread block |
| **L2 Cache** | 50 MB total | ~12 TB/s | ~150-200 cycles | Shared across all SMs |
| **High-Bandwidth Memory (HBM3)** | 80 GB | 3.35 TB/s | ~400-600 cycles | Global device memory |
| **Host System RAM (PCIe 5.0)** | 1 TB to 2 TB | 0.064 TB/s | ~1,000+ cycles | CPU main memory |

On-chip SRAM is **10× faster** than off-chip HBM3. An algorithm that reads and writes intermediate matrices to HBM spends 90% of its execution cycles stalling for memory lines.

<GoDeeper title="Go deeper: Mathematical derivation of the Online Softmax algorithm">

Standard softmax over a vector $x \in \mathbb{R}^N$ requires two sequential passes:
1. Compute the maximum $m = \max_i x_i$ to prevent numerical overflow.
2. Compute the normalization denominator $d = \sum_{i=1}^N e^{x_i - m}$.

In FlashAttention, $x$ arrives in small blocks (tiles) that fit in SRAM. When a new block $x^{(2)}$ arrives with local maximum $m_2$ and local sum $d_2$, FlashAttention merges it with previous state $(m_1, d_1)$ using the online recurrence:

$$m_{\text{new}} = \max(m_1, m_2)$$

$$d_{\text{new}} = d_1 \cdot e^{m_1 - m_{\text{new}}} + d_2 \cdot e^{m_2 - m_{\text{new}}}$$

The running output vector $O$ is rescaled instantaneously without ever materializing all elements at once:

$$O_{\text{new}} = O_1 \cdot \left(\frac{d_1 \cdot e^{m_1 - m_{\text{new}}}}{d_{\text{new}}}\right) + O_2 \cdot \left(\frac{e^{m_2 - m_{\text{new}}}}{d_{\text{new}}}\right)$$

This mathematical formulation enables exact attention computation in $O(N)$ memory with zero numerical error.

</GoDeeper>

## Authoring Custom GPU Kernels with OpenAI Triton

Historically, writing custom GPU kernels required low-level CUDA C++, manual warp-divergence synchronization (`__syncthreads()`), and raw pointer arithmetic.

**OpenAI Triton** allows developers to author high-performance GPU kernels directly in Python. Triton abstracts thread blocks into multi-dimensional arrays, automatically compiling them into optimized PTX assembly:

```python
import triton
import triton.language as tl
import torch

@triton.jit
def fused_add_gelu_kernel(
    x_ptr, y_ptr, out_ptr, n_elements,
    BLOCK_SIZE: tl.constexpr
):
    """Fuses elementwise addition and GeLU activation into a single SRAM pass."""
    pid = tl.program_id(axis=0)
    block_start = pid * BLOCK_SIZE
    offsets = block_start + tl.arange(0, BLOCK_SIZE)
    mask = offsets < n_elements

    # Load activations from slow HBM into fast on-chip SRAM registers
    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)

    # Compute fused arithmetic entirely within registers
    val = x + y
    # Fast approximation of GeLU activation: 0.5 * x * (1 + erf(x / sqrt(2)))
    gelu = 0.5 * val * (1.0 + tl.math.erf(val * 0.70710678118))

    # Write final result back to HBM once
    tl.store(out_ptr + offsets, gelu, mask=mask)

def launch_fused_add_gelu(x: torch.Tensor, y: torch.Tensor) -> torch.Tensor:
    output = torch.empty_like(x)
    n_elements = x.numel()
    grid = lambda meta: (triton.cdiv(n_elements, meta['BLOCK_SIZE']),)
    fused_add_gelu_kernel[grid](x, y, output, n_elements, BLOCK_SIZE=1024)
    return output
```

## Compilation & Graph Capture: CUDA Graphs & TensorRT-LLM

In low-latency inference serving ($< 10\text{ ms}$ per token), CPU launch overhead becomes a primary bottleneck: invoking 80 consecutive PyTorch layer kernels from Python incurs ~3 microseconds of CPU dispatch latency per kernel, causing the GPU to sit idle between launches.

### CUDA Graphs

**CUDA Graphs** record a sequence of GPU kernel launches into a single static execution graph:
1. **Capture Phase**: Run the forward pass once in capture mode; the CUDA driver records all kernel addresses, thread parameters, and memory dependencies.
2. **Replay Phase**: The CPU dispatches the **entire graph with a single driver call**, eliminating CPU launch overhead and maximizing GPU compute utilization.

```python
# Real production CUDA Graph capture in PyTorch
static_input = torch.zeros(1, 1024, device='cuda')
# Warmup iterations to initialize memory allocators
for _ in range(3):
    static_output = model(static_input)
torch.cuda.synchronize()

# Record graph
graph = torch.cuda.CUDAGraph()
with torch.cuda.graph(graph):
    static_output = model(static_input)

# Replay during production serving (sub-millisecond execution)
def infer_step(new_input):
    static_input.copy_(new_input)
    graph.replay()
    return static_output
```

## A Full Worked Example: Online Softmax Across SRAM Tiles

Consider an activation vector of length 6: `x = [1.2, 3.4, 2.1, 0.8, 4.5, 2.9]`.
We simulate an on-chip SRAM capacity of only 3 elements, forcing the computation into two sequential tiles:
- **Tile 1**: `[1.2, 3.4, 2.1]`
  - Maximum $m_1 = 3.4$
  - Exponentials: $e^{1.2-3.4} = 0.1108$, $e^{3.4-3.4} = 1.0$, $e^{2.1-3.4} = 0.2725$
  - Denominator sum $d_1 = 0.1108 + 1.0 + 0.2725 = 1.3833$
- **Tile 2**: `[0.8, 4.5, 2.9]`
  - Maximum $m_2 = 4.5$
  - New global maximum $m_{\text{new}} = \max(3.4, 4.5) = 4.5$
  - Rescaling factor: $e^{m_1 - m_{\text{new}}} = e^{3.4 - 4.5} = e^{-1.1} = 0.3329$
  - Updated denominator:
    $$d_{\text{new}} = 1.3833 \times 0.3329 + (e^{0.8-4.5} + e^{4.5-4.5} + e^{2.9-4.5}) = 0.4605 + (0.0247 + 1.0 + 0.2019) = 1.6871$$
- **Final Normalized Output**: Both tiles are divided by $d_{\text{new}}$, yielding `[0.0219, 0.1973, 0.0538, 0.0147, 0.5927, 0.1197]`, matching the global softmax down to 15 decimal places with zero precision loss.

## Common Problems & Fixes

1. **Shared Memory Bank Conflicts in Custom Triton Kernels**: Multiple threads in a warp access the same 32-bit shared memory bank simultaneously, serializing memory access.
   - *Fix*: Pad shared memory arrays by 1 element (`tl.zeros([BLOCK_SIZE + 1], dtype=tl.float32)`) or use Triton's built-in block swizzling to offset access strides.
2. **Dynamic Sequence Shape Graph Invalidations**: CUDA Graphs require static tensor shapes; varying prompt lengths force expensive graph re-captures.
   - *Fix*: Bucket input sequences into discrete power-of-two lengths (e.g. 128, 256, 512, 1024, 2048) and maintain a separate pre-captured CUDA Graph for each bucket.
3. **Register Spilling Degrading Occupancy**: Adding too many intermediate variables in a Triton kernel exceeds the 255 register-per-thread limit, spilling variables into slower local memory.
   - *Fix*: Pass `num_warps=4` or `num_stages=3` to the `@triton.jit` decorator to guide the compiler's register allocator.

## When *Not* to Use It

| Situation | Better Choice | Why |
| :--- | :--- | :--- |
| Rapid exploratory prototyping in research | Standard PyTorch eager mode | Custom Triton kernels require manual compilation and debugging; eager PyTorch is faster for prototyping. |
| CPU-only edge deployment (Raspberry Pi / x86) | GGML / llama.cpp / ONNX Runtime | Triton and TensorRT-LLM compile specifically for NVIDIA GPUs; ARM and x86 require SIMD AVX/NEON kernels. |
| Small batch size with short sequence length (< 64) | Built-in cuBLAS GEMM | At tiny sequence lengths, attention memory overhead is negligible and cuBLAS GEMMs are already fully optimized. |
