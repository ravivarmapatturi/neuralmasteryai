# Prompt Engineering

<ELI5>

A language model continues whatever text you give it. If you hand a new colleague a vague note, you get a vague result; if you give them the goal, two good examples and the format you want, you get what you asked for. Prompting is writing that note. The surprising part is how much it matters, and the hard part is telling whether a new note is really better or you just got lucky on the few tries you looked at.

</ELI5>

## Why This Exists

A prompt is the cheapest lever on an LLM's behaviour: no training, no data pipeline, and a change is live in minutes. It is also the easiest to fool yourself with. Models are sensitive to wording, order and examples, and a prompt that looks better on five hand-picked inputs can be worse on the next five hundred. This page covers the techniques (examples, step-by-step reasoning, sampling several answers), when a reasoning model is worth its cost, how to get output code can parse, the security problem of untrusted text in the prompt, and how to measure a prompt change so the decision is based on evidence.

## Zero-Shot, One-Shot, Few-Shot

- **Zero-shot** asks for the task with no examples and relies on the model's instruction following.
- **Few-shot** puts a handful of input-output pairs before the real query. The model conditions on the whole context, so the examples set a pattern it continues, with no weight updates. GPT-3's paper named this **in-context learning**.

Examples teach format and edge cases better than instructions do, but they also teach things you did not intend. If four of five examples are labelled "positive", the model leans positive; if the last example is unusual, its pattern leaks into the answer. Use examples that cover the label set evenly and include the hard cases.

## Chain-of-Thought (CoT) Prompting

Asking the model to reason step by step before answering improves accuracy on maths and multi-step logic. Each generated token is another forward pass, so intermediate reasoning gives the model more computation, and its final answer can condition on the steps it wrote instead of being produced in one pass. Wei et al. (2022) showed the gain was large for big models and small or negative for small ones.

**Self-consistency** samples several reasoning paths at a non-zero temperature and takes a majority vote on the final answer.

### A Full Worked Example: When Voting Helps

If each path is right with probability $p$, independently, and wrong answers do not agree with each other, the vote is right whenever more than half the paths are. With $p = 0.6$, accuracy rises from 0.600 with one sample to 0.683 with 5, 0.753 with 11 and 0.826 with 21. With $p = 0.45$ the same vote makes things worse: 0.407 with 5 and 0.321 with 21. Voting amplifies whichever side of one half you start on. And 21 samples of a 400-token chain of thought cost 8,400 output tokens per question.

<RunnableCode code={`from math import comb

# Self-consistency: sample n reasoning paths, majority-vote the final answer.
# If each path is right with probability p, independently, and wrong answers
# never agree with each other, the vote is right when more than half are right.
def majority_correct(p, n):
    return sum(comb(n, k) * p**k * (1 - p)**(n - k) for k in range(n // 2 + 1, n + 1))

for p in (0.6, 0.45):
    row = "  ".join(f"n={n}: {majority_correct(p, n):.3f}" for n in (1, 5, 11, 21))
    print(f"single-path accuracy {p}:  {row}")

# Cost: 21 samples of a 400-token chain of thought is 8,400 output tokens per question
print("output tokens for n=21 at 400 tokens each:", 21 * 400)

# Try it: set p = 0.5. The vote never improves on a coin flip, however many
# samples you take: voting amplifies whichever side of 0.5 you start on.`} />

In practice paths are correlated (the same model makes the same mistake) and wrong answers sometimes agree, so real gains are smaller than the binomial ones. Self-consistency only applies when answers can be compared exactly, such as a number or a multiple-choice letter.

**Tree of Thoughts** goes further: it explores several reasoning branches, scores partial solutions and backtracks. It is more expensive and is used for search-like problems.

## Reasoning Models vs. Prompted Chain-of-Thought

Prompted CoT asks any model to show its working. A **reasoning model** (OpenAI's o-series, DeepSeek-R1, Claude with extended thinking) was additionally trained with reinforcement learning, often on problems with checkable answers (see [GRPO](/docs/llms-genai/training-pipeline#group-relative-policy-optimization-grpo)), to find its own reasoning strategies: backtracking, re-checking an assumption, abandoning an approach. At inference it spends a variable and often large number of tokens thinking before it answers, without being asked.

That extra compute has a price, so choosing when to use one is an engineering decision:

- **Worth it** for problems with checkable structure where a first answer is often wrong in a findable way: a subtle bug, a multi-step proof, a scheduling puzzle.
- **Not worth it** for lookups, formatting, casual questions, or anything a fast model already gets right. The extra latency, sometimes minutes, buys accuracy you did not need.

In production this is usually a **routing** decision (see [Routing & Supervisor](/docs/agents/routing-and-supervisor)): send only the requests that benefit to the expensive mode.

### Test-Time Compute Scaling: a Second Scaling Axis

For years, pretraining scale (see [Scaling Laws](/docs/llms-genai/training-pipeline#scaling-laws-and-the-chinchilla-result)) was the one lever that reliably bought capability. Reasoning models add a second: **test-time compute**, spending more computation per request after training is finished. In APIs this is a **thinking budget**, a token limit on internal reasoning set per request. Anthropic's API calls it `budget_tokens`, a target rather than a floor, with a minimum of 1,024.

<TestTimeComputeScalingDiagram />

The gain is roughly **logarithmic**: Anthropic reports maths accuracy improving with the logarithm of thinking tokens, and OpenAI's o1 chart shows the same log-linear shape. Each doubling of the budget buys about the same small improvement, and every thinking token is billed as output. Past a point a bigger budget mostly buys latency.

**Interleaved thinking** lets a reasoning model think between tool calls in an agent loop, reasoning about each result before choosing the next call (see [Tool Use](/docs/agents/agent-fundamentals#tool-use-function-calling)), so it can change course once it has real feedback.

## ReAct (Reasoning + Acting)

ReAct alternates reasoning with actions and observations: think, call a tool, read the result, think again. It is the basic loop behind most tool-using [agents](/docs/agents/roadmap).

## System Prompts & Structured Output

A **system prompt** sets persistent context for the whole conversation (role, tone, constraints), separate from the user's messages. Put stable instructions there; it is also the part that [prompt caching](/docs/llms-genai/calling-the-llm-api#paying-less-prompt-caching) can reuse.

When code reads the output, ask for a structure and enforce it. Instructions and a format example get most of the way; **structured outputs** or **tool calling** with a JSON schema constrain decoding so the output always parses. Validate it anyway: a schema guarantees shape, not correct content.

## Prompt Injection and Jailbreaking

**Prompt injection** is text inside content the model processes (a web page, an email, a tool result) that tries to override the original instructions. It matters for any system where an LLM reads untrusted content, and most of all when the LLM can also take actions. **Jailbreaking** is a user directly trying to get around a model's safety training.

<PromptInjectionFlowDiagram />

No prompt wording reliably stops injection, because instructions and data share one channel. Defences are architectural: keep trusted instructions separate from untrusted data and mark which is which, give the model only the tools and permissions the task needs, require confirmation before actions with side effects, and filter inputs and outputs. Models are also trained to give lower priority to instructions arriving from non-privileged sources.

## Measuring a Prompt Change

Treat a prompt like code: change it, run a test suite, compare. The suite is a fixed set of inputs with known-good outputs or a grading rule, and both versions run on the same cases so the comparison is paired.

### Run It Yourself: Is a 4-Point Gain Real?

An old prompt scores 0.845 on 200 cases and a new one 0.885, a gain of 4 points. Looking case by case, the new prompt fixed 14 cases and broke 6. A paired bootstrap, resampling the 200 cases 5,000 times, puts the gain's 95% interval at -0.005 to +0.080. It includes zero: on this suite, the improvement could be noise. Had the new prompt fixed 24 cases, the interval would be +0.040 to +0.145, a real improvement.

<RunnableCode code={`import numpy as np

# Two prompt versions run on the same 200 test cases (1 = correct).
rng = np.random.default_rng(3)
n = 200
old = (rng.random(n) < 0.82).astype(int)
new = old.copy()
flip_up = rng.choice(np.where(old == 0)[0], 14, replace=False)    # new prompt fixes 14
flip_down = rng.choice(np.where(old == 1)[0], 6, replace=False)   # and breaks 6
new[flip_up], new[flip_down] = 1, 0

print(f"old prompt {old.mean():.3f}, new prompt {new.mean():.3f}, gain {new.mean() - old.mean():+.3f}")
print(f"cases fixed {int(((old == 0) & (new == 1)).sum())}, cases broken {int(((old == 1) & (new == 0)).sum())}")

# Paired bootstrap: resample test cases, recompute the gain each time
gains = []
for _ in range(5000):
    idx = rng.integers(0, n, n)
    gains.append(new[idx].mean() - old[idx].mean())
lo, hi = np.percentile(gains, [2.5, 97.5])
print(f"95% interval for the gain: [{lo:+.3f}, {hi:+.3f}]")
print("verdict:", "real improvement" if lo > 0 else "could be noise; add test cases")

# Try it: change 14 to 24, so the new prompt fixes 24 cases. The gain becomes
# +0.090 and the interval [+0.040, +0.145] no longer includes zero.`} />

<GoDeeper title="Go deeper: why chain of thought adds computation">

A transformer does a fixed amount of computation per token: one pass through every layer. A question answered in one token gets one pass. If the answer needs, say, several sequential steps of arithmetic, a fixed-depth network may not be able to carry them out within one pass, but it can if each intermediate result is written out as tokens and read back on the next pass. Theoretical work on transformers (Feng et al., 2023; Merrill and Sabharwal, 2023) makes this precise: problems that a constant-depth transformer cannot solve in one step become solvable with a chain of intermediate tokens whose length grows with the problem. That is the formal version of "more tokens is more computation", and it is why a reasoning budget helps most on problems with many dependent steps.

</GoDeeper>

## Failure Modes and Debugging

- **Prompt sensitivity.** Small wording changes give inconsistent output. Make the instructions explicit, add examples, lower the temperature, and measure with a suite rather than spot checks.
- **Lost in the middle.** Models use information near the start and end of a long context more reliably than information in the middle, even inside the context window. It matters for prompting and for [RAG](/docs/llms-genai/rag).

<LostInTheMiddleDiagram />

This is one symptom of **context rot**, the broader drop in recall as context grows; see [Context Engineering](/docs/agents/context-engineering).

- **Cost and latency.** Shorter prompts, cached prefixes and the smallest model that passes the suite all cut cost.

<NotebookCallout color="green" title="A prompt workflow that holds up">
Write the test suite before the prompt. Start with the simplest instruction, run the suite, read the failures, change one thing, run again. Keep the suite in version control next to the prompt.
</NotebookCallout>

## When *Not* to Use It

| Situation | Better choice |
| --- | --- |
| The model lacks the facts | [RAG](/docs/llms-genai/rag) or tools; prompting cannot add knowledge |
| Thousands of examples of a fixed format or style | Fine-tuning |
| Output must always parse | Structured outputs or tool calling, not format instructions alone |
| Untrusted text can trigger actions | Permission boundaries and confirmation, not a stronger warning in the prompt |

## Remember

| Idea | One line |
| --- | --- |
| Few-shot | Examples set format and edge cases; balance the labels |
| Chain of thought | More tokens is more computation before the answer |
| Self-consistency | Majority vote over samples; helps only when one path beats 0.5 |
| Reasoning models | RL-trained to think; route only hard requests to them |
| Thinking budget | Accuracy grows roughly with the log of thinking tokens |
| Structured output | Constrain decoding with a schema, then validate content |
| Prompt injection | Architectural defence; wording alone does not stop it |
| Measuring | Paired test suite plus an interval on the gain |
