# Calling the LLM API in Practice

<ELI5>

Calling a hosted model is like ordering from a busy kitchen over the phone. You say what you want and how long the answer may be. The kitchen may tell you it is too busy and to call back later, the line may drop halfway through, and you get a bill per word in both directions. A good caller knows which problems to retry, how long to wait, and keeps the receipt for every order.

</ELI5>

## Why This Exists

[Prompt Engineering](/docs/llms-genai/prompt-engineering) covers what to put in the request. This page covers everything around it: the parameters that are not prompt text, how to read a streamed response, what to do when the call fails, how to pay less for repeated prompts, and what to log on every call. A correct prompt still fails in production if the response is silently truncated, if a thousand clients retry in lockstep after an outage, or if nobody can say why last week's bill doubled.

Every major hosted API (Anthropic, OpenAI, Google) shares the same basic shape, so the ideas carry over even where field names differ.

## The Request and the Response

A chat call is one HTTP POST: a list of role-tagged messages in, one message out, plus a usage block and a reason the generation stopped.

```python
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

response = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=200,
    system="You are a concise technical assistant.",
    messages=[{"role": "user", "content": "Explain what a KV cache is in two sentences."}],
)

print(response.content[0].text)
print(response.usage.input_tokens, response.usage.output_tokens)
print(response.stop_reason)   # "end_turn", "max_tokens", "stop_sequence" or "tool_use"
```

The OpenAI Chat Completions call has the same parts under different names: `choices[0].message.content` for the text, `usage.prompt_tokens` and `usage.completion_tokens`, and `finish_reason` with values `"stop"`, `"length"` or `"content_filter"`.

The stop reason is the field most often ignored. `"max_tokens"` (or `"length"`) means the model was cut off mid-answer. The text looks normal, and a JSON object may simply be missing its closing brace. Checking the stop reason before trusting the output is one line and catches a common production bug.

## The Parameters That Change the Output

- **`max_tokens`** caps the generated part only. Set it too low and answers are truncated; with no cap at all, one runaway response can be expensive.
- **`temperature`** divides the logits before the softmax. Below 1 it sharpens the distribution towards the most likely token; above 1 it flattens it.
- **`top_p`** (nucleus sampling) keeps the smallest set of tokens whose probabilities add up to `p`, and samples only from those.
- **`stop`** (`stop_sequences` in the Anthropic API) ends generation as soon as a given string is produced.

### A Full Worked Example: Temperature and Top-p on Five Tokens

Suppose the model's logits for the next token after "the KV" are 4.0 for "cache", 3.2 for "memory", 2.5 for "store", 1.0 for "buffer" and -2.0 for "banana". At temperature 1 the softmax gives "cache" 0.580, "memory" 0.261, "store" 0.129, "buffer" 0.029 and "banana" 0.001. At temperature 0.3 the logits are divided by 0.3 before the softmax, and "cache" rises to 0.929. At 1.5 it falls to 0.474 and "banana" goes from 0.1% to 0.9%.

Top-p works differently. With `top_p = 0.8` at temperature 1, "cache" (0.580) and "memory" (0.261) already add up to 0.841, so only those two survive and are renormalised to 0.690 and 0.310. "Banana" can never be sampled, however many calls you make.

<RunnableCode code={`import numpy as np

# Five candidate next tokens and the model's raw logits for them
tokens = ["cache", "memory", "store", "buffer", "banana"]
logits = np.array([4.0, 3.2, 2.5, 1.0, -2.0])

def sample_dist(logits, temperature=1.0, top_p=1.0):
    z = logits / max(temperature, 1e-6)
    p = np.exp(z - z.max()); p /= p.sum()
    order = np.argsort(-p)
    keep = np.cumsum(p[order]) - p[order] < top_p   # smallest set reaching top_p
    q = np.zeros_like(p); q[order[keep]] = p[order[keep]]
    return q / q.sum()

for T, P in [(1.0, 1.0), (0.3, 1.0), (1.5, 1.0), (1.0, 0.8)]:
    q = sample_dist(logits, T, P)
    row = "  ".join(f"{t}={v:.3f}" for t, v in zip(tokens, q))
    print(f"temperature={T:<4} top_p={P:<4} {row}")

# Try it: set top_p=0.8 with temperature=1.5. Raising temperature flattens the
# distribution, so three tokens are now needed to reach 0.8 and "store" survives the cut.`} />

## Streaming Responses

A 500-token answer can take several seconds to generate, and without streaming the user sees nothing until the last token. Streaming sends tokens as they are produced, as server-sent events.

```python
with client.messages.stream(
    model="claude-sonnet-5-5",
    max_tokens=500,
    messages=[{"role": "user", "content": "Write a short paragraph about KV caches."}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
    final = stream.get_final_message()

print("\n", final.usage.output_tokens, final.stop_reason)
```

Two things change under streaming. The usage numbers arrive at the end, so cost tracking has to wait for the stream to finish. And the connection can fail partway through, leaving half an answer: the error path has to decide whether to show the partial text, retry from scratch, or ask the model to continue.

Streaming also splits latency in two. **Time to first token** is dominated by the prompt: the server has to process every input token before it can emit one. **Time per output token** is dominated by decoding speed. A slow first token points at a long prompt or a queue; slow tokens afterwards point at the model or the server's load. See [The roofline model and KV cache](/docs/inference-engineering/roofline-and-kv-cache) for why the two phases behave so differently.

## Retries, Rate Limits and Idempotency

Failures fall into three groups, and each needs a different response.

| Status | Meaning | What to do |
| --- | --- | --- |
| `429` | Rate limited | Retry after a backoff; honour a `retry-after` header if present |
| `500`, `502`, `503`, `529` | Transient server failure or overload | Retry with backoff |
| `400` | Malformed request: bad parameter, prompt too long | Do not retry; fix the request |
| `401`, `403` | Authentication or permission | Do not retry; fix the key |
| Timeout | The request may or may not have run | Retry only if repeating it is safe |

### Why Jitter Matters

Exponential backoff waits `base * 2^attempt` seconds, capped. If 100 clients all receive a 429 at the same instant and use the same fixed schedule, they all retry at exactly the same moment and recreate the spike. "Full jitter" picks a random wait between 0 and the exponential ceiling instead. In the simulation below, without jitter all 100 clients retry for the second time at exactly 3.0 seconds; with jitter they spread over 0.2 to 2.9 seconds and the busiest tenth of a second holds 8 of them.

<RunnableCode code={`import random

random.seed(7)
BASE, CAP, MAX_ATTEMPTS = 1.0, 30.0, 6

def backoff(attempt, jitter=True):
    ceiling = min(CAP, BASE * 2 ** attempt)
    return random.uniform(0, ceiling) if jitter else ceiling   # "full jitter"

# 100 clients all hit a 429 at the same instant. When do they retry?
for jitter in (False, True):
    first_retry = sorted(round(backoff(0, jitter) + backoff(1, jitter), 1) for _ in range(100))
    busiest = max(first_retry.count(t) for t in set(first_retry))
    print(f"jitter={jitter!s:5}  second retry lands between {first_retry[0]}s and {first_retry[-1]}s, "
          f"busiest 0.1s slot has {busiest} clients")

def should_retry(status):
    return status == 429 or 500 <= status < 600

for status in (400, 401, 429, 500, 503):
    print(status, "retry" if should_retry(status) else "do not retry")

# Try it: set CAP = 4.0 and print backoff(5) a few times. The cap stops the
# wait growing past 4 seconds however many attempts have failed.`} />

Both official SDKs already retry 429 and 5xx errors with backoff (two retries by default, set with `max_retries`). Wrapping them in a second retry loop multiplies the attempts; configure the SDK instead.

A timeout is the dangerous case. Generating text twice only costs money, but if the call is wired to a tool that sends an email or writes to a database, a blind retry can do it twice. Make the side effect idempotent: give each logical operation a client-generated ID and have the tool ignore an ID it has already processed.

<GoDeeper title="Go deeper: why full jitter, and not a small random offset?">

The AWS Architecture Blog compared three schemes on a simulated contended resource: exponential backoff with no jitter, "equal jitter" (half the ceiling plus a random half), and "full jitter" (uniform between 0 and the ceiling). Without jitter, total work was far higher because clients collided in waves. Both jittered schemes cut the number of calls sharply, and full jitter finished with the fewest calls. The reason is that what matters is spreading clients across the whole window. A small offset added to a fixed delay keeps them bunched together.

</GoDeeper>

## Paying Less: Prompt Caching

Many applications send the same long prefix on every call: a system prompt, tool definitions, a document. Providers can cache the processed prefix and charge a fraction of the normal input price when it is reused. Anthropic marks the cacheable prefix with `cache_control`, and OpenAI caches long shared prefixes automatically. In both cases the prefix must match exactly, byte for byte, so put stable content first and anything that varies (the user's question, a timestamp) after it.

The worked example below uses placeholder prices ($3 per million input tokens, $15 per million output, $0.30 per million cached input). A support bot with a 6,000-token system prompt, a 400-token question and a 300-token answer costs $0.0237 per call without caching and $0.0075 with the prefix cached, about a third.

<RunnableCode code={`# Cost per call from the usage block. Prices are per million tokens and are
# placeholders: read your provider's current price page before using them.
PRICE = {"input": 3.00, "output": 15.00, "cached_input": 0.30}

def call_cost(input_tokens, output_tokens, cached_tokens=0):
    fresh = input_tokens - cached_tokens
    return (fresh * PRICE["input"] + cached_tokens * PRICE["cached_input"]
            + output_tokens * PRICE["output"]) / 1e6

# A support bot: 6,000-token system prompt + 400-token question, 300-token answer
no_cache = call_cost(6400, 300)
with_cache = call_cost(6400, 300, cached_tokens=6000)
print(f"per call, no caching:   \${no_cache:.5f}")
print(f"per call, cached prefix: \${with_cache:.5f}")
print(f"per day at 50,000 calls: \${no_cache*50_000:,.2f} vs \${with_cache*50_000:,.2f}")

# Try it: change the answer to 3,000 output tokens. Output tokens cost 5x input
# here, so long answers dominate the bill once the prefix is cached.`} />

## What to Log on Every Call

Log these on every call, not only when something looks wrong:

- **Model name**, exactly as sent. Price and behaviour vary by model, and silent routing changes happen.
- **Input, cached and output token counts** from the usage block. This is what you are billed on, and what [cost and latency trade-offs](/docs/llms-genai/evaluation-and-serving#costlatency-tradeoffs) reason about.
- **Time to first token and total time**, separately when streaming.
- **Stop reason**, so truncated answers can be found.
- **Request ID** from the response headers, which the provider's support needs to investigate a specific call.
- **Retry count**, so a slow call can be told apart from a call that failed twice.

Without these, "why did costs spike last week" and "why was this answer cut off" cannot be answered after the fact.

## Common Problems & Fixes

| Problem | Cause | Fix |
| --- | --- | --- |
| JSON output fails to parse occasionally | Truncated at `max_tokens` | Check the stop reason; raise the cap; use structured outputs or tool calling |
| Bursts of 429s after every outage | Clients retry in lockstep | Full jitter; honour `retry-after`; a client-side rate limiter |
| Duplicate side effects | A timed-out call was retried and had already run | Idempotency keys on every tool that writes |
| Prompt cache never hits | A timestamp or user ID near the start of the prompt | Move all variable content after the stable prefix |
| Costs jump with no traffic change | A model change, or answers getting longer | Log model and output tokens per call; alert on the daily total |

## When *Not* to Use It

| Situation | Better choice |
| --- | --- |
| Thousands of offline requests with no deadline | The provider's batch API, usually about half price |
| Data that must not leave your network | A self-hosted open-weight model, see [LLM hosting and serving](/docs/mlops/llm-hosting-and-serving-patterns) |
| A fixed label set with plenty of training data | A small fine-tuned classifier is faster and cheaper per call |
| Many tools and multi-step tasks | An agent loop built on [tool use](/docs/agents/agent-fundamentals), not ad hoc calls |

## Remember

| Idea | One line |
| --- | --- |
| Stop reason | `max_tokens`/`length` means truncated; check it before parsing |
| Temperature | Divides logits; below 1 sharpens, above 1 flattens |
| Top-p | Keeps the smallest set of tokens with total probability p |
| Temperature 0 | Low variance, not a determinism guarantee |
| Streaming | Usage arrives at the end; handle mid-stream failure |
| Retry | 429 and 5xx yes; 400, 401, 403 no |
| Jitter | Random wait between 0 and the ceiling spreads retries |
| Timeouts | May have succeeded; retry only idempotent work |
| Prompt caching | Stable prefix first, byte for byte |
