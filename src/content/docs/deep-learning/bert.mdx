# BERT

[Attention and Transformers](/docs/deep-learning/attention-transformers#bert-roberta-deberta-and-sbert-encoder-only-representations) introduced BERT as the canonical encoder-only transformer. Released by Google in October 2018, it changed natural-language processing in a few months: one pretrained model, fine-tuned briefly, beat task-specific systems on eleven benchmarks at once, and "pretrain, then fine-tune" became the standard recipe. This page makes that introduction concrete: the architecture and its sizes, how the input is represented, the two pretraining objectives and what later work found about them, how a pretrained encoder is put to work, real masked-word predictions and sentence similarities computed with the actual model, the family of encoders that followed, and where encoders still beat much larger generative models today.

<ELI5>

Imagine a fill-in-the-blank worksheet where you're allowed to read the *entire* sentence — words before and after the blank — before guessing what goes in it. That's BERT: it's trained by hiding random words in a sentence and learning to guess them using context from both directions at once, not just what came before (the way GPT-style models are forced to work). Reading both directions before answering produces a genuinely richer understanding of each word's meaning in context, which is exactly why BERT-family models became the standard for tasks where you already have the full input and need to *understand* it — classification, search, extracting an answer from a passage — rather than generate new text one word at a time.

</ELI5>

## 1. The Architecture

BERT is the encoder half of the original transformer, stacked deep, with no decoder. Every layer is bidirectional self-attention followed by a feed-forward network, each with a residual connection and LayerNorm, so every token sees every other token in both directions at every layer.

| Model | Layers | Hidden size | Heads | Parameters |
|---|---|---|---|---|
| BERT-base | 12 | 768 | 12 | about 110 million |
| BERT-large | 24 | 1,024 | 16 | about 340 million |

It was pretrained on about 3.3 billion words (BooksCorpus and English Wikipedia) with a WordPiece vocabulary of 30,000 subword tokens, and inputs of up to 512 tokens. By today's standards it is small: a modern laptop runs it comfortably, which is a large part of why encoders like it remain in wide production use.

## 2. Input Representation: Three Embeddings, Summed

**What is it?** Before any attention happens, every token in BERT's input becomes a single vector built from three separate pieces of information, not just "which word is this."

**How does it work?** Each token gets three embeddings looked up independently, then summed element-wise into one vector: a **token embedding** (which word/subword this is), a **segment embedding** (which of the two sentences — A or B — this token belongs to, relevant for sentence-pair tasks), and a **position embedding** (where in the sequence this token sits). A special **`[CLS]`** token is prepended to every input, and **`[SEP]`** separates the two sentences in a pair (or marks the end of a single input).

<BertInputRepresentationDiagram />

**Why is it useful?** Summing three embeddings — instead of using only token identity — lets the same word carry different information depending on its position and which sentence it's in, before a single attention layer even runs. `[CLS]`'s role is specifically deliberate: because every token can attend to it and it can attend to every token, its final hidden state ends up summarizing the whole input, which is why it becomes the standard pooled vector fed into a classification head.

**Limitation:** All three embeddings are summed into a fixed-size vector — there's no way to recover which part of that vector "came from" token identity versus position versus segment after the fact, and this fixed setup is learned once at pretraining time, not adapted per task.

<Remember>BERT's input isn't just "the word" — it's word + which sentence + where, summed into one vector before anything else happens. `[CLS]`'s final hidden state, not any other position, is what a classification head is trained to read.</Remember>

Every token now carries identity, position, and segment information — the next question is what BERT is actually trained to *do* with that.

## 3. Masked Language Modeling (MLM)

**What is it?** BERT's primary pretraining objective: hide some of the input, and train the model to predict exactly what's missing.

**How does it work?** Roughly 15% of input tokens are replaced with `[MASK]` (or, in a fraction of cases, a random other token, or left unchanged, to keep the model from over-relying on literally seeing `[MASK]`), and the model predicts the original token at each masked position using the full bidirectional context — everything to the left *and* right of the mask. This is exactly the opposite constraint from decoder-only models: [GPT-style causal masking](/docs/deep-learning/attention-transformers#gpt-llama-mistral-and-claude-style-models-decoder-only-generation) forces token $t$ to only ever see tokens $\leq t$, precisely so it can be trained to predict the *next* token without leaking the answer — BERT has no next-token objective to protect, so it's free to look both directions at once.

**Why is it useful?** Predicting a hidden token from its full surrounding context — not just what preceded it — forces every position's representation to encode genuine two-directional understanding, which is exactly the property that makes BERT's token vectors useful for tasks like NER or extractive QA where the answer's meaning depends on what comes after it, not only before.

**Limitation:** Because 15% of tokens are masked, only a fraction of each training example contributes directly to the loss, and `[MASK]` never appears at inference time on real input — this train/inference mismatch is part of why the "80% `[MASK]`, 10% random token, 10% unchanged" masking recipe exists, to keep the model from learning to rely on a token it will never actually see outside of training.

MLM alone isn't the whole pretraining story — BERT's original recipe paired it with a second objective aimed at a different kind of understanding: relationships *between* sentences, not just within one.

## 4. Next Sentence Prediction (NSP)

**What is it?** BERT's original second pretraining objective: given two sentences A and B, predict whether B genuinely follows A in the source text, or is a random unrelated sentence.

**How does it work?** Half the training pairs are real consecutive sentences (label: "IsNext"), half are B swapped for a random sentence from elsewhere in the corpus (label: "NotNext") — the `[CLS]` token's final representation is fed into a binary classifier trained on this label, using the `[SEP]`-separated two-sentence input the earlier embedding diagram shows.

**Why is it useful?** The original motivation was giving BERT some notion of sentence-level relationships (useful for tasks like natural language inference or question-answering that depend on how two spans of text relate), on top of MLM's token-level understanding.

**Limitation — a real, worth-stating nuance, not an unqualified win:** [RoBERTa](/docs/deep-learning/attention-transformers#bert-roberta-deberta-and-sbert-encoder-only-representations) — a later, more carefully-trained BERT variant — found that dropping NSP entirely and instead training longer, on more data, with dynamic masking improved downstream performance. That doesn't mean NSP was actively harmful in every setting, but it does mean NSP wasn't the load-bearing ingredient BERT's original paper implied — a good example of a plausible-sounding design choice that a later, more rigorous ablation didn't fully hold up.

<Remember>NSP is part of BERT's original recipe, but RoBERTa's own ablation found dropping it — and just training harder on more data — worked better. Treat NSP as a real historical design choice with a real documented limitation, not a permanently-settled best practice.</Remember>

## 5. Fine-Tuning vs. Feature Extraction

Pretraining (MLM + optionally NSP) produces a general-purpose encoder — the practical question is how to actually put it to work on a specific task.

**What is it?** Two different ways to use a pretrained BERT for a downstream task, trading off how much of the model actually gets updated.

**How does it work?** **Fine-tuning** adds a small task-specific head (for example, a linear classifier reading `[CLS]`'s final vector) on top of BERT, then trains the *entire* stack — head and BERT's own weights together — end-to-end on labeled task data. **Feature extraction** instead freezes BERT entirely and uses its output vectors as fixed input features to a separate downstream model — the same pattern earlier contextual-embedding methods like ELMo used, treating the encoder purely as a representation-producing black box.

**Why is it useful?** Fine-tuning generally reaches higher task accuracy, since every one of BERT's weights can adapt to the specific task rather than staying fixed — this is why "pretrain then fine-tune" became the standard NLP recipe BERT is credited with popularizing. Feature extraction is cheaper and simpler when compute is limited, when the downstream model needs to stay small, or when the same frozen embeddings need to be reused across many different downstream tasks without retraining BERT itself for each one.

**Limitation:** Fine-tuning needs enough labeled task data and compute to update a full-size model without overfitting, and produces one specialized copy of BERT per task; feature extraction leaves real accuracy on the table by never letting BERT's own representations adapt to what the downstream task actually needs.

## 6. Running It

### Real Code: Masked-Token Prediction

Here is the masked-language-modelling objective run directly, with the [Hugging Face `transformers`](https://huggingface.co/docs/transformers/en/model_doc/bert) library and the original `bert-base-uncased` weights, printing the model's top three guesses and their probabilities for each blank:

```python
import torch
from transformers.utils import logging; logging.set_verbosity_error()
from transformers import AutoModelForMaskedLM, AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("google-bert/bert-base-uncased")
model = AutoModelForMaskedLM.from_pretrained("google-bert/bert-base-uncased")

for text in ["Plants create [MASK] through a process known as photosynthesis.",
             "The [MASK] barked at the mailman all morning.",
             "She deposited the cheque at the [MASK] before it closed."]:
    inputs = tokenizer(text, return_tensors="pt")
    with torch.no_grad():
        logits = model(**inputs).logits
    position = (inputs["input_ids"][0] == tokenizer.mask_token_id).nonzero().item()
    probs = logits[0, position].softmax(-1)
    top = probs.topk(3)
    guesses = ", ".join(f"{tokenizer.decode(int(i))} {p:.2f}" for p, i in zip(top.values, top.indices))
    print(f"{text:60s} -> {guesses}")
```

```text
Plants create [MASK] through a process known as photosynthesis. -> energy 0.15, flowers 0.15, sunlight 0.08
The [MASK] barked at the mailman all morning.                -> dog 0.28, man 0.09, dogs 0.03
She deposited the cheque at the [MASK] before it closed.     -> door 0.70, desk 0.05, counter 0.04
```

The first two are sensible: "energy" for photosynthesis, "dog" for barking. The third is instructive. A person reads "deposited the cheque" and fills in "bank". BERT puts 70% on "door", because "at the door before it closed" is a very common phrase and the model weights that local pattern over the longer-range clue. MLM teaches strong contextual statistics, not reasoning about the situation, and it's why encoders are fine-tuned before being trusted on a task.

### Why raw BERT vectors aren't sentence embeddings

A tempting shortcut is to average BERT's output vectors over a sentence and use that as an embedding for search. The next script compares that with a model fine-tuned for sentence similarity (`all-MiniLM-L6-v2`, an SBERT-style model): cosine similarity between a question and a paraphrase of it, and between the question and an unrelated one.

```python
import torch
import torch.nn.functional as F
from transformers import AutoModel, AutoTokenizer
from transformers.utils import logging; logging.set_verbosity_error()

sentences = ["How do I reset my password?",
             "I forgot my login credentials and need to change them.",
             "What is the capital of Australia?"]

def mean_pooled(name):
    tok, model = AutoTokenizer.from_pretrained(name), AutoModel.from_pretrained(name)
    batch = tok(sentences, padding=True, return_tensors="pt")
    with torch.no_grad():
        states = model(**batch).last_hidden_state
    mask = batch["attention_mask"].unsqueeze(-1)
    return F.normalize((states * mask).sum(1) / mask.sum(1), dim=-1)    # average over real tokens

for name in ["google-bert/bert-base-uncased", "sentence-transformers/all-MiniLM-L6-v2"]:
    e = mean_pooled(name)
    print(f"{name:40s} same meaning {e[0] @ e[1]:.2f}   unrelated {e[0] @ e[2]:.2f}")
```

```text
google-bert/bert-base-uncased            same meaning 0.68   unrelated 0.64
sentence-transformers/all-MiniLM-L6-v2   same meaning 0.63   unrelated 0.05
```

Raw BERT rates the paraphrase 0.68 and the unrelated question 0.64: nearly the same. Its vectors all point in similar directions, so cosine similarity barely separates meaning. The fine-tuned model gives 0.63 against 0.05, a clear separation, though it's about five times smaller (22 million parameters against 110 million).

<GoDeeper title="Go deeper: why SBERT exists, and why raw BERT embeddings aren't automatically good sentence vectors">

A natural instinct is to grab `[CLS]`'s final vector (or an average of all token vectors) straight out of a pretrained BERT and use it as a sentence embedding for similarity search. In practice this works poorly — BERT's pretraining objective (MLM) never explicitly trains `[CLS]` to make semantically similar sentences land close together under cosine similarity; it only trains `[CLS]` to be *useful once a task-specific head is trained on top of it*. **[SBERT (Sentence-BERT)](/docs/deep-learning/attention-transformers#bert-roberta-deberta-and-sbert-encoder-only-representations)** exists specifically to fix this: it fine-tunes a BERT-family model with a contrastive/siamese objective that directly optimizes for "similar sentences → nearby vectors," which is exactly the property RAG's [bi-encoder retrieval](/docs/llms-genai/retrieval-and-reranking-architectures#bi-encoder-independent-encoding-pooled-to-one-vector) depends on. Reaching for a raw pretrained BERT checkpoint as a drop-in sentence encoder, without this additional fine-tuning step, is a common and avoidable mistake.

</GoDeeper>

## 7. The Encoder Family After BERT

BERT's recipe was improved quickly, mostly by training it better rather than changing the architecture:

- **RoBERTa** (Facebook AI, 2019) trained longer, on ten times more data, with bigger batches and fresh masks each epoch, and dropped NSP. Same architecture, clearly better results.
- **ALBERT** (2019) shared weights across layers and factorized the embedding matrix, cutting parameters sharply.
- **DistilBERT** (2019) used knowledge distillation to keep about 97% of BERT's quality with 40% fewer parameters, running 60% faster.
- **ELECTRA** (2020) replaced MLM with **replaced-token detection**: a small generator fills in masks, and the encoder learns to spot which tokens were replaced. Every token gives a training signal, not just the 15% masked, so it learns far more per unit of compute.
- **DeBERTa** (Microsoft, 2020; v3 in 2021) separated content and position in attention and adopted ELECTRA-style training. It was the strongest encoder for classification tasks for several years.
- **ModernBERT** (Answer.AI and LightOn, December 2024) brought in a decade of decoder improvements: rotary position embeddings, an 8,192-token context, GeGLU feed-forward layers, alternating local and global attention, FlashAttention, and training on 2 trillion tokens including code. It is faster than DeBERTa and stronger on retrieval and code.

The most widely deployed descendants today are **embedding models**: BERT-style encoders fine-tuned contrastively on question-answer and paraphrase pairs, which power the retrieval step of [RAG](/docs/llms-genai/rag) and semantic search.

## 8. Where BERT Fits Today

BERT itself — and its direct descendants (RoBERTa, DeBERTa) — remain a strong, efficient default anywhere the task is *understanding a complete input* rather than generating open-ended text: classification, named-entity recognition, extractive question answering, and — via SBERT-style fine-tuning specifically — the embedding models behind [dense retrieval in RAG](/docs/llms-genai/rag#choosing-an-embedding-model) and the [bi-encoder half of retrieval-and-reranking](/docs/llms-genai/retrieval-and-reranking-architectures#bi-encoder-independent-encoding-pooled-to-one-vector). For open-ended generation, decoder-only models (GPT, LLaMA, and the rest of the [decoder-only family](/docs/deep-learning/attention-transformers#gpt-llama-mistral-and-claude-style-models-decoder-only-generation)) are the right tool instead — the two families solve genuinely different problems, not competing versions of the same one.

## 9. When *Not* to Use a BERT-Style Encoder

| Situation | Better choice |
|---|---|
| Generating text: answers, summaries, code | A decoder-only language model |
| Sentence or document embeddings for search | A contrastively trained embedding model, not raw BERT outputs |
| Documents much longer than 512 tokens | A long-context encoder such as ModernBERT, or chunking |
| A classification task with no labelled data at all | Zero-shot prompting of an instruction-tuned LLM, or an NLI-based zero-shot classifier |
| High-volume classification with labelled data and tight latency | An encoder is often the *right* choice here: fine-tuned, it is fast, cheap and accurate |
| Tasks needing world knowledge or multi-step reasoning | A large generative model; small encoders hold little of either |

## Remember

| Idea | In one line |
|---|---|
| Architecture | The transformer's encoder stack only; every token attends both ways |
| Sizes | Base 12 layers, 768 wide, 110M; large 24 layers, 1,024 wide, 340M |
| Input | Token, segment and position embeddings summed; `[CLS]` first, `[SEP]` between |
| MLM | Mask 15% of tokens (80/10/10 recipe) and predict them from both sides |
| NSP | Was the second objective; RoBERTa found dropping it and training longer did better |
| Using it | Fine-tune the whole model with a small head, or freeze it and extract features |
| Measured | Sensible fills, but "door" over "bank": statistics, not reasoning |
| Embeddings | Raw BERT vectors barely separate meaning; contrastive fine-tuning fixes it |
| Family | RoBERTa, ALBERT, DistilBERT, ELECTRA, DeBERTa, ModernBERT |
| Today | Fast, cheap, accurate for classification, extraction and retrieval |
